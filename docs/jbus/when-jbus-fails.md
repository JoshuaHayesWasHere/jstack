# When jbus fails

A failure that repeats is told once, and so is its end. jbus counts these kinds of failure in a row:

- `pass`, a pass that did not finish. `jbus.service` has `OnFailure=jbus-failed.service`, which runs `jbus alarm` to count it.
- `webhook <project>`, a POST the project's own webhook did not take.
- `top-level webhook <project>`, a POST of the project's events that the top-level webhook did not take.
- `blocking webhook <project>`, a body of the project's that the second target did not take.
- `jmerge <project>`, a `jmerge` that did not run. When it stopped because it could not ask GitHub, the alert's `<why>` is its line, `wait: could not ask GitHub: gh exited <code>: <what gh said>`; a run of such passes is one streak whatever the text of each says. A pass of jbus that cannot ask GitHub says the same, `wait <project>: could not ask GitHub: gh exited <code>: <what gh said>`.
- `snapshot`, a snapshot of the homes' state that did not finish. `jbus snapshot --alarm` counts it.
- `stale`, a look that found no pass ended in the last 2 hours. `jbus-stale.timer` runs `jbus alarm --stale 2h` every 15 minutes, from 2 hours after boot or install, apart from `jbus.timer`, so a `jbus.timer` that is stopped or disabled, or a `jbus.service` that never starts, is caught: `jbus-failed.service` runs only when a pass fails, and a timer that is stopped fails nothing. The look reads the end of the last pass from `~/.local/state/jbus/pass.json`, or its start while a pass runs or after one that died, and with no `pass.json` at all it counts too. The next pass in which nothing raised ends the streak. The look runs the same `jbus` program as the pass, so a jbus that cannot start at all (an import that fails) stops both, and nothing alerts: that is the limit of this watch.

The alert goes out after 3 failures in a row, and for `snapshot` and `stale` after the first, as `alert: <key> failed <n> times in a row since <HH:MM zone>: <why>`. Later failures say nothing. The first success after an alert sends `recovered: <key> after <n> failures since <HH:MM zone>`. An alert is a `user` event, so it goes to both webhooks, and the one that works says the other failed. jbus raises a `pass`, `snapshot` or `stale` alert on the desktop with `notify-send`, and the others while the project's own webhook is failing. Every alert also waits in each project's outbox, goes to the webhook, and from there to the relay ([The relay](the-relay.md)) where a webhook names it: where none does, an alert reaches the desktop, the outbox and the webhook only.

A pass goes on past a project that raises. It prints `pass failed <project>: <error>`, launches nothing in that pass, runs the other projects, and then `jbus poll` exits 1. jbus stops a `jmerge` it runs after 17 minutes and any other command after 300 seconds, and the unit stops a pass after 20 minutes (`TimeoutStartSec=20min`), so a command that hangs cannot hold every later pass. A fresh check runs outside the pass ([jmerge](../../features/jmerge/docs/jmerge.md)), and a pass does not wait on one. A pass that finds the lock held prints `busy` and ends.

`jbus status` prints `~/.local/state/jbus/status.json`, which every pass rewrites. It has the time of the last pass, when the sign-in runs out, `sign_in_reminder`, the days the sign-in reminder is due ([Set up jbus](set-up-jbus.md)), the open failure streaks, the homes not on the bus ([Add a project](add-a-project.md)), and each project's last error and the number of events in its outbox. A project posted to the top-level webhook beside its own also has `top_level`, the same three counts for that webhook, and with a second target set it has `blocking`, the same for that one. The view's Bus card shows each outbox. It says what a webhook that is down cannot. The first pass of each hour queues a quiet `heartbeat` event from the same file.

Beside it a pass leaves `pass.json`: when the pass started and ended, and for each project its open rows and its `threads`. `threads` is every thread T3 Code lists as not settled, a crewmate's, a reviewer's, a scout's, a home's or any other, each with its role, slug, status, `updatedAt` and its liveness: `moving`, `quiet`, `hung`, `waiting`, `ended` or `unknown`. A turn that has written no item for 10 minutes is `quiet`: jbus counts from the pass that last saw the thread's count of items change, since T3 Code moves `updatedAt` when a message is queued. It is `hung` after 20 minutes, or after 10 with a run queued behind it, and jbus reads only a quiet thread to learn that. A thread that turns `hung` is one `stall` event for that thread and that run, and one line of `hung.jsonl` in the project's state directory. A later pass adds a line there with what became of it: `wrote again`, `interrupted` or `ended`. jbus interrupts no thread and sends a hung one nothing.
