## 1. What a top professional would do
An observability engineer, of the kind who builds metering for LLM workloads, would do two things the task does not ask for:
- They would derive every number from the per-request `usage` records the API already returns, and never from a count someone made by hand.
- They would reconcile the derived totals against an independent ledger before trusting any dashboard. "Digestable" comes after "correct to the token", not before it.

They would also join tokens to task and home through IDs that are already in the data (session id, cwd, brief slug, jbus thread). They would not tag anything by memory.

## 2. The rawest material
- `~/.claude/projects/*/*.jsonl`, the session transcripts. Each assistant line carries `message.usage.{input_tokens,cache_creation_input_tokens,cache_read_input_tokens,output_tokens}`, `sessionId`, `cwd` and `timestamp`. These replace the hand-kept token tallies.
- The transcript lines where a context summary or compaction happened, plus each turn's running `input + cache_read + cache_creation`. These replace guessing how full the context was.
- `tasks/<slug>.md` briefs (their `Task:` and `Result` lines) and the jbus thread and message log (`jbus` history or its store on disk). Joined to `sessionId`, these replace remembering which session served which task and which home.
- The Anthropic Console usage and cost export (CSV) for the same days. This replaces trusting the local numbers on their own say-so.

## 3. The methods and tools
- `jq -c 'select(.message.usage) | {s:.sessionId, cwd, t:.timestamp, u:.message.usage}' ~/.claude/projects/*/*.jsonl`: extracts raw events first and leaves aggregation for later.
- `duckdb` (or `sqlite3`) with `read_json_auto('~/.claude/projects/*/*.jsonl')`: puts the events in one table with views per task and per home. This makes the rollup a query that can be rerun, and nobody re-adds by hand. If duckdb is missing, install it with `pacman -S duckdb`.
- `npx ccusage@latest daily --json`: an independent parser of the same transcripts, used to cross-check the query's daily totals.
- `/context` and `/cost` inside a live session: spot checks of a single session's context size against the derived peak.
- `watch -n 60 duckdb … -c 'select …'`, or a static HTML page regenerated by `make` or a `systemd --user` timer: the digestible view, built only after the numbers reconcile.

## 4. What outside the agent shows it is right
- The derived totals for a past week must match the Anthropic Console usage export within 1% per day and per model. That target is reasonable for metering.
- `ccusage daily` must agree with the duckdb daily totals to the token.
- For one task the user has already counted by hand, the per-task query must reproduce the user's figure, or explain the gap line by line, for example a cache read the user missed.
- The user must be able to answer "which home spent the most context yesterday" from the view in under 10 seconds, without opening a transcript.
