# review-concurrency: let up to three reviews run at once instead of one at a time

Task: "Something is blocking our process and making a run in a one at a time basis or something", and, asked how many reviews may run at once: "three at a time"

Done when:
- The cause of the one-at-a-time behaviour is found and named in the PR description. It could be a lock, a semaphore, a queue, a sequential loop or a blocking wait.
- Up to three reviews run concurrently.
- A fourth review waits until one of the three finishes, then starts. It is not dropped or failed.
- The limit of three is set in one place, not scattered as literals.
- A test starts more than three reviews. It asserts that no more than three run at once and that all of them complete.
- Existing tests pass.

Where: the code that dispatches and waits on reviewers (the Python commands and any skill or playbook text that starts reviews), and the shared state they coordinate through (locks, queues, worktree or process bookkeeping).

Do not touch: how scouts and crewmates are scheduled; review content, prompts or verdict format; any concurrency limit other than the one for reviews.

Decisions: how many reviews may run at once: "three at a time"

Design: none. This removes a serialising bottleneck and puts a fixed cap in its place, at a value the user already chose. There is no structural choice to make.
