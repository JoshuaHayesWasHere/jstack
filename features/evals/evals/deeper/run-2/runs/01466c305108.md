# thread-cap-headroom: replace the fixed thread cap with a limit sized from machine load and past runs
Task: "I was just warned that I hit an arbitrary thread limit despite being at 3.5 of 12 cores used address this, I want to push my machine as hard as I can without going over the edge" and "is the cap relevant? Can we go higher based off the past runs we've done?"
Done when:
- The code that sets the thread cap and raises the "limit hit" warning is found, and the brief's reply names it with its path and line.
- The reply says whether the cap is still needed, based on CPU, memory and load numbers from past runs: the peak cores used, the peak memory, and the threads running at that peak.
- The cap is set from the machine's real headroom, meaning cores, free memory and current load, or from a higher value that the past-run data supports. It is no longer a fixed number.
- A guard still stops new threads before the machine is overloaded. The reply states the threshold and why it was chosen.
- When 3.5 of 12 cores are busy and memory is under the threshold, the warning does not fire. When the threshold is crossed, the warning still fires. Tests cover both cases.
- The existing tests pass.
Where: the code that spawns home threads, scouts, crewmates and reviewers and counts them against the cap; the setting or constant that holds the cap; the warning message; the logs or records of past runs.
Do not touch: what scouts, crewmates and reviewers do once they are running; any playbook's steps that do not concern the thread count.
Decisions: "I want to push my machine as hard as I can without going over the edge"
Design: none, this replaces one limit with a check sized from measured headroom and does not change how the parts fit together
