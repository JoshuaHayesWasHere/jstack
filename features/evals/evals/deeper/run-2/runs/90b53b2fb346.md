# make-check-slowdown: diagnose what makes `make check` slow, and why, without fixing it
Task: "figure out what is slowing down make check and why"
Done when:
- A baseline from `hyperfine --warmup 1 --runs 10 'make check'` is reported as mean ± σ, both warm and cold (`--prepare 'make clean'`)
- Wall time is broken down by target (`make --trace` with `ts -s '%.s'`, or `remake --profile`), by test (`pytest --durations=0` or the runner `check` uses), and by import (`python -X importtime`)
- CPU time is located with `py-spy record --subprocesses`, and the run is classed as CPU-bound or waiting with `perf stat` and `pidstat -u -d 1`. Spawns and syscalls are counted with `strace -f -c make check`
- The attribution accounts for at least 95% of the measured wall time
- Each named cause is confirmed by a controlled hyperfine run with that cause removed, and its measured saving matches the prediction within noise
- If the slowness is a regression, the commit is found with `git bisect run` and a hyperfine threshold, not by guessing
- The report names the changes that would bring warm `make check` under half its current time, and cites the measurements that show it
- The CI log's step timings for `make check` are compared with the local numbers
Where: `Makefile` and every file it includes, the output of `make -n check`, the test suite and runner that `check` invokes, the CI config and the CI log for `make check`
Do not touch: anything in the repo. No fixes and no edits to the `Makefile`, tests or CI config. The controlled "cause removed" runs go on a scratch branch or in a worktree and are not committed
Decisions: "Do not fix anything; this is diagnosis." "Start from the raw material, not from impressions." "If it regressed, find the commit with `git bisect run` and a hyperfine threshold instead of guessing."
Design: none, this is a measurement and diagnosis task with no code to design
