# thread-cap-headroom: Measure real headroom and raise the thread cap to the knee, or name what it guards
Task: "I was just warned that I hit an arbitrary thread limit despite being at 3.5 of 12 cores used address this, I want to push my machine as hard as I can without going over the edge" and "is the cap relevant? Can we go higher based off the past runs we've done?"
Done when:
- The warning's exact text is quoted from `journalctl` or the home's log.
- The cap's definition is located (`rg` for max_threads/workers/concurrency), and `git log -S` on its value explains why it was set.
- Cgroup `TasksMax`/`MemoryMax` and `ulimit -u` are reported, along with whether either is the real limit.
- The past runs' logs are summarized with thread count, duration and exit status, and checked against `sar` history and `journalctl -k` for OOM or throttling on those dates.
- A ramp table covers N from the current cap to 16 in steps of 2. Each step is timed with `hyperfine --runs 3` and watched with `vmstat`, `pidstat -t`, `/proc/pressure/*` and `free`. Columns: N, time and spread, peak RSS, PSI memory/cpu avg10, swap, and the `rg -c '429|rate.?limit'` count. The table shows the knee.
- The new cap is the highest N that still gains ≥10% throughput over N-2, and at that N:
  - zero OOM kills and zero throttle lines appear in `journalctl -k`;
  - PSI memory some avg10 is < 5% and swap stays flat;
  - CPU use is about 10 of 12 cores sustained.
- One real run at the new cap beats the user's last run at the old cap, with both times shown.
- If the cap guards something other than CPU (memory, I/O, API rate limits), the brief's result names it and shows its number instead of raising the cap.
Where: the file and line that define the thread/worker/concurrency cap (found by `rg`); the home's log and `journalctl`; the past runs' logs; `sar` history; cgroup and ulimit settings (read only)
Do not touch: system cgroup, `TasksMax`, `MemoryMax` and `ulimit` settings (report them, don't change them); the past runs' logs; any limit other than the one cap; N above 16
Decisions: "push my machine as hard as I can without going over the edge"; "Ramp concurrency in steps of 2 from the current cap to 16, timing each step with `hyperfine --runs 3`"; "Set the new cap at the highest N that still gains ≥10% throughput over N-2"; "If the cap guards something other than CPU, say what it is and show its number instead of raising it."
Design: none, the user set the method, the thresholds and the rule for choosing N, so the only change is one cap value picked by measurement
