# review-concurrency: let reviews run three at a time instead of one at a time

Task: "Something is blocking our process and making a run in a one at a time basis or something" and, asked how many reviews may run at once: "three at a time".

Done when:
- The cause of the one-at-a-time behaviour is named in the PR description: the lock, queue, semaphore or wait that serializes reviews, with its file and line.
- Up to three reviews run at the same time. Starting three reviews together shows all three running before any finishes.
- A fourth review waits until one of the three running reviews finishes, then starts. It is not dropped or failed.
- The limit of three lives in one place: a constant or a setting, not values scattered through the code.
- Crewmates, scouts and the home thread are not newly limited or serialized by the change.
- A test covers the cap: three run at once and the fourth is held.
- The existing tests pass.

Where: the code that dispatches and schedules reviewers, meaning the Python commands and any skill or playbook text that starts reviews or waits on them, plus any shared lock, queue or state file they use.

Do not touch: how crewmates and scouts are scheduled, except where they share the review mechanism and must keep their current behaviour; what a review checks or outputs.

Decisions: "three at a time".

Design: none, this finds what serializes reviews and caps them at a fixed number; the user already chose the number.

Pull request: open one when done

Review: review

Playbook: none
