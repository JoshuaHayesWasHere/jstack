# parallel-tests: run the test suite in parallel with pytest-xdist, with shared state made per-worker first
Task: "run the test in parallel"
Done when:
- hyperfine's median parallel wall time is ≤ ¼ of serial, or the single slowest test is named as the floor
- the parallel junit xml has the same tests and the same pass/fail set as serial.xml
- 20 random-order parallel runs all pass (`pytest --count 20 -n auto -x` with pytest-randomly)
- the CI log shows the parallel step green with its new duration
Where: tests/, conftest.py, the pytest config (pyproject.toml / pytest.ini / setup.cfg), the dev/test dependency list, the CI workflow that runs pytest
Do not touch: test assertions or what each test checks; no skipping, xfailing or deleting tests to make the parallel run pass or go faster; non-test source code
Decisions: "Start from the raw numbers, not an impression: run `pytest --durations=0 -q --junitxml=serial.xml`, read the last CI run's log for its timings, and check `nproc`/`lscpu` here and on the CI runner." "Grep tests/ and conftest.py for shared state (/tmp paths, ports, sqlite files, session fixtures) and make each one per-worker (tmp_path, worker_id-suffixed names) before parallelising." "Parallelise with pytest-xdist (`-n auto`), choosing --dist loadscope or loadfile to fit the fixture scopes." "Flush out coupling with pytest-randomly and `pytest --count 20 -n auto -x`." "Measure with `hyperfine --warmup 1 --runs 5` serial against parallel at several worker counts, and use pidstat to see whether the cores are saturated."
Design: none, the user already chose the tool, the dist mode options, the isolation approach and the measurements, so there is no design call left to make
