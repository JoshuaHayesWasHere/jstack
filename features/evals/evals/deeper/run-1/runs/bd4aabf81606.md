# check-runner-flip: measure what slows `make check` on GitHub's runners vs the current runner, and why

Task: "figure out what is slowing down make check and why", the part that asks what changes at the flip to GitHub's runners
Done when:
- The per-step table for both runner types is in hand: at least 5 runs of the check workflow on one SHA, on the current runner and on ubuntu-latest, with every number a median and its spread
- Each gap between the runners is attributed to a named resource (cores vs -j, disk/tmpfs, network fetches, cold caches, CPU model)
- The top cause comes with a predicted saving
- A hosted run measures that saving within the spread
Where: the Makefile's check target; .github/workflows/*.yml (runs-on, -j, cache steps); a diagnostic step on each runner type that prints nproc, free -h, df -h, lscpu and mounts
Do not touch: the rest of "what is slowing down make check" that has nothing to do with the runner flip; runs-on on the default branch (measure on a branch, don't flip it); the check target's behaviour beyond adding measurement
Decisions: "Start from the raw runs, not memory: pick one SHA, get at least 5 runs of the check workflow on the current runner and on ubuntu-latest (gh run list --json …, gh run view <id> --log)". "Measure, don't guess: per-step times from the run logs, per-target times from make --trace | ts -s (or remake --profile), per-test times from the test runner's --durations, and CPU/IO/idle from /usr/bin/time -v and pidstat -u -d 1. Report every number as a median with its spread." "Target: make check on GitHub's runners no slower than on the current runner."
Design: none, this is measurement and attribution, and the user already set the method and the done checks
