# make-check-slow-diagnosis: Find what makes `make check` slow, and why, with numbers anyone can reproduce

Task: "figure out what is slowing down make check and why"

Done when:
- A `hyperfine --warmup 1 --runs 5` breakdown attributes at least 90% of `make check`'s wall time to named targets, tests or imports.
- Each named cause is backed by a profile (`py-spy record`, or `perf record -g` for non-Python steps) or by `pytest --durations=0` output.
- Removing or stubbing each cause cuts roughly the claimed time in a fresh hyperfine run.
- If history shows a regression, `git bisect run` with a timing threshold names the commit, and a parent-vs-commit hyperfine run reproduces the slowdown.
- The report lists the exact commands, so the user can re-run them and get the same numbers.

Where: the Makefile and every file it includes; the test suite and its config (pytest config, conftest files); `git log` for the Makefile, tests and config; recent CI runs of `make check` (`gh run view <id> --log`).

Do not touch: any committed code, Makefile, test or config. Stub or remove causes only in a scratch worktree to measure them, and throw the stubs away afterwards. Do not push anything.

Decisions: "Do not fix anything; diagnose only." "Start from the raw material, not from impressions": read the Makefile and its includes, get the real step list with `make -n check` and `make --trace check`, and time each output line with `ts -s`. "Measure before explaining": baseline with hyperfine, then each sub-target the same way. Separate collection/import time (`--collect-only`, `python -X importtime`) from test run time. Use `/usr/bin/time -v` and `pidstat` to tell CPU-bound, I/O-bound and idle time apart. Compare `make -j$(nproc) check` to see whether serialization plays a part. "Install anything missing with pacman or pipx."

Design: none, this is a diagnosis that changes no code, so there is no design call to make
