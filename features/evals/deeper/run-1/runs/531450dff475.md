# parallel-tests: run the pytest suite in parallel with pytest-xdist, after finding and isolating order-dependent tests
Task: "run the test in parallel"
Done when:
- The serial baseline is recorded first: the output of `pytest --durations=0 -q`, `nproc` on this machine, and the CI runner's core count from its workflow config.
- Every order-dependent test that `pytest -p randomly` turned up over several seeds is fixed or isolated, using tmp_path or a per-worker DB/port via worker_id.
- `hyperfine --warmup 1 --runs 10 'pytest -q' 'pytest -q -n auto'` shows a parallel mean within 1.5× of serial ÷ nproc, and the two spreads do not overlap.
- `pidstat -u 1` during a `-n auto` run shows the workers saturating the cores.
- 20 consecutive `pytest -q -n auto -p randomly` runs pass, each with the same test count as the serial run.
- The next CI run's log shows a shorter suite time and an unchanged passed count.
- The report includes the before/after hyperfine table and each test that was isolated, with the reason.
Where: conftest.py and every session- or module-scoped fixture; tests/, especially shared temp paths, ports, sqlite/.db files and os.environ writes; the dev dependency config for pytest-xdist and pytest-randomly; the pytest invocation in the CI workflow.
Do not touch: jstack's skills, playbooks and Python commands outside tests/; what any test asserts. Do not skip, xfail or delete tests to make the suite pass or run faster.
Decisions: "add pytest-xdist and run with `-n auto`, choosing `--dist loadfile` or `--dist loadscope` to fit the fixture scopes"; "Before changing anything, run the suite under `pytest -p randomly` over several seeds, and fix or isolate any order-dependent test you find (tmp_path, per-worker DB/port via worker_id)"
Design: none, the user already set the approach (xdist with `-n auto`, the dist mode picked from the fixture scopes, isolation through tmp_path and worker_id) and the remaining choices depend on what the fixtures turn out to be
