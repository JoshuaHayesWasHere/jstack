The ten steps

The same numbers as the picture, one line each.

  1. 1Plan entryThe operator says what they want. The home writes one entry per pull request in plan.md, with a "Done when" list.the operator, with the home
  2. 2BriefThe home writes tasks/<slug>.md: the task, where it may work, its Proves it:, Design:, Review: and Playbook: lines.a model: the home
  3. 3The queue and the approvalThe brief waits as a row of the queue. The operator approves that exact brief, named by its sha.the operator
  4. 4Launchjbus launches an approved row once its depends are merged and jgauge room prints go.a command, no model
  5. 5The worktreeA new thread in its own worktree, on a branch named for the slug, works the brief by its playbook.a model: the crewmate
  6. 6The checkThe repo's check command runs once, under a test slot. CI runs the repo's checks on the pull request the crewmate opens, and jmerge waits for the check named check, or for the checks the repo lists in required-checks.a command, no model
  7. 7The reviewOne fresh thread reviews each pull request, with no reviewer subagents. It reads the diff itself, judges what it found, and proves one safety fact by running code. It fixes nothing.a model: the reviewer
  8. 8The findingsThe crewmate ends every finding with a Finding: line, fixed or not fixed and why, then writes one Fixed: line.a model: the crewmate
  9. 9jmergeMerges what is reviewed, fixed and green at the head that was checked. For the rest it prints wait or hold and the reason. jbus runs it on each pass, and no home runs it to merge.a command, no model
  10. 10The sweepjmerge --sweep removes the worktree and the branches a finished thread left, and prints what it kept and why.a command, no model
before step 2, sometimesA scout goes firstWhen the home cannot write the brief from what it knows, a scout reads the code and the docs and writes down what it found. The home itself never reads the code.
at any stepA gateWhen a thread gets a question only the operator can answer, it takes a default and keeps working. It records the question with jbus gate, which numbers it and keeps it until the operator answers.
at step 9, rarelyA holdA plain jmerge never merges a pull request that touches a protected path. Only the operator can accept it.
With a home thread and no queue

A repo can run with a home thread, with jbus and its queue, or with both. With a home thread alone, steps 3 and 4 happen in the thread. The operator says yes to the plan entry there, and the home launches the crewmate itself after jgauge room prints go. With jbus alone, jbus launches only the approved rows of the queue. A release install writes a jbus config with dispatch = false, so jbus launches nothing until the operator sets it up.

How to use it: your first day

Three things to do, then choose who merges.

  1. 1Start a homeIn T3 Code, type /new-home <path> with the path of the repo's main checkout. Once that home ends, the next thread you open in the project becomes the home by itself, or you type /home in one.back: where things stand
  2. 2Plan one taskSay what you want. The home asks until the shape is settled.back: a plan entry and its brief
  3. 3Approve itRead the brief and say yes.back: a crewmate you can watch and steer
  4. 4Merge itThe build, the review and the fixes run by themselves. Nothing merges until you choose who runs jmerge. Run it in the main checkout, or let the jbus timer run it on each pass once the repo is a project in its config, or put one home's id in home-thread.back: one merged line
Before the first day

Install once. The README's Quickstart gives the curl line that fetches the latest release's install.sh and pipes it to sh. The script installs uv where it is missing, installs the nine commands as the uv tool jstack, and runs jinstall --setup. Setup links the skills for Claude Code, Codex and Cursor, adds the hooks, and prints a needs you line for each thing only you can do, such as gh auth login. Run jinstall --setup again until no such line is left, then jinstall --check.

Ending the day

Type /handoff in the home. It updates the plan and the notes and writes a one-page handoff. Tomorrow's home starts from that page, not from today's chat.

How to use it: what you are asked for, and when

Three things come to you. Without asking the operator, the threads do everything else that is reversible.

An approval

A brief is ready, or it changed after your go, or an approved task depends on one you have not approved.

You give: a yes to that exact brief.

A gate

A thread met a question only you can answer. It took a default and carried on. The home shows open gates at its start, on a status request, and when the planned work is done.

You give: keep the default, or change it.

A held pull request

jmerge printed hold: the change touches a protected path, or a review did not uphold a line dropped in a rebase.

You give: jmerge --accept <number> --by <user> --at "<date and time>", where <user> is the user of your jstack config. Add --check to see what it would do. jmerge refuses --accept unless the review proved the fact that makes the change safe.

What wait means

A pull request that waits is not a failure and asks nothing of the operator. jmerge prints the first thing it is short of, such as a check that has not passed, and a later run merges it once the reason is gone.

Run the pipeline Five make a thread a role: home, crew, scout, the reviewer of pr-review, and expert. Each is the full text of what that thread does. The others close a home, set one up or switch it off, answer a help question, set up the machine, and make a bot's page.

/home

Makes this thread the repo's home. It reads the last home's note and what jbus holds, plans with the operator, writes each brief and launches its crewmate. It does none of the work.

Reach for it when you start or continue work in a repo.

autopilot-stack

For: A queue of approved entries that each need the one before, built as one linear stack of pull requests that the operator reviews and lands.

orchestrate

For: A standing program: many entries toward one goal that outlives a single home, worked to a predicate that can be counted.

For: Landing a stack that autopilot-stack built, on the operator's word, bottom link first and one link at a time.

session-pickup

How a thread uses a playbook

The thread copies the playbook's numbered steps into its todo list, word for word, and works them in order. A step it does not do stays in the list as skip: <reason>. Playbook: none, or no line, means the thread works by its skill alone. Where a playbook and the skill disagree, the skill wins.

jmerge no model

Decides
Whether an open pull request merges, waits or is held.
Rules in
features/jmerge/src/jmerge/ready.py
Run by
jbus on each pass, or a home while home-thread holds its id, or the operator by hand
What ready means
  • A brief names the pull request, and its base is the default branch.
  • The review is written, every finding has its Finding: line and the Result has its Fixed: line.
  • The check named check, or each check the repo's required-checks file lists, passed at the head, and that green still covers today's default branch.
  • A rebase kept every line.
  • A protected path (secrets, keys, the merge rules' own lists) is a hold. A guarded path merges only with the review's proven safety fact, and guarded.txt lists none.

jbus no model

Decides
Which approved rows of the queue launch on this pass, and what is told to whom. It makes no judgment call. A case that no rule covers becomes one gate line.
Rules in
features/jbus/src/jbus/dispatch.py
Run by
a timer, one pass a minute
One pass
  • Runs jmerge, unless home-thread holds a home's id.
  • Reads the briefs and the scout requests, and makes one event for each new Result, Review, Report and gate.
  • Asks for the threads and the pull requests, and ties each crewmate to its thread.
  • Launches the approved rows, lowest priority number first.
  • Says what waits on the operator, and sends what it found to the project's webhook.

jgauge room no model

Decides
Whether the machine and the plan have room for one more thread. It prints go, or wait: and the first reading with no room.
Rules in
features/jgauge/src/jgauge/room.sh
Run by
the home before a launch, a crewmate before a review, jbus before each launch
The readings
  • CPU pressure, the share of the last minute something waited for a core, and the one-minute load against the cores as a backstop.
  • The memory available, and memory pressure.
  • The plan's five-hour and weekly limits.
  • A machine reading it cannot read is a wait. A plan limit it cannot read stops nothing.

jroles no model

Decides
Which model a launched thread of a role runs on: crew, scout, review or home. With no line for the role, the launch inherits its launcher's model.
Rules in
features/jroles/src/jroles/cli.py
Run by
any thread, before it launches one of that role
The role map
  • One line a role in the operator's jstack/roles config file: <role>: <provider> <model>.
  • <role>: inherit is the same as no line.
  • When it cannot use a map, it says so on stderr, and the launch inherits.

jdrift no model

Decides
Which of the files taken from the upstream skill stack are same, changed or gone since the pinned commit, and which upstream files are new.
Rules in
features/jdrift/src/jdrift/cli.py
Run by
whoever works on jstack, as make pstack-drift in a checkout
What it reads

Four more commands decide nothing on the path. jbriefs writes every brief of every home on one page. jinstall installs, checks and removes jstack. jleak refuses a push or a pull request that leaks what must stay private, and keeps AI co-author trailers out of commits. jpack checks a context pack. The README's Reference links a page for each of the nine.

Mindset

Four rules the system is built on, then the principles a playbook step names.

1Disk is the record, and a thread is disposable.

A thread can end at any time. The next one starts from the files in the state directory, so nothing that matters lives in a chat.

handoffsession-pickuppause-safely

2Judgment in threads, repeatable steps in commands.

A model plans, writes and reviews. Whatever has the same answer every time is a command with no model, whose rules are one file.

jmergejbusjgauge room

3A gate takes a default, so work never waits.

When a question only the operator can answer comes up, the thread takes a default and keeps working. It records the question in a gate, with that default, the work that depends on it, and how to undo it.

crewscouthome

4A test must execute something.

A test runs the shell a skill tells an agent to run, parses a block out of it, or runs the script. Finding a sentence in a file is not a test.
