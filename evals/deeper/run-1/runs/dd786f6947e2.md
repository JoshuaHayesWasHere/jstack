# thread-cap-from-load: Replace the fixed thread limit with one based on real machine load and past runs

Task: "I was just warned that I hit an arbitrary thread limit despite being at 3.5 of 12 cores used address this, I want to push my machine as hard as I can without going over the edge" and "is the cap relevant? Can we go higher based off the past runs we've done?"

Done when:
- The answer to "is the cap relevant?" is written up from the data of past runs: peak threads, CPU, memory and load seen, and whether any run came near the edge. It says how much higher the cap can go and why.
- The fixed thread cap is replaced by, or raised to, a limit that comes from measured headroom (cores, memory and load) and is backed by those past runs, not by a hard-coded number.
- At 3.5 of 12 cores used, with memory to spare, the warning no longer fires and new threads can still start.
- A guard still stops new threads before the machine goes over the edge. It covers CPU, memory and load, and a test or dry run shows it fires when headroom is gone.
- The warning text names the resource that is short and its numbers, not just the thread count.
- The existing tests pass.

Where: the code that counts threads and enforces the cap, the warning it prints, any config or constant that holds the limit, and the records or logs of past runs used as evidence.

Do not touch: limits that are not about how many threads run at once, the skills and playbooks apart from where they read the cap, and the past-run records themselves (read them only).

Decisions: "I want to push my machine as hard as I can without going over the edge"; "Can we go higher based off the past runs we've done?"

Design: none, it retunes one existing limit against measured data and does not change how threads, scouts or crewmates fit together.
