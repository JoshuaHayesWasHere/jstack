# raise-thread-cap: Measure past runs and step the worker cap up until throughput stops rising

Task: "I was just warned that I hit an arbitrary thread limit despite being at 3.5 of 12 cores used address this, I want to push my machine as hard as I can without going over the edge" and "is the cap relevant? Can we go higher based off the past runs we've done?"

Done when:
- The brief's report names the file and line where the thread limit and the warning text are defined (found by grepping `~/.claude`, `~/.config` and the jbus source), and says what resource that number was meant to protect.
- The report lists the hard ceilings as read on this machine: `ulimit -u`, `ulimit -n`, `/proc/sys/kernel/threads-max`, and the user slice's `pids.max`.
- For each past run the report shows the live worker count and tasks completed per hour. Beside them it shows that run's sar history from `/var/log/sa/saDD` (`-u -r -q -B`), any OOM kills from `journalctl -k`, and any 429, rate-limit or timeout errors in the jbus and crewmate logs. It also names the resource that came closest to its limit: CPU, memory, I/O, pids, or the API.
- sysstat is installed, or the report confirms it was already present.
- The report has a table of steps, starting at the current cap and rising in increments of 2, with the same fixed workload at every step. Each row gives throughput, `/proc/pressure/{cpu,memory,io}`, MemAvailable, swap-in from `vmstat 5`, per-worker RSS from `pidstat -u -r -t 5`, and the API error rate.
- The new cap is the last step at which throughput still rose. Over a full run at that cap:
  - memory `full avg60` = 0
  - cpu `some avg60` < 10%
  - no swap-in
  - no OOM kills
  - no 429s in the logs
  - roughly 10 of 12 cores busy
- The report quotes the config line that changed, showing the old value and the new one. If the cap should not go up, the report instead shows the counter that proves it, and the config is left as it was.

Where: the thread/worker limit and its warning, wherever they are defined (`~/.claude`, `~/.config`, jbus source); the jbus and crewmate logs; `/var/log/sa/`; `journalctl -k`; `/proc/pressure/`; `/proc/meminfo`.

Do not touch: the kernel and user-level ceilings (`ulimit` settings, `threads-max`, systemd slice `pids.max`). They are to be read only, never raised. Also off limits: any other jstack config, and the skills and playbooks apart from the one cap line.

Decisions: "I want to push my machine as hard as I can without going over the edge"; "Start from the raw data, not impressions"; "step it up from the current value in increments of 2, with a fixed workload at each step"; "Install sysstat if it is missing"; "Aim for ~10 of 12 cores busy"; "If the answer is that the cap should not go up, show the counter that says so."

Design: none, because the task is to measure one existing number and retune it, with no new structure to design.
