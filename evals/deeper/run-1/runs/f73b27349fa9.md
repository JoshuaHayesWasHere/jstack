# ci-chrome-hang: find and fix why the first public CI check hangs at 92–95% with Chrome left running
Task: "jstack's first public check never finished: two attempts on `ubuntu-latest` hung after the dots reached 92% and 95% and were cancelled at the job's 15-minute limit, with Chrome processes still running." Find out why and fix it. Do not fix it by raising the limit or adding retries. Start from the raw runs, not the summary: `gh run view <run-id> --log` for both attempts. Map each last `[ 92%]`/`[ 95%]` line to a test ID using `pytest --collect-only -q` in the same order, and say whether both attempts stopped on the same test. Read `.github/workflows/*.yml` and the fixtures that launch and quit Chrome. Record the runner image, the Chrome and chromedriver versions, and the CPU and memory from the log header. Make the hang report itself before changing any code. Run CI with `pytest -v -p no:randomly --timeout=120 --timeout-method=thread` and set `faulthandler_timeout` in pytest.ini. Add a step guarded by `if: failure() || cancelled()` that dumps `ps -ef --forest`, `pgrep -a chrome`, and `py-spy dump` of the pytest process. Reproduce in the same image (`act` or `docker run ubuntu:24.04`), then bisect the test order down to the smallest set that hangs, and measure how often it hangs with `pytest --count 20`. It is done when a run that hung before the fix passes after it on the CI runner, and 20 out of 20 consecutive `ubuntu-latest` runs finish green, each under 5 minutes. Every run must end with a step `! pgrep -a chrome` that passes, so no Chrome process outlives the tests. Report the cause with the stack dump that shows it, and the 20 run IDs with their durations.
Done when:
