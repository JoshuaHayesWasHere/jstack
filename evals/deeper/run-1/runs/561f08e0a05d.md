# review-concurrency-3: find what forces reviews to run one at a time and let exactly three run at once

Task: "Something is blocking our process and making a run in a one at a time basis or something."

Done when:
- The report names the exact blocking line or lock (file:line, or lock path and holder). It is identified by observing a waiting review with `py-spy dump` (or the runtime's equivalent) and `strace -f -e trace=flock,fcntl,futex,wait4`, not by inference.
- Raw evidence is captured while several reviews are queued:
  - `ps -eo pid,ppid,lstart,etime,stat,wchan:32,cmd --forest`
  - `lslocks`
  - the contents of any lock or pid files
  - per-review start and end timestamps from the run logs
  - grep hits for `max_workers`, `concurrency`, `Semaphore`, `Lock`, `flock` and `queue` settings in the launch code and config
- If reviews once ran in parallel, the introducing commit is found with `git log -S` and confirmed with `git bisect run` using the test below.
- A test launches 6 reviews on a sleeping stub and records each start and end time.
  - Before the fix it fails with a peak in flight of 1.
  - After the fix it passes with a peak of exactly 3, never 4.
- `hyperfine --runs 5` puts 6 reviews at ≤ 2.2× the wall time of one review, measured before and after.
- A `ps --forest` snapshot from a real run shows three reviews in flight at once.
- The report gives the blocking line or lock, the fix, and the before and after numbers: peak in flight, hyperfine times, and the ps snapshot.

Where: the review launch path (the Python commands and skills that start reviewers), its concurrency and queue config, lock and pid files, and the run logs.

Do not touch: anything beyond the one serialising cause and the concurrency limit. That excludes unrelated refactors, other locks, and scout, crewmate or home-thread scheduling.

Decisions: "Reviews should run three at a time: never one at a time, never more than three." "Fix that cause and nothing else, and set the limit to 3."

Design: none, because this is a single observed cause plus a fixed limit of 3 that the user already chose, so there is no design call to make.
