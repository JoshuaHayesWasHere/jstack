# make-check-slowness: find what makes `make check` slow, and why, with measured proof
Task: "figure out what is slowing down make check and why"
Done when:
- A baseline from `hyperfine --warmup 1 --runs 5 'make check'` at -j1 and at -j$(nproc) is reported, with the mean and the spread for each.
- A table ranks recipes by share of wall time and covers at least 90% of the hyperfine mean.
- Each "why" for a top culprit cites its profile (py-spy or perf record), its CPU, I/O or waiting split (pidstat or perf stat), and its syscalls and sleeps (strace -c).
- Each "why" states a predicted saving. Removing or stubbing that cause then cuts the hyperfine mean by that amount, within its spread, and the measured figure is shown next to the prediction.
- If check was faster before, `git bisect run` with a hyperfine threshold pins the regression to one commit. The commit hash and the script are included.
- Every command is included, so the user can rerun them and get the same ranking.
Where: the Makefile and every file it includes; `make -n check`; per-recipe timings from `make check SHELL='/usr/bin/time -f "%e s %U u %S s %C" /bin/sh'` and `make --trace check | ts -s`; the test runner's per-test timings (`pytest --durations=0` or the runner's equivalent); the step timestamps in the CI log, if CI runs check.
Do not touch: the Makefile, tests, source and CI config on any branch that is kept. Stubs used to test a prediction go only in a scratch worktree and are thrown away afterwards. After bisecting, run `git bisect reset` so the repo is back on its original branch.
Decisions: "Start from the raw run, not from the test names"; "Diagnose only; don't fix."
Design: none, this is a diagnosis with no code to design
