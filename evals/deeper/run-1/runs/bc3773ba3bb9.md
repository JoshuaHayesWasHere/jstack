# review-concurrency: let reviews run three at a time instead of one at a time

Task: "Something is blocking our process and making a run in a one at a time basis or something" and, asked how many reviews may run at once: "three at a time".

Done when:
- The cause that forces reviews to run one at a time is found and named in the PR description, with file and line.
- With four or more reviews queued, exactly three run at once and the rest wait, then start as slots free.
- The limit of three is set in one place (a constant or config value), not scattered across call sites.
- A test covers it: queue more than three reviews, then assert that no more than three are active and that all of them finish.
- Existing tests pass.

Where: the Python commands and home-skill code that launch and track reviewers, including any lock, queue, semaphore or "one active reviewer" check in that path.

Do not touch: concurrency for scouts, crewmates or the home thread. Playbooks unrelated to review. Any other limits that are already in place.

Decisions: reviews may run "three at a time".

Design: none, it is a fix to one concurrency limit with the number already decided, and no new structure is needed.

Pull request: ask first

Review: review

Playbook: none
