# review-concurrency-three: Find what serializes reviews and let exactly three run at once

Task: "Something is blocking our process and making a run in a one at a time basis or something". Reviews should run "three at a time".

Done when:
- The serialization is proven from the run logs' start and end timestamps (`logs/*.log` or `journalctl`), with the peak overlap counted and reported (expected: 1)
- A waiting review was caught while reviews were queued, using `ps -eo pid,lstart,stat,wchan:32,cmd --forest`, `py-spy dump --pid` or `strace -f -tt -p`, plus `lsof` on any lock or `.db` files, and the captured output is included
- The exact lock, semaphore, worker count, queue or rate limit that holds the review is named with `file:line` (found via `rg -n 'Semaphore|Lock|flock|max_workers|concurrency|queue'`) and tied to the captured evidence
- Only that cause is changed, so at most three reviews run at once, set in one named setting
- A test starts four stub reviews of N seconds and asserts peak overlap == 3 and wall time ≈ 2N. It fails on the code before the fix and passes after, and both runs are shown
- A real run's timeline shows three overlapping reviews
- `hyperfine --runs 5` wall time for three reviews is within 1.2× of one review, and the output is included

Where: the review runner and whatever starts, queues or limits reviews (locks, semaphores, worker pools, queues, rate limits, `.db` access); `logs/*.log`; the setting that holds the concurrency cap; the test suite

Do not touch: any lock, limit or code path other than the one proven to serialize reviews; scouts, crewmates and the home thread beyond what that one fix needs

Decisions: "three at a time"; "Do not guess the cause"; "Fix only that, so that at most three reviews run at once, set in one named setting"

Design: none, the cause has to be found from evidence first, and the fix is limited to that one cause behind one setting
