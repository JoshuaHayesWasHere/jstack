# raise-thread-cap: Replace the fixed thread cap with a limit sized from this machine and past runs

Task: "I was just warned that I hit an arbitrary thread limit despite being at 3.5 of 12 cores used address this, I want to push my machine as hard as I can without going over the edge" and "is the cap relevant? Can we go higher based off the past runs we've done?"
Done when:
- The thread cap and the warning that fires on it are traced to where they are set, and the brief's answer says whether the cap guards any real limit (CPU, memory, API rate, disk) or is arbitrary.
- Past runs' records are read, and peak CPU, memory and concurrent-thread counts are reported, with the run each figure came from.
- The new limit comes from those peaks and the machine's capacity (12 cores, total RAM), keeps stated headroom below the edge, and the reasoning is written next to it.
- With the new limit, the warning no longer fires when well under capacity (e.g. 3.5 of 12 cores), and it still fires before CPU or memory would go over the edge.
- Existing tests pass, and a test covers the new limit and the point where the warning fires.
Where: the code that sets and enforces the thread/crewmate concurrency cap and emits the limit warning, the home skill and playbooks that read that cap, and the logs or records of past runs
Do not touch: past run records (read only); unrelated scheduling, review or scout logic; machine or OS settings outside the repo
Decisions: "I want to push my machine as hard as I can without going over the edge"
Design: none, it retunes an existing limit from measured data and leaves the structure of threads, scouts and crewmates as it is
Pull request: open one when done
Review: review
Playbook: none
