# raise-thread-cap: find what saturates first, then raise the thread cap or replace it with a pressure-based admission guard

Task: "I was just warned that I hit an arbitrary thread limit despite being at 3.5 of 12 cores used address this, I want to push my machine as hard as I can without going over the edge" and "is the cap relevant? Can we go higher based off the past runs we've done?"

Done when:
- The code that defines and emits the limit is named by path and line, with its comment and `git blame`, and the brief's report says what the cap protects.
- The resource that saturates first is named, with evidence from the raw record. CPU at 3.5/12 does not count as proof of headroom. The evidence covers:
  - `sar -u -r -q -B -W -d -f /var/log/sa/saDD` for each run day
  - the warning's own log line and timestamp
  - `/proc/pressure/{cpu,memory,io}`
  - OOM lines from `journalctl -k`
  - 429/rate-limit counts in the run logs
  - per-task peak RSS and duration
- A step test has run on one representative batch, starting at the current cap and adding 2 at each step:
  - PSI is logged every 10 s.
  - Each step records tasks/hour, p95 task duration, swap-in rate and 429s.
- The new cap sits just below the knee. If a PSI/MemAvailable admission guard fits better, it replaces the fixed cap instead.
- A full real run at the new setting meets all of these:
  - about 2× the tasks/hour of the current cap
  - p95 duration within 1.25× baseline
  - zero OOM kills
  - memory PSI `full avg60` = 0 and `some avg60` < 5%
  - no rise in the 429 rate
- The user has checked that the desktop stayed responsive during that run, and says so.
- The report includes the step-test table as the proof.

Where: the code that defines and emits the thread limit (find it with `rg`), its git history, the run logs, `/var/log/sa/`, `/proc/pressure/`, `journalctl -k`

Do not touch: system-wide settings outside jstack (sysctl, swap, cgroup/systemd config), the files in `/var/log/sa/` and the run logs (read them, never edit or delete), API rate-limit settings, and any other limit in jstack that is not this thread cap

Decisions: "push my machine as hard as I can without going over the edge"; "read the raw record of past runs, not recollection"; "CPU at 3.5/12 is not proof of headroom"; "run a step test on one representative batch: current cap, then +2 each step"; "Pick the cap just below the knee, or replace the fixed cap with a PSI/MemAvailable admission guard if that fits better"; "the desktop staying responsive by my own check"; "Report the step-test table as the proof"

Design: none, the user already named both options, and the step-test data chooses between them
