# check-runner-flip: measure what slows `make check` and what changes on GitHub's runners

Task: "Figure out what is slowing down make check and why", the part that asks what changes at the flip to GitHub's runners. Start from the raw material: the `Makefile` and `.github/workflows/*.yml`, the current CI's job logs (`gh run view <id> --log`), GitHub's per-step timings from `gh api repos/{owner}/{repo}/actions/runs/<id>/jobs`, `nproc; free -m; lscpu; df -h` printed inside a job on each runner, and the test runner's own per-test durations (`pytest --durations=0` or the equivalent). Don't start from dashboard totals or remembered numbers. Time `make check` per target with `make check --trace | ts '%.s'`, and use `hyperfine --runs 10 --prepare 'make clean'` for every number. Emulate the GitHub runner locally with `taskset` set to its core count, `systemd-run -p MemoryMax=`, and empty caches. Use `pidstat -u -d -r 1` to say whether each slow target is waiting on CPU, I/O, memory, the network, or a cache miss. Write down, per target, the GitHub time this predicts. Then check it on real GitHub runners with at least 5 runs from a branch, using `gh workflow run` (ask me before pushing). Done when a table of per-target times on both runners, with spreads, attributes ≥90% of the difference to named causes, and the local prediction lands within 15% of the measured GitHub times.
Done when:
- `nproc; free -m; lscpu; df -h` output is recorded from inside a job on each runner (current CI and GitHub-hosted).
- Every local number comes from `hyperfine --runs 10 --prepare 'make clean'`, with per-target splits from `make check --trace | ts '%.s'`.
- Each slow target has a `pidstat -u -d -r 1` trace and a stated bottleneck: CPU, I/O, memory, network, or cache miss.
- A written per-target GitHub time prediction exists from the local emulation (`taskset` to the runner's core count, `systemd-run -p MemoryMax=`, empty caches), recorded before any GitHub run.
- At least 5 `gh workflow run` runs from a branch have been made on GitHub's runners, with per-step timings from `gh api repos/{owner}/{repo}/actions/runs/<id>/jobs`.
- A table gives per-target times on both runners with spreads, and attributes ≥90% of the difference to named causes.
- For each target, the local prediction is within 15% of the measured GitHub time.
Where: `Makefile`, `.github/workflows/*.yml`, current CI job logs and run timings, the test runner's per-test durations, and a throwaway branch for the GitHub timing runs.
Do not touch: the default branch, and any change to `make check`, the `Makefile` or the existing workflows beyond what the timing branch needs. Do not push anything until the user has said yes.
Decisions: "Don't start from dashboard totals or remembered numbers." "use `hyperfine --runs 10 --prepare 'make clean'` for every number." "at least 5 runs from a branch, using `gh workflow run` (ask me before pushing)."
