### Intent
> Replace the two pr-review reviewer subagents (A/B) per pull request with one scoped review thread. That thread reads the diff itself with the same intent, `SCOPE` text and seven questions, keeps the blast-radius proof, and writes one `## Review` section with `Reviewers: 1`. The section must still satisfy jmerge's review-at-head rule without changing `ready.py`. jbus archives (not only settles) a pull request's `review:` thread once the PR merges or closes, and never archives one for an open PR. Every skill or doc that says "two reviewers" now says one. The change is tested: the skill names no A/B call, jbus archives on merge and leaves open PRs alone, and jmerge reads the new section as ready. `make check` exits 0.

### Reviewers
- Reviewer A: 8 findings
- Reviewer B: 4 findings
- The two independently agreed on three things: the archive rule's definition of "closed", the stale step 4 sentence, and the out-of-`Where` files. The seven questions were asked by both.

### Act On

**1. "Closed" is inferred from absence, and the result is a destructive archive** (A2, B1)
`shut()` (`src/jbus/threads.py:164`) treats a slug as closed when its Result's `Branch:` URL is missing from `world.open`.
- That list is capped at 100 open PRs and matched by raw URL string.
- Any open PR outside the list, or whose URL differs in form, gets its review thread archived.
- That breaks a Done when line outright: "a review thread of an open pull request is never archived".
- jbus never undoes an archive.

B adds the structural point: `watch.pull()` already decides MERGED/CLOSED, and `shut()` is a second rule that disagrees with it. The new test's `eta`/`pull/8` case shows the disagreement.

This came from both reviewers independently, on a concrete path, and it hits a correctness requirement. The fix is one remedy: drop `shut()`, derive "ended" from `pull(...) in (MERGED, CLOSED)`, and make sure CLOSED rests on GitHub's real state, not on absence from the open list. If `watch.pull`'s CLOSED is itself inferred from absence, confirm it with `gh pr view --json state`, cached like `merged.json`, before it drives an archive.

**2. The jmerge "new shape" test never lists a finding** (A1)
- The template's `Findings:` line has no `": "`, so the filler skips it.
- The `- ` item is filtered out, and the `.replace` is a no-op.
- jmerge therefore sees `found == 0`, and the "every finding answered" half of the ready rule is never exercised.

The Done when line asks for exactly that check. The evidence is specific (`cat -A`, `ready.py:298-303`).
- Write the `Findings:` list explicitly into the section.
- Add the negative case: the same section with the `Finding:` line removed must not be ready.

**3. `docs/flow.html:214` still says "Two reviewers … settles itself"** (A3)
This is a direct miss of "any other skill or doc that tells pr-review to start two reviewers says one". It is hand-written, not generated, so the docs sweep won't fix it. It is a one-line edit. It is outside `Where`, but the Done when line covers it, just as it covered `README.md` and `docs/flow.md`.

**4. Step 4 claims the lead judges against context "the reading was not given"** (A6, B2)
That was true when two subagents saw only the intent. Now the same thread read the whole brief, so the sentence promises an independent cross-check that no longer exists. The skill text is the product here, and a reviewer told it has an outside check will lean on one it doesn't have. Both reviewers raised it, and the fix is cheap: say the reading and the judgment are one thread, and point the judgment at re-checking each claim against the repo and the brief.

### Consider

**5. The `"archive"` flag sits inside a prefix-keyed map** (A4)
The `"archive"` key in `finished()` forces a special case in `settle`, a copied `shelve` set and a nested loop with `break`. Computing `ended` once and deciding settle vs settle+archive at the call site would delete that machinery. This is a real simplification, and fixing item 1 rewrites this code anyway, so do both together. On its own it is not blocking.

**6. A merged PR's review thread stays unarchived when the last verdict is `not run`** (A5)
After a merge the thread waits on nothing, and the Done when line says the thread is archived on the next pass. The case is narrow: a later scoped pass that stopped early. The tradeoff is archiving regardless of verdict for ended slugs (simpler, matches intent) versus documenting the exception. I lean toward archiving, since that is the user's literal ask.

They also agreed on the stale step 4 sentence. That one is easy to miss, because the old design's language survives a change that removed its premise.

Pattern: the skill-text rewrite and the docs are nearly right. The risk is concentrated in `threads.py`'s new archive logic and in one test that proves less than it claims. Fixing items 1 and 2, along with 5, is the substance of the rework.
