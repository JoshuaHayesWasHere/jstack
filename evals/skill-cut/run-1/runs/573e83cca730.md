### Intent
> Every home ends up on jbus. A home's start ("When a home starts") registers its repo through `jbus project add` when the config has no table for it, using the same block or helper as `/new-home` step 3. A home that merges its own pull requests writes its id to `home-thread` before the add, so `jmerge` does not race it. jbus lists every `home-id` folder that has no project in one quiet line, in `jbus status` and as a count in the view's machine row. Parties and experts are left out. Nothing touches the config except `jbus project add`, and firstmate and LittleRamPantries are named but not added.

### Act On

**1. Step 3 of every later start calls a deliberate `home-thread` a legacy leftover** (A1, B1)
- This change makes "On the bus" write the home's id to `home-thread`.
- The unchanged step 3 (skills/home/SKILL.md:171-178) and the state row at :74 ("not this home's id") still tell the user that an old home left a stray id there.
- B gives the concrete harm: a user who believes that empties the file, and then jbus and the home both merge. That is the exact race the task exists to prevent.
- Both reviewers found it independently. The changed line causes the break, so it is in scope.
- Fix: reword step 3's "jbus does not merge here" explanation and the row's clause so they recognise a switch set at registration.

**2. new-home now contradicts itself about who writes `home-thread`** (B2)
- Step 3's shared block now writes the switch.
- Step 4 of the same file (skills/new-home/SKILL.md:171, :175) still says the skill "writes none of" the user's four switches and that `home-thread` is "written by hand".
- Fix those two lines in this PR; they are inside "Where".
- The same claim in skills/handoff/SKILL.md:199, docs/state.md:18 and docs/configuration.md:151 sits outside "Where". It is noted for a follow-up, not asked for here.

**3. `ME='… or nothing'` invites a literal word that silently turns jbus merging off** (B3)
- The block only checks that the placeholder's brackets are gone. `ME='nothing'` or `ME='none'` therefore gets written to `home-thread`.
- `merge.home_thread` only checks that the file is non-empty, so jmerge stops for the repo.
- This is the "rule in prose" case, and the runtime check is cheap. Accept only an id shaped like a thread id (or empty), and otherwise print `not filled in`.
- The same guard can absorb A4 (see Noted).

### Consider

**Drop the "On the bus" block's unreachable branches** (A2, B4)
- Step 5 only enters the block after step 4 printed `no project:`, so the `on the bus` and `jbus is not installed` branches can't run. The new test reaches them only by calling `machine.start()` outside the real trigger.
- A's simplification removes a guarded block and a branch table: derive `C` from `git rev-parse --git-common-dir`, or have step 4's line carry the checkout. B's alternative is to run the block on every start so it is the check itself.
- Both are better than the current shape. The tradeoff is only that it reworks a block that already works for the path that matters, and the test's count goes back to 7.

**`already` after a racing add keeps a switch that turns off merging for a project someone else just added** (A3)
- The path is concrete: another thread adds the repo with jbus merging between step 4 and this block.
- The window is narrow. A second home of a repo already on the bus never reaches the block, because step 4 would not print `no project:`.
- The fix is small: on `already`, empty the switch if this block wrote it, or print a line saying so. Worth doing if you're already editing the block for item 3.

**`status()` docstring says the opposite of the code** (A5)
- It says "no pass leaves" the list, but `poll` writes the list to `status.json` and the view reads it from there.
- It is a one-line fix to a line this PR wrote.

**docs/jbus.md:190-192 splits the command from its argument bullets** (A6)
- The new paragraphs make the `<name>`/`--checkout`/`--project-id` bullets read as part of the wrong paragraph.
- Moving the paragraphs below the list is trivial.

### Noted
- **A4**: a trailing slash on a hand-filled `C` writes `home-thread` at the state root. The input is unlikely, and the item 3 guard (refuse an empty `${C##*/}`) covers it for free.
- **B5**: the `project` to `one` renames in `poll`/`alarm` aren't needed, and `first()` still shadows the module. This is real but minor churn. Leave the renames or finish the job; either way it doesn't block.

### Dismissed

- **Where they agreed:** both reviewers converged on the skill prose. The new deliberate `home-thread` write collides with older text that treats the file as user-only or legacy, and the new start block carries branches its trigger can never reach. That consensus is the strongest signal in the review.
- **Where they diverged:**
  - A looked at execution edges: the `already` race, the empty folder name, and docstring and doc ordering.
  - B looked at consistency and enforcement: self-contradicting rules across files, and a placeholder guarded only by prose.
- **What the pattern says:** neither reviewer found a problem in the Python side beyond a docstring and rename churn. The merge switch changed meaning from "only the user writes it" to "a self-merging home writes it at registration", and the surrounding text and guards haven't caught up. Items 1–3 close that gap.
