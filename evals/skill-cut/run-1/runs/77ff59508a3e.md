### Act On

1. **The effort shape is asserted, not read from T3's schema (A1, B4).** The repo's T3 fixture types `options` as `anyOf [{}, null]`. That is the schema "Proves it" asks to be quoted, and it says nothing about `{"id": "effort", "value": …}`.
   - The schema test therefore passes for any shape.
   - If the shape is wrong, every Claude role silently launches at T3's default, which the PR itself says is `high`. That breaks the one rule this half of the task exists to keep.
   - Both reviewers found this independently, and it fails a "Done when" line.
   - The fix: cite the real source of the shape (T3's provider or contract code, or a captured accepted launch), pin it in a fixture or test that rejects other shapes, and quote it in the Result. If no source can be found, record it as a `jbus gate`.

2. **The rename case is not covered (B1).** `related` builds `ours` from `one.files`, and GitHub lists only the new path of a rename. So if the PR runs `git mv core.py engine.py` and main adds `from pkg import core`, the check stays green on a broken merge.
   - This is the central case of #613, it has a concrete execution path, and the new test does not exercise it.
   - The fix is small: feed `left` into `ours` with empty text, and add a `git mv` Kitchen test.

3. **Bare-name sibling imports in `tests/` are missed (A4, B2).** `modules()` only knows dotted paths and `src/`-stripped paths.
   - This repo's tests import each other by bare name, the new `test_jmerge_callers.py` included.
   - So main changing `Kitchen` in `test_jmerge_fresh.py` never makes a dependent PR stale.
   - Both reviewers found this independently, with the same concrete repo example.
   - The fix: name files under the pytest import root (`tests/`) by their bare module name, and add a sibling-import test.

4. **An unreadable head fails open (A3).** When `git show <head>:<path>` fails in the main checkout, the file reads as empty, so the "main changed a dependency" direction can never match.
   - `moved` fetches branches only, and other code in `cli.py` already fetches `refs/pull/<n>/head` when the head is missing. That suggests the gap is real, not hypothetical.
   - Every other git failure in jmerge blocks the merge, and this one lets it through.
   - The fix: check `cat-file -e` and fetch the PR ref. If the head is still missing, treat the check as stale. Add a test.

5. **The rule is overclaimed for Codex and Grok (A2).** THIRD_PARTY.md and the docstring say "never above medium" holds for every role the map names, but Codex and Grok lines send no effort and nobody checked their defaults.
   - The PR's own reasoning, that T3's default is above medium, suggests the claim may be false.
   - The cheap fix is in scope: narrow the wording to Claude lines and gate the Codex/Grok question. Capping those providers instead would need the same schema evidence as item 1.

### Consider

- **Prose path mentions make doc-only PRs stale (B3, with A5 merged in).**
  - A substring match on any file's text means edits to THIRD_PARTY.md or `docs/*.md` go stale whenever main touches a path they mention, and this PR is one such case.
  - The same match has no boundary, and `endswith("conftest.py")` matches `myconftest.py`.
  - Both fail closed, so the cost is extra re-checks or rebase demands, not wrong merges.
  - Limiting path matching to files the check executes (code, Makefile, CI config) and adding a basename/boundary check is cheap while this code is already open. It is a judgment call for this PR.
- **Doc files outside "Where" (A7).** The changes to `docs/configuration.md`, `docs/jmerge.md` and `docs/jroles.md` describe the new behaviour, so keeping them is likely right. They are outside the brief, though, so the Result should name them for the home to accept or revert.
