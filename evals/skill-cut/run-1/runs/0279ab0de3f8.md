### Intent
> Task: the audit's P6. Once a crewmate has written `fixed and green`, a third rebase forced by main is not made. The crewmate writes one stop line in its Result and pipes a gate, and jbus surfaces the pull request as waiting. The count is kept where jbus or jmerge can read it, and a test drives three rebases and finds the stop on the third. `make check` and `jgauge test-slot -- make check` pass. How a rebase is pushed (`--force-with-lease`) is untouched.

### Reviewers
- Reviewer A: 6 findings
- Reviewer B: 5 findings
- They agree on two issues (the jbus step mapping and the `Fixed:` proxy) and partly overlap on test coverage. Both answered the review skill's questions.

### Act On

**1. jbus shows a held pull request as waiting on its crewmate, not on the user** (A1, B1)
- `REBASE_HELD` maps to the `rebase` step (src/jbus/merge.py:97), which src/jbus/work.py:287 draws as "Rebase, its crewmate".
- The crewmate has nothing it may do until `Rebase hold lifted:` is written. The PR's own skill text says jbus lists it as waiting on the user.
- Once the gate is answered, or never parked, nothing outranks the step, so the row reads wrong permanently.
- This is the "jbus surfaces it as waiting" line of Done when, pointed at the wrong party. Both reviewers found it independently.
- The test table at tests/test_jbus_merge.py:288 locks it in.
- Fix: map it to `hold`, as `NOT_UPHELD` and `UNRULED_DROPS` already are. This is inside **Where**.

**2. The count reads the whole brief, not the last Result** (B2)
- SKILL.md:396-399 counts `Fixed:` and `Rebased after fixed:` lines anywhere in the file.
- SKILL.md:159 makes it a rule that every block reads the last result.
- Concrete path: two rebases in round one, then a follow-up round from a user steer. The first conflict of the new round is held at once.
- That breaks a stated convention and produces a wrong stop. The fix is cheap: reset the counters on `/^## Result/`.

**3. Re-running the block on a held head tells the crew to park another gate** (A3)
- The block prints `hold:` on every run, and the prose says to park a gate on `hold`.
- mainmoved wakes red pull requests once per main commit, and a held pull request is often red. So the user gets a duplicate gate per main commit.
- This is a real idempotency gap on a real wake path.
- Fix: print a distinct word when the line already exists, and park only on the first `hold:`.
- Dedup against the last hold-or-lift line (as `rebase_held` does) so that B5 is closed in the same edit.

### Consider

**4. `Fixed:` stands in for "fixed and green"** (A2, B3)
- Both reviewers flag it. Rebases forced while the fix is still red use up the cap.
- Tradeoff: the PR explains that `fixed and green` is only sent to a home and never written. A real green marker means a new Result line and a crewmate step to write it, which is more surface than an S task.
- At minimum, state the deviation from the Done-when line plainly in the PR body.
- Add the marker only if early holds turn out to matter in practice. The audit's goal of stopping rebase churn is served either way.

**5. Test coverage of the conflict path and of jmerge's `waits()`** (B4, A5)
- The Done-when test (three rebases, stop on the third) exists and runs the shell for real, so the line is met.
- Two things go unexecuted:
  - The `counted` call on a rebase that stops on a conflict. In practice this is probably the most common way main forces a rebase.
  - The placement of `rebase_held` in `waits()` at cli.py:703.
- Deleting either would not fail a test. One more main move that touches the branch's file, plus one `waits()` assertion, is cheap. It is worth doing but doesn't block.

**6. Hold recorded at the local HEAD, compared with GitHub's head** (A4)
- This bites only when the second rebase's push is refused and main then moves again, which is narrow.
- The suggested `pushed` head is a one-line change. Check that it is actually the head the hold should name (the unpushed head is the one being held) before switching.

### Noted
- **A6**: the `home` argument to `run()` also switches the slug. This is test-helper coupling with no current wrong caller. Tidy it if the helper is touched again.
- **B5**: the dedup and `rebase_held` disagree on what the current hold is. It needs the branch to land back on a previously held head after a lift, which is contrived. The fix for item 3 covers it anyway.

### Dismissed
- None. Every finding was about a changed line and grounded in a concrete path. The nits are real, just low-impact.

- **Overlapped:** on tests, A saw only the missing `waits()` path. B also saw the untested conflict branch, which is the stronger half.
- **Diverged:** each reviewer found one state bug the other missed. A found the duplicate gate on re-run, B found the whole-brief count across rounds. Both bugs come from the same blind spot: the block reads brief state without scoping it to "this round" and "first time".
