### Intent
> The user, 2026-10-15: "We need to add this project to jbus and ensure any new home we create is added to the bus." A home's start registers its repo through the same `jbus project add` block that new-home's step 3 uses. A home that merges by itself writes `home-thread` before the add, so `jmerge` does not race it. jbus lists homes with a `home-id` and no project, as a quiet line, in `jbus status` and as a count in the view's machine row. Parties and experts are excluded. The tests and docs cover all of this, and `make check` is green.

### Act On

**1. Step 3's "stale id" prose now contradicts the new deliberate write** (A1, B1)
- Every later start of a self-merging home will report its own switch as a legacy leftover.
- It will also say that "Nothing empties it but the user, by hand". That invites the user to empty it, and then jbus and the home would both merge. That is the race this task exists to prevent.
- The damage is at `skills/home/SKILL.md:171-178` and in the row's "not this home's id" clause. Both are in Where, so fix them here.
- Reword step 3 so that an id written by "On the bus" reads as the switch being on by choice.

**2. new-home step 4 still says the skill writes none of the four switches** (B2)
- The same file now holds two opposite rules about `home-thread`: step 3 writes it, and step 4 (`skills/new-home/SKILL.md:171,175`) says nothing writes it.
- An agent reading step 4 gets the wrong rule. Fix those lines in this PR.
- The matching lines in `skills/handoff/SKILL.md:199`, `docs/state.md:18` and `docs/configuration.md:151` are outside Where. Note them for a follow-up.

**3. The placeholder `<the id of a home that merges by itself, or nothing>` invites a literal `nothing`** (B3)
- The only check is that `<` and `>` are gone, and `merge.home_thread` only tests that the file is non-empty.
- So `ME='nothing'` (or `none`) silently turns jbus merging off for the repo. It also prints a "done" line that looks correct.
- This is a rule in prose where a one-line runtime check would do. Reject a value that is not shaped like a thread id and print `not filled in`, or make the default placeholder the empty string.

### Consider

**Unreachable branches in the "On the bus" block** (A2, B4)
- Step 5 only runs the block after step 4 printed `no project:`. So the `on the bus` and `jbus is not installed` branches, and the prose that handles them, are dead.
- The test that checks the "present project left alone" case reaches it by calling `machine.start()` directly. A real start never takes that route.
- Dropping the block, and deriving `C` from `git rev-parse --git-common-dir` or printing it in step 4's line, removes a guarded block and a branch table.
- Tradeoff: it is cheap, and it makes the test reflect a real path. "Leave a present one alone" would then be proven by `jbus project add` answering `already`. It does not block anything, because nothing is wrong at runtime.

**`status()` docstring says the opposite of what the code does** (A5)
- The docstring says "which no pass leaves", but `poll` writes the list to `status.json`, and both the view and the change check read it from there.
- This is a one-line fix in a changed line. Do it if you touch the file again.

**New docs paragraphs split `jbus project add` from its argument bullets** (A6)
- This is a real readability regression in the doc that a "Done when" line requires.
- Moving two paragraphs below the bullet list fixes it.

### Noted
- **A3, the switch is kept on `already` when another thread just added the project with jbus merging.** The window is narrow. More to the point, a home whose rules say it merges by itself *should* hold the switch no matter who added the project; otherwise both merge. Two homes of one repo disagreeing on merge policy is a question for the user, not a reconciliation step in this block. A one-line notice on `already` with `ME` set would be harmless if it is wanted later.
- **A4, a trailing slash on a hand-filled `C` writes `home-thread` at the state root.** This is hypothetical: the home's own block derives `C` with `dirname`. If the block is touched for B3 anyway, `C=${C%/}` costs nothing.

### Dismissed
- **B5, renaming `project` to `one` in `poll`/`alarm`.**
  - The rename in `status()` is required, and making the other loops match keeps the module name unshadowed inside the file it now imports into. That is a reasonable consistency choice, not churn that changes behavior.
  - The remaining `first(project: ...)` parameter is a style nit, not a defect.
