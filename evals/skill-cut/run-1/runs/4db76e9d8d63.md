### Intent
> Add a `Proves it:` line to `templates/brief.md`, right after `Done when:`. The brief parser, and the launch check jbus runs beside `dispatch.designed`, accepts the line only when it names something outside the agent: a test, metric, dataset, external judge or the user. It refuses empty lines, the template's own text, and proofs by the crew, crewmate, reviewer, agent, "self", "the model" or a review alone, with a one-line reason. Briefs already queued without the line are grandfathered or refused, whichever does not strand an approved row. The change also adds tests for every kind, documents the line, and must pass `make check` and `jgauge test-slot`.

### Reviewers
- Reviewer A: 7 findings
- Reviewer B: 6 findings
- The two reviewers found the same core problems independently: loose `_OUTSIDE` patterns, tests that skip near-misses, a duplicated head-line loop, an unused `Brief.proof`, fragile template detection, and two Done-when items the diff can't show. A alone raised the forever-grandfathering and the double gate.

### Act On

**1. Self-referential proofs pass because `_OUTSIDE` is checked first and its patterns match ordinary words.** (A1, B1, with B2 as the test side)
`proof()` returns success on the first `_OUTSIDE` match and never consults `_SELF`. Each of these lines names only the agent and gets through:
- "make sure the reviewer is happy" passes as a test (`make \w`)
- "self-test" passes as a test (`\btests?\b`)
- "`the crewmate` checks it" passes as a test (any backticked text)
- "the reviewer is 100% sure" passes as a metric (`\d\s*%`)
- "the model is the judge" passes as an external judge (`\bjudge\b`)
- "the reviewer gives his word" passes as the user

Those are exactly the cases the task says to refuse. This check is the only gate before launch, since `_ready` launches whenever `proven()` returns `""`. Both reviewers built concrete inputs that pass, so this is not hypothetical.

The fix:
- Make "a test" require a path (`tests?/\S+`, `test_\w+`, `\w+_test\.py`) or a backticked command starting with a known tool (`make <target>` but not "make sure", `uv`, `pytest`, `jbus`).
- Require a metric word near `%`.
- Drop or tighten "judge", "his word/pick/eye" and "eval".

Keep the rule "a test the crewmate runs is still a test", but only when the outside match really is a test.

**2. The tests pin only the happy side of the precedence rule.** (B2, A1)
Every `REFUSED` case is a short phrase with no outside keyword in it. Add a `REFUSED` case that runs `parse.proof` on each example above. Without them, the tightening in item 1 can quietly regress.

**3. Grandfathering is unconditional, so leaving the line out bypasses the gate for every future brief.** (A2)
`proven()` returns `""` whenever `proves_it` is `None`, and nothing ties that exemption to when the row was approved. The Done-when asks for *existing queued* briefs to be grandfathered so that no approved row is stranded. It does not ask for a permanent opt-out. As written, the requirement holds only through prose in `skills/home/SKILL.md`, which is the "rule in prose" pattern.

Fix: exempt a missing line only for rows approved before a cut-off, using the `approved` time or `brief_sha` the queue already records, and gate it on anything approved later. Only one reviewer raised this, but it is a concrete correctness gap in the feature's core promise.

### Consider

**4. A brief failing both checks costs the user two gates and two re-approvals.** (A3)
`proven()` runs only when `designed()` passes, so a brief missing both lines surfaces one problem per round. Collecting both faults into one gate keyed by the brief sha is a small change inside `_ready`, which is in Where, and every round costs the user an approval.
- Tradeoff: it touches the `_ready` flow that the Design check shares. It's cheap, but it isn't strictly required by the task.

**5. Template-text detection by a leading `<` is wrong in both directions.** (A6, B5)
- A legitimate metric like `<= 50 ms p95 from jgauge` is refused.
- The guide text with its brackets removed is accepted as "a test", because the guide itself contains the word "test".

Matching `^<[^>]*>$` and comparing against the template's own line with brackets stripped makes it exact.
- Tradeoff: low likelihood in practice, but the fix is a couple of lines, and the second case lands in the area item 1 is already tightening.

**6. `Brief.proof` (and `Proof.said`) are read only by tests.** (A5, B4)
These are surface area with no consumer and weren't asked for.
- Tradeoff: remove them, or show the field on the jbriefs page if that was the plan. Either is fine. Leaving dead API is the only wrong option.

### Noted

- **Duplicated head-line loop and the `proven` pass-through** (A4, B3). The real fix is a shared `head_line(text, label)` helper in `jbriefs.parse` and a `(kind, check)` tuple in `_ready`. That means moving `designed`, whose rules are "do not touch", so it is noted for later. B3's warning that each further check will need another branch is speculative until a third check exists. If item 4 is taken, the tuple shape falls out of it naturally.
- **Two Done-when items are invisible in the diff** (A7, B6): the grandfather/refuse statement in the Result, and one real queued brief run through the launch check with its line printed. Verify both in the brief's Result before accepting.

### Dismissed

None. Every finding was either correct or a fair note.

### Agreement Map

The reviewers converged hard on the central defect. Both found the precedence rule plus loose patterns independently and produced overlapping inputs that pass ("make sure", backticks, judge, eval), which is the strongest signal in this review. B rated it critical and A a warning. I side with B in substance: this is the feature's whole job, so it goes first in Act on.

They also agreed on all of the secondary items: duplication, the unused property, template detection and the missing Result evidence. On template detection they found opposite failure modes of the same heuristic, which strengthens the case for fixing it.

The only divergence is that A went further on the gate's lifecycle (grandfathering, double gate) while B went further on test coverage. Those are complementary rather than conflicting. The overall pattern is that the plumbing is sound and the judgment logic, the part that decides what counts as "outside", is under-specified and under-tested.
