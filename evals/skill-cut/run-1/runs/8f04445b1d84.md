### Intent
> Every home ends up on jbus. A home's start ("When a home starts") registers its repo when the config has no table for it. It shares one registration block with new-home's step 3, and `jbus project add` stays the only writer. A home that merges its own PRs writes its id to `home-thread` before the add, so `jmerge` does not race it. jbus's pass lists the homes with a `home-id` and no project, in a quiet line, in `jbus status` and as a count in the view's machine row. Parties and experts are excluded. The work comes with tests and with docs in `docs/jbus.md`.

- Both independently found the stale-id contradiction (A1/B1) and the unreachable branches in "On the bus" (A2/B4). Neither named an unmet "Done when" line, and both answered the review's questions.

### Act On

1. **A deliberate `home-thread` write is reported as a legacy leftover at every later start** (A1, B1). Step 3 of "When a home starts" (`skills/home/SKILL.md:171-178`) still prints "Nothing empties it but the user, by hand." It also tells the home to explain the id as left behind by an old home. After this change, that is false for every repo that took the merge-by-itself path.
   - B1 shows the real risk: the user is told to empty a stale switch, does so, and both jbus and the home merge. That is exactly the race the task exists to prevent.
   - The fix is inside the Where line: reword step 3 and the state-table row ("not this home's id").
   - A1's alternative, a fixed marker instead of an id, also works but changes what the switch holds. Rewording is the smaller fix.

2. **Two of the three branches in "On the bus" can never run, and the test covers only the unreachable route** (A2, B4). Step 5 only enters the block after step 4 printed `no project:`, which implies jbus is installed and `$P` is empty.
   - The `on the bus` branch, the `jbus is not installed` branch and the prose for both are dead code.
   - The test reaches `on the bus` only by calling `machine.start()` outside the trigger, so it checks a path a real start never takes.
   - Take A2's remedy: drop the block. Name the checkout via `git rev-parse --git-common-dir`, or have step 4's `no project:` line print it. That deletes a guarded block and a branch table, and the guarded-block count in `test_scoped_home.py` goes back to 7.

3. **new-home now writes `home-thread` while its own step 4 says it writes none of the switches** (B2). `skills/new-home/SKILL.md:171` ("written by hand") and `:175` ("this skill writes none of them") contradict the block this PR added to the same file. Fix both lines here.
   - `skills/handoff/SKILL.md:199`, `docs/state.md:18` and `docs/configuration.md:151` say the same thing but are outside Where. Note them for a follow-up.

4. **The `ME` placeholder invites a literal "nothing", which silently turns off jbus merging** (B3). The placeholder text says "or nothing". The only guard is that `<` and `>` are gone, and `merge.home_thread` treats any non-empty file as "home merges".
   - A model filling in `ME='nothing'` disables `jmerge` for the repo, and the block reports success.
   - This is the "rule in prose" case. Make the mistake impossible: require the thread-id shape, or make merge-by-itself an explicit separate flag so the default path has no third value to fill in.

### Consider

- **A self-merging start can flip an already-added project to "home merges"** (A3). This happens if another thread adds the project between step 4 and the block. The add returns `already`, the switch stays, and nothing says so.
  - The path is real but the window is narrow.
  - The cheap fix: on `already`, when this block wrote the switch, empty it again or print a line. That is worth doing alongside item 4, since both touch the same write.
- **`status()` docstring says the opposite of the code** (A5, `src/jbus/cli.py:192-193`). The list is written to `status.json` and read back by `poll` and the view. This is a one-line fix and misleading as it stands. Just fix it.
- **New docs paragraphs split `jbus project add` from its argument bullets** (A6, `docs/jbus.md:190-192`). This is a real readability regression in a section the task asked to edit. Moving the two paragraphs below the list fixes it.

### Noted
- **Empty `${C##*/}` from a hand-filled checkout with a trailing slash** (A4). It needs a hand-typed trailing slash, and the damage is one stray file under the state root before the add refuses. Stripping the trailing `/` is cheap if item 4's validation is being touched anyway.
- **Loop-variable renames in `poll` and `alarm`** (B5). The rename in `status()` is needed. The others are churn, and `first(project: ...)` still shadows the module. This is low impact. Narrowing it is fine but not required.

### Dismissed
- None. Every finding traced to a changed line and described a real (if sometimes minor) effect.

### Agreement Map
- The reviewers converged on the two things that matter most:
  - The new deliberate `home-thread` write collides with the existing "stale leftover" narrative. B2 extends that collision to new-home's own step 4 and the docs.
  - The "On the bus" block carries dead branches.
- They diverged on how the merge switch can go wrong. A looked at timing (A3, the `already` race) and B looked at input (B3, a literal "nothing").
- Taken together, the pattern points at one weak spot: the merge switch is now written by a skill, but its validation, its reconciliation and the prose around it still assume only the user writes it by hand.
- The jbus side (pass, status, view count) and the tests drew only a docstring nit and a rename nit. That part looks sound.
