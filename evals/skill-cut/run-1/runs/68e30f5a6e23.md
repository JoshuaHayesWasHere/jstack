### Act On

**1. Snapshots now race each other and the timer, and nothing serializes them** (A1, B1)
Before this change, only the timer ran `take`. Now any home or scoped home can run it at any time, on one shared index, with no lock. Both reviewers trace concrete failures:
- **False alarms.** A home's run that overlaps the 08:30 or 17:30 timer run hits `.git/index.lock` and `_must` raises. If the timer loses, `OnFailure` sends `--alarm` to the desk and every project for a failure that isn't real.
- **Lost commits.** A's `git reset -q` (the gitleaks path) can land between B's `git add -A` and B's `diff --cached`. B then prints "nothing changed" and its edit gets no commit.

This defeats the "each edit is a commit of its own" Done-when line, and the change itself created it.

Fix: take an exclusive `fcntl.flock` on a file under the tree's `.git`, held across add, scan, commit and push, so concurrent runs wait instead of failing. This is inside `snapshot.py`, so it is in scope.

**2. The documented undo can wipe the live `standing.md`** (A2, B2)
The shell truncates the target before `git show` runs. If `git show` fails, the rules file is left empty, and the doc's next step tells the user to snapshot it. `git show` fails on:
- a mistyped or ambiguous hash;
- the commit that created the file, so `<commit>^` lacks the path;
- the root commit.

Since this is the recovery procedure, it must not destroy data.

Fix:
- Document `git -C ~/.local/state/home restore --source=<commit>^ -- <repo>/standing.md`. It writes nothing on failure.
- Say what to do when the bad edit created the file (delete it, or restore an empty file deliberately).
- Add a test that undoes the creating commit. The current test only covers a parent that has the file.

**3. Handoff gains a new duty to write standing rules** (A5, B3)
"One it did not write yet goes there now, as one dated line" is new behaviour the task didn't ask for. It also contradicts the sentence before it ("the home wrote it to `standing.md` when it heard it"). The line was invented to give the snapshot step something to hang on.

Fix: cut it and keep only the general instruction, "after any edit to `$H/standing.md`, run `jbus snapshot --why ...`". It is cheap to fix and a clear scope violation, so it belongs here even though B rated it a nit.

### Consider

**4. `--why` labels a whole-tree commit** (A3; B1's "mixed commits" and "two edits in one commit" points)
`git add -A` sweeps in briefs, `merge.log`, other repos' trees and the like, and the message names only the standing.md edit. The undo still works, because `log -p` and `show <commit>^:<path>` are path-limited. But un-pathed history now carries misleading messages. In B's case, two homes' edits to the same `standing.md` land under one `--why`, and undoing "the bad one" reverts both.

Tradeoff: letting `--why` commit only named paths (`git commit -- <path>`) is a small change in `snapshot.py`. It does interact with the gitleaks staging step, so it is more than one line. The lock in Act On #1 removes the races. What remains is message accuracy plus the rarer same-file double edit. It is worth doing if cheap. Otherwise, have the message say it is a whole-tree snapshot.
