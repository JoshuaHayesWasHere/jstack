### Act On
1. **`queue add` lets unedited template text through for Task, Done when, Pull request and Review** (A1, B1). `_filled` (src/jbriefs/parse.py:355) only treats a value as template text when it starts with `<`. The template's own lines for those four fields start with `"`, `-`, or have no `<` at all.
   - This fails a "Done when" line directly ("refuses an incomplete brief").
   - It makes the docs and the home skill wrong, since both say a field must not be "the template's own text".
   - The new test hides the gap: it writes `Task: <the request>` without the template's quotes.
   - Fix: strip quotes and list markers, reuse `_template`, and add a test that runs `queue add` on the unedited `templates/brief.md` and expects a fault for every required field.
2. **Contraction stripping lets a negation keep the go** (A3, B2). Stripping the apostrophe turns `shouldn't` into `shouldnt`, which is two edits from `should`, so a Done-when line can flip its meaning and still keep the user's approval.
   - The two-edit rule is the spec's. Stripping the apostrophe is the PR's own choice, and it is what pulls negations inside the allowance.
   - Fix: turn `n't` into a separate `not` token, and add a test that `should` → `shouldn't` re-asks.
   - The cases that remain inside the spec's rules must go into the stated known limit in `docs/jbus.md` and the PR body: near-opposite words (`include`/`exclude`, `import`/`export`) and direction swaps hidden by dropping fillers and sorting. The task requires that limit to be stated, and right now it names only `must`/`may` and `files`/`fixes`.
3. **The add checks and the launch checks are two hand-kept lists** (A4, B3). `faults` repeats `CHECKS` + `ASKED` from dispatch by hand. The whole point of the task is that `queue add` runs every check a launch runs, so the next check added to dispatch would bring back "queued, approved, then gated" with no test failing.
   - Fix: keep one tuple of checks in `jbriefs.parse`, run by both `faults` and dispatch. Dispatch keeps only the grandfathering for old rows.
   - Fold A7's duplicate `designed()` call and the discarded `_filled` result for Size into this fix.
4. **The home skill throws away "its go does not hold"** (A2). On a successful add, skills/home/SKILL.md:632 prints only `added: the row <slug>`. A change in scope therefore looks like a plain success, and the user is only asked again later, when the launch gate fires.
   - That is the "re-ask" behaviour the user wanted, delayed until after the brief is queued, which is the very ordering this task removes.
   - Fix: print `$said` whenever it carries the void line, and say in the skill that the home then puts the brief to the user again.

### Consider
- **`scope` is stored and printed, but nothing checks it** (A5).
  - The flaw that matters for the "verifiable approvals" goal: after a typo fix, `scope` differs while `holds: true`. A bot that compares `scope`, as the docs suggest, would refuse a brief that jbus launches.
  - Cheapest fix: say in the docs that `holds` is the verdict and `scope` is stricter.
  - The other two points are worth weighing but are not urgent: checking `scope` against `meaning` (that defends against hand edits to `queue.json`), and adding a method/version field so a later change to `FILLER` doesn't silently reshape comparisons.
- **The PR description should say that `playbook` now refuses non-crewmate playbooks at launch** (A8). The change is intended, but the "launch checks unchanged" claim is false, and correcting it costs one sentence.
- **Re-prioritising an old row now forces a full brief, which voids its go** (A9). This runs against "rows approved before this change keep working". It is theoretical today, because all four queued rows are complete. A cheap fix: skip `faults` on a re-add whose body is unchanged.
- **`approve` does not run `faults`** (B4). An incomplete row queued before this change can still be put to the user. The launch backstop catches it, and adding the check is one line.
