### Intent
> Section 3 of the /deeper design: a step in the home skill's brief writing, not a separate file. It runs on its own for research, perf, analysis and outcome briefs and carries its own copy of the four questions (`/deeper` stays manual). Answer 2 goes to the scout's `Read:` or the request's sources, answer 3 to the brief for the crew, and answer 4 to `Proves it:`. A mechanical fix, a docs change and a bug fix with a known cause skip the step. The home skill's text tests cover it, and `make check` and `jgauge test-slot -- make check` pass.

### Reviewers
- Reviewer A: 6 findings
- Reviewer B: 7 findings
- The two agreed on the three core problems (the `Instruments:` field, the `bug-fix` misclassification, the hard-coded playbook list) and on the lost answers for a no-brief request. Each also raised items the other did not. Both asked the review skill's questions.

### Act On

**1. `Instruments:` is an invented brief line, and the step contradicts `templates/brief.md`** (A1, B1)
The step sends answer 3 to an `Instruments:` line. No template, skill or parser defines that line, and the scout skill's five-line shape drops it. So answer 3 survives only if the home remembers to write it into the Deliver line.
- The task said "in the brief for the crew", not "on a new line". Inventing a field under a template the PR may not touch is the wrong remedy.
- Fix within "Where": put answer 3 on a line the template already has. The Done-when list is the natural home, since methods and tools are how "done" gets checked, or it can go in the task body. Say so in the step.
- The `Read:`-on-home-briefs clash is different, because the intent itself asks for it. The step can't settle it, so it stays, but the Result must record a follow-up for `templates/brief.md` line 17 and the scout skill. The words "though the home wrote it" are not a resolution.

**2. The step keys on the playbook name, not on the kind of work, so it misclassifies in three ways** (A2, B2, A3, A4, B3, merged)
These share one root cause: a hand-kept list of ten playbook names decides the step whenever a playbook is picked.
- **`bug-fix` always skips.** That playbook is for bugs whose cause is not yet known, which are the ones that need raw logs and a failing-before test. The boundary exempts only a known cause. The test labels `bug-fix` "known bug" and pins the mistake in place.
- **Outcome work under `feature` or `autonomous-run` always skips.** The intent names outcome briefs, yet they get the step only with no playbook at all.
- **A scout request is judged by the scout's playbook.** Every scout playbook is in the arm, so a request whose Deliver is a docs-change brief still gets the four questions. That breaks the second Done-when line for scout-written briefs.
- **The list drifts silently.** A new research playbook skips, and the test checks only that each listed name is a file.

The fix removes the list rather than patching it. Run the case on the kind of the task being briefed (`research|perf|analysis|outcome|other`), which the home can state for every task, including the task behind a scout request. The test then pins kinds, not playbook names. Marking playbooks with a front-matter tag would touch `playbooks/`, which is outside "Where", so that is noted for later only.

### Consider

**3. A request whose Deliver asks for no brief has nowhere to put answers 3 and 4** (A5, B4)
B's remedy fits the template that exists: write answers 3 and 4 as `Questions:` items. The tradeoff is that for a report-only request there is no crew brief, so dropping them is defensible too. Either way, the step should say which, so the home isn't left guessing.

**4. The tests don't tie the named lines to the templates** (A6)
Once item 1 is fixed, a test that each brief line the step names exists in `templates/brief.md` would have caught the `Instruments:` mismatch. It is cheap and executes something real. The catch is that `Read:` would fail it, for the intent-driven reason above, so the test needs a deliberate exception.

### Noted
- **B5:** "the block under it" at SKILL.md:430 points at a block about 90 lines away, in another section. Naming the section is a one-line clarity fix worth doing if the line is being edited anyway.
- **B6:** the "Done when already names its data, instruments and judge" skip is prose that overrides the block's output. If item 2 moves the step to a kind input, fold this in as an input then. Otherwise it's low-impact.
- **B7:** neither reviewer ran `make check` or `jgauge test-slot -- make check`. That is not a defect in the diff, but the Result must show both passing before the merge. It must also say how the "Proves it" brief will be checked.

### Dismissed
None. Every finding names a concrete path or a real gap. The nits are small but correct.

### Agreement Map
The two reviewers converged independently on the three structural problems: the undefined `Instruments:` line, `bug-fix` skipping, and the hand-kept playbook list. That consensus is the strongest signal in this review. It also shows that items 1 and 2 are really one design slip each, not five separate bugs.

A alone saw that the scout-request path inherits the same misclassification (A3). B alone saw the readability and prose-override issues (B5, B6) and the unverified checks (B7). The divergence is in breadth, not in judgment, and neither reviewer padded with style preferences. The step's shape is right; fixing its two inputs (where answer 3 goes, and what the case keys on) should carry the rest.
