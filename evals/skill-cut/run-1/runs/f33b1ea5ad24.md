### Intent
> Task: the audit's P6. In `skills/crew/SKILL.md` "A conflict", once a crewmate has written `fixed and green`, a third rebase forced by main is not made. Instead the crewmate writes one stop line in its Result and pipes a gate, and jbus surfaces it as waiting. The count is kept where jbus or jmerge can read it, and a test drives three rebases and finds the stop on the third. `make check` and `jgauge test-slot -- make check` pass. How a rebase is pushed (`--force-with-lease`) is not touched.

### Reviewers
- Reviewer A: 6 findings (3 warnings, 3 nits)
- Reviewer B: 5 findings (4 warnings, 1 nit)
- Both reviewers asked the review skill's questions. They agreed on the jbus step mapping, the `Fixed:` proxy and the test gap. Each also found one distinct state-handling bug in the shell block.

### Act On

**1. jbus shows a held PR as waiting on its crewmate, not the user** (A1, B1)
- `src/jbus/merge.py:97` maps `held a third rebase` to the `rebase` step, which `work.py:287` draws as "Rebase, its crewmate".
- Once the gate is answered or never parked, the row reads that way for good, yet the crewmate is forbidden to act.
- This misstates the "jbus surfaces it as waiting" line, and `tests/test_jbus_merge.py:288` locks the wrong mapping in.
- The repo already routes user-only waits (`NOT_UPHELD`, `UNRULED_DROPS`) to `hold`. Move it there and fix the test table.
- Both reviewers raised this independently with the same execution path, so this is the clearest finding of the review.

**2. The count reads the whole brief, not the last Result** (B2)
- `SKILL.md:396-399` counts `Fixed:` and `Rebased after fixed:` lines anywhere in the file.
- `SKILL.md:159` says every block reads the last result.
- A follow-up round inherits the previous round's two rebases, so its first conflict is held at once.
- The path is concrete and the fix is a one-line counter reset on `/^## Result/`.

**3. Re-running the block on a held head parks another gate** (A3)
- The block writes the hold line once per head but prints `hold:` on every run, and the prose says to park a gate on `hold`.
- `mainmoved.py` re-wakes red PRs on every main commit, and a held PR is likely red. So the user gets a duplicate gate per main commit.
- This is the run-twice case question 4 asks about. The fix: print a distinct word (`held:`) when the line already exists, and park only on the first.

**4. The new jmerge path and the conflict-stop count are not executed by any test** (A5, B4)
- The test runs the block for real, which is good, and it meets the "drives three rebases" line.
- But every rebase in it succeeds, so the `counted` call in the stopped-rebase branch (`SKILL.md:443`) never runs.
- jmerge is checked only via `ready.rebase_held` directly, so the `waits()` ordering in `cli.py:703` is unpinned.
- That untested seam is where the "surfaces as waiting" behaviour lives, and where finding 1 hid. Two small additions are enough:
  - one run where main touches the branch's own file, so the rebase stops
  - one assertion through `waits()` / `merge.step` that the held head reports `REBASE_HELD` and lands on `hold`

### Consider

**`Fixed:` stands in for "fixed and green"** (A2, B3)
- This is a real proxy: `Fixed:` is written before CI passes, and `Fixed: none needed` starts the count too.
- The failure mode is mild, though. The hold can come early and produce one unnecessary gate. It never lets a fourth rebase through.
- The PR already explains why: `fixed and green` is sent to the home, not written to the brief.
- Adding a green marker means a new piece of state the crewmate must write. The cheap option is to state the deviation from the "Done when" line plainly in the PR and the skill prose.
- The user may prefer the exact condition, so this is their call.

**The hold de-dup disagrees with `rebase_held` on what the current hold is** (B5)
- The scenario is more plausible than it first looks: hold at X is lifted, the next rebase stops and is aborted back to X, and the count is still ≥2.
- The block then sees the old line and writes nothing, while jmerge sees the lift as last and reports no hold.
- Fold this into the fix for Act On 3: de-dup against the last `Rebase hold`/`Rebase hold lifted` line, the same rule jmerge uses.

**The hold records local `HEAD`, not the pushed head** (A4)
- This only diverges after a refused push, which is a narrow path.
- The block already has `pushed` from `gh pr view`, though, so using it removes the proxy at no cost.
- Worth doing while in that block.

### Noted
- The test's `run(about, home)` also switches the slug to `"alpha"` (A6). This is harmless coupling in a test helper with one caller.

### Dismissed
- None. Every finding traced to a changed line and described a real behaviour, and neither reviewer padded with style preferences.

### Agreement Map
- The reviewers converged on three things: the jbus step mapping, the `Fixed:` proxy, and the test not reaching jmerge's `waits()`. Their consensus on the mapping and the test gap is the strongest signal, and the two are linked: the mapping bug survived because the test pins the table but never drives the board path.
- They diverged in a useful way. Each found a different state-reconciliation flaw in the shell block. A found the repeated gate on re-run, B the whole-brief count and the de-dup rule.
- Together these show the block's main weakness: it reads the brief's history loosely, while jmerge reads "last line wins". Aligning the block on "last Result, last hold line" fixes B2, A3 and B5 together.
- The pushing mechanics stayed untouched, as the "Do not touch" line required. No out-of-scope files were flagged.
