### Intent
> Task: the audit's P7 optional items, under the user's approval of "every other upstream update". Done when: (1) the merge-result question is answered from the code, with a test. Does jmerge's "fails over today's main" check run the checks on the merge result? If not, it is made to when main changed a caller or a dependency of the PR's files (or a lockfile). (2) Whether a T3 launch (`modelSelection`) takes an effort setting is read from T3's own tool schema. The decision goes in THIRD_PARTY.md, and nothing raises effort above medium. (3) `make check` and `jgauge test-slot -- make check` pass. Proves it: the merge-result test, and the T3 schema quoted in the Result.

### Reviewers
- Reviewer A: 7 findings (4 warnings, 3 nits)
- Reviewer B: 5 findings (4 warnings, 1 nit)
- Both reviewers asked the review skill's questions. Neither said Done-when (1) or (3) was unmet, so the main open gaps are the cases the new check misses and the unproven effort shape.

### Act On

1. **The effort shape is not proven by T3's schema, and no test pins it** (A1, B4). Both reviewers found this on their own.
   - The repo's T3 fixture types `options` as `anyOf [{}, null]`, which accepts anything. So the schema test passes whatever jroles prints.
   - "Proves it" asks for the schema to be quoted, and the schema does not contain this answer.
   - If the shape is wrong, every Claude role silently launches at T3's default. The PR itself says that default is `high`, which breaks the one rule this half of the task exists to keep.
   - Fix: cite the real source of the `{"id": "effort", "value": …}` shape (T3's provider code or a captured accepted launch) and validate against it. If no source can be found, record it as a `jbus gate`, as the Decisions line prescribes, and say so in THIRD_PARTY.md rather than asserting the shape.

2. **A PR that renames or moves a module misses callers main added under the old name** (B1).
   - This is a concrete execution path: `left` reaches `stale_paths` but not `related`, and GitHub lists only the new path.
   - It is the central case #613 is about, and the new test covers only an in-file rename.
   - Fix: pass `left` into `related` as empty-text entries, and add a Kitchen test that does a `git mv` while main adds a caller of the old module.

3. **Bare-name sibling imports in `tests/` are never matched** (A4, B2). Both reviewers found this, and the repo does it in at least ten test files, including the PR's own new test.
   - A change on main to the shared `Kitchen` fixture leaves a stale green standing.
   - Fix: name files under the pytest import root (`tests/`) by their bare module name, and add a test for the sibling-import case.

4. **An unreadable head makes the check fail open** (A3).
   - When `git show <head>:<path>` fails, the file is read as empty, so no dependency can match and the check stays green.
   - Everywhere else in jmerge, a git failure blocks the merge. Other code in `cli.py` already fetches `refs/pull/<n>/head` when the head is missing.
   - This is a merge gate, so failing open is the wrong default even if the case is rare.
   - Fix: run `cat-file -e` first and fetch the pull ref if needed. If the head still can't be read, return a stale reason. Add a test for this case.

### Consider

- **Codex and Grok lines send no effort, yet the docs say the rule holds for every role** (A2).
  - Not sending effort is not *setting* it above medium, so the user's rule isn't strictly broken.
  - But THIRD_PARTY.md and the docstring claim more than was checked.
  - Cheapest honest fix: narrow the wording to Claude lines and gate the Codex/Grok defaults question. Finding the actual caps is the bigger option.
- **Any path mentioned in any file counts as a dependency, so docs-only PRs go stale** (B3).
  - The match is a proxy (a substring in raw text), not a real relationship. It fails closed, but it costs rebases and full `make check` reruns. This very PR would trigger it.
  - Limiting the path match to files the check can execute or load is a small change. Worth doing if it stays cheap; otherwise note it for later.
- **Three doc files changed outside the "Where" line** (A7): `docs/configuration.md`, `docs/jmerge.md` and `docs/jroles.md`.
  - The edits describe the new behaviour, so keeping them is defensible.
  - The scope rule is explicit, though, so this needs a deliberate keep-or-revert, with the reason given in the finding's ending.

### Noted
- **A5**: the substring path match and the suffix-based `conftest.py` rule. These are real imprecisions, but they fail closed. The basename fix is trivial and can ride along with B3 if that one is taken.
- **A6, B5**: one `git show` per file and O(n×m) `ast.parse` calls. Neither reviewer showed that the 300 s jbus limit is actually at risk at current sizes. Batching with `cat-file --batch` and parsing each file once would be a fine follow-up.

### Dismissed
- None. Every finding was about changed lines and had a concrete basis. The nits are low-impact but not wrong.

### Agreement Map
- The two reviewers agreed independently on the two most important problems: the unproven effort shape (A1/B4) and the bare-name import blind spot (A4/B2). They also agreed the matching loop is inefficient (A6/B5).
- Where they diverged, each added a distinct gap in the new check's coverage:
  - A found the fail-open unreadable head (A3).
  - B found the rename hole (B1) and the docs false positives (B3).
- The pattern says the merge-result heuristic is sound in shape but under-tested at its edges. Its tests cover the happy `src/` layout and in-file renames, but not moves, the `tests/` import root, or a missing head.
- The effort decision rests on an assertion that the schema cannot back. Proving that shape, or gating the question, matters more than anything else here, because a wrong shape silently breaks the user's never-above-medium rule.
