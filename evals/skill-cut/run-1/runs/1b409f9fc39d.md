### Intent
> Topic 10, "A way to undo a bad merge into standing.md." Every edit to a home's `standing.md` becomes its own pushed commit in `~/.local/state/home`. The home skill, the scoped-homes page and the handoff skill run `jbus snapshot --why <text>` right after the edit, and the twice-daily timer stays. `docs/state.md` gains a short "Undo an edit to standing.md" section (find with `log -p`, restore with `show <commit>^:<path>`, then snapshot with `--why`). Tests in a temporary tree with a bare remote prove both the one-commit snapshot and the documented restore. `make check` passes.

### Reviewers
- Reviewer A: 7 findings
- Reviewer B: 5 findings
- The two agreed on the four findings that matter most: concurrency, restore truncation, the new handoff duty, and the out-of-scope file. Both answered the review skill's questions.

### Act On

**1. No lock between snapshots: concurrent runs fail on `index.lock`, or one run's `reset` swallows another's staged edit.** (A1, B1)
- **Where:** `src/jbus/snapshot.py` `take`/`_commit`. The prose that triggers it is at `skills/home/SKILL.md:79` and `skills/home/scoped-homes.md:7`.
- **Why it matters:** Before this change, one timer ran `take` twice a day. Now any home or scoped home runs it at any moment against the same index.
- **Concrete failures:**
  - A home overlapping the 08:30 or 17:30 run can make the timer's unit fail. `OnFailure --alarm` then alerts the desk and every project about a failure that isn't real.
  - A's `git reset -q` landing between B's `add -A` and `diff --cached` gives B "nothing changed", and B's edit gets no commit of its own. That breaks the guarantee the task exists for.
- **Fix:** an exclusive `flock` on a file in `.git` held across add, commit and push. It is small, inside `snapshot.py`, and turns collisions into waits. Add a test that runs two `take` calls concurrently.

**2. The documented restore truncates the live `standing.md` before `git show` can fail.** (A2, B2)
- **Where:** `docs/state.md:108`.
- **Why it matters:** `> file` empties the target first. Three ordinary inputs then wipe every standing rule for the repo:
  - the commit that created the file (its parent has no such path);
  - the root commit;
  - a mistyped hash.
- The next step in the doc then snapshots the empty file, and the next start reads "no rules".
- This is the recovery procedure, so it must not be the thing that destroys data. Both reviewers traced the same path independently.
- **Fix:** document `git -C ~/.local/state/home restore --source=<commit>^ -- <repo>/standing.md`. It fails without writing. Say what to do when the bad edit created the file (delete it, or restore from `<commit>` minus the line). Add a test that undoes the creating commit.

**3. Handoff gains an untasked duty to write standing rules.** (A5 warning, B3 nit)
- **Where:** `skills/handoff/SKILL.md:92`.
- **Why it matters:** "One it did not write yet goes there now" adds a new place where rules get written. It contradicts the sentence just before it ("the home wrote it … when it heard it"), and it exists only to give the snapshot step a hook.
- The task asked handoff to snapshot after an edit, not to start making edits. Two writers of standing rules is a behavior change the user didn't ask for.
- **Fix:** drop the line. Keep a general "after any edit to `$H/standing.md`, run `jbus snapshot --why …`". This also removes the hardcoded `added` that A4 flags as drift.

### Consider

**4. `--why` labels a whole-tree commit.** (A3, B1)
- **Where:** `src/jbus/snapshot.py:193–195`.
- **The problem:** `add -A` sweeps in briefs, `merge.log`, other repos' trees and so on, under a message that names one standing.md edit. When two homes of the same repo both edit before either snapshots, one commit holds both edits, and the documented undo of "the bad one" reverts the other rule too.
- Path-limited `log -p` and `show` still work, so undo is not broken in the common case.
- **Tradeoff:** a path-scoped form (`jbus snapshot --why … -- <path>`, committing only that path) makes "a commit of its own" literally true and the message honest. But it widens a task whose Design line says "one flag and one step", and it changes what `snapshot` means.
- The lock in item 1 already narrows the two-edits window. My lean: take the lock now and gate path-scoping through `jbus gate` with the default "not now".

### Noted
- **Rule in prose, copied three times** (A4). The task specified skill instructions as the mechanism, so prose is the chosen design. The drift A4 points to goes away with the item 3 fix. A `jbus standing add` verb that writes and snapshots in one step is the durable answer, outside Where, for later.
- **`docs/jbus.md` edited outside Where** (A6, B4). The edit is accurate and is the right place to document the flag. Keep it, and record that the brief's Where line missed it.
- **`with_origin` beside older inline copies** (A7). Moving the old tests onto it means editing unchanged lines. Low impact, so leave it.
- **Test name narrower than its body** (B5). `tests/test_jbus_snapshot.py:285` checks the `why=` message too, and its no-why half repeats line 77. A rename would be tidy but nothing is wrong.

### Dismissed
None. Every finding was grounded in the diff. The weak ones are low-impact rather than wrong.

### Agreement Map
- **Convergence:** both reviewers independently found the two real defects, the missing lock and the truncating restore, plus the scope creep in handoff and the out-of-scope doc file. That consensus on concrete execution paths is why items 1–3 are Act on.
- **Divergence on handoff severity** (A warning, B nit). I side with A: it changes who writes standing rules and contradicts adjacent text, which is more than a nit.
- **Unique to A:** the structural critiques (prose rule, helper duplication). Fair points, but they ask for design beyond this task.
- **Unique to B:** a test-naming nit.
- **What the pattern says:** the feature is the right shape. Its weak points are the two places where it meets the real environment, concurrent homes and a failing shell command. The fixture tests, which use a clean, single-actor tree whose parent always has the file, never exercised either one.
