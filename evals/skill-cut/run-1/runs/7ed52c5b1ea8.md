### Intent
> Move the brief checks (Proves it, Size, Playbook a real crewmate playbook, and every required field of `templates/brief.md`) to `jbus queue add`, so an incomplete brief is refused with one line per fault and never queued. The launch keeps its checks as a backstop. Bind the user's approval to a deterministic meaning fingerprint over the scope and risk fields, so typos, formatting, reordering and Task-only edits keep the go, while a changed Done-when line, path, number or value re-asks. The record holds the fingerprint, the full `brief_sha` and the basis (the user's word or message id). `queue show --json` or `queue verify` prints them so another bot can check them. Old full-sha rows keep working. The PR description and `docs/jbus.md` state the method and its known limit. `make check` exits 0.

### Act On

1. **Unfilled template text passes `queue add` for Task, Done when, Pull request and Review** (A1, B1). `_filled` only treats a value as template text when it starts with `<`. The template's own lines start with `"` or `- `, or are `a | b` choices. So a brief copied straight from the template gets queued and put to the user. That breaks the core Done-when line ("an incomplete brief can't be queued"), and the docs and skill now claim otherwise. The test hides this because it writes `Task: <the request>` without quotes.
   - Fix: strip quotes and list markers, then reuse `_template`.
   - Test: run `queue add` on the unedited `templates/brief.md` and expect a fault for every required field.

2. **Contractions turn a negation into a typo** (A3, B2). The author chose to strip apostrophes, so `shouldn't` becomes `shouldnt`, which is within two edits of `should`. As a result, "should fire" changed to "shouldn't fire" in a Done-when line keeps the go. That is a real change of intent passing silently, which is the one thing the fingerprint must catch.
   - Fix: tokenise `n't` as `not`, and add a test that `should` changed to `shouldn't` re-asks.
   - The other cases come from the spec itself, not from the author's choices: near antonyms (`include`/`exclude`, `import`/`export`) and direction lost to filler-dropping plus sorting ("move a to b" versus "move b to a"). For those the remedy is to state them in the limit section of `docs/jbus.md` and the PR description, not to change the method.

3. **`faults` and the launch's `CHECKS`/`ASKED` are two hand-kept lists** (A4, B3). The task exists because checks ran in the wrong place. Keeping add and launch in step "by prose" recreates that failure for the next check someone adds. The only parity test covers Design alone.
   - Fix: one `(kind, check)` tuple in `jbriefs.parse`. `faults` iterates it after the required-field pass. `dispatch` builds its checks from it and keeps only the grandfathering. Both files are inside Where.

4. **The home skill discards "its go does not hold"** (A2). The launch block prints `$said` only on failure. A successful add that voids the go therefore looks like a plain success, and the user is re-asked only when the launch gates later. That is the "queued, then gated" order the task removes. The fix is small and inside Where (`skills/home/SKILL.md`):
   - Surface the line on success.
   - Say in the skill that the home then puts the brief to the user again.

5. **The PR description says the launch checks are unchanged, but they are not** (A8). `parse.playbook` now refuses non-crewmate playbooks. `dispatch.ASKED` calls it, so rows approved since `shaped_since` with, say, `autopilot-full` now gate at launch. The change is intended, but the description must say so; it is a one-line edit.

### Consider

- **`scope` integrity and semantics** (A5).
  - The cheap, worthwhile part: the docs tell other bots to compare `scope`, but `scope` can differ while `holds` is true (after a typo fix). The docs should say `scope` equality is stricter than `holds`, and that bots should rely on `verify`'s `holds`.
  - The part that can wait: a fingerprint method or version field is cheap now and painful to retrofit once `FILLER` changes.
  - Checking `scope` against the stored `meaning` defends only against hand-edits of `queue.json`. Anyone who can edit that file can forge anything, so it is low value.
- **The CLI matches the end of a string to decide what to print** (A6, B5). It is fragile and breaks silently if the wording of either constant changes. It is likely to be touched anyway when fixing Act-on 4; returning a small structured result from `queue.add` would fix both.

### Noted
- Redundant work: `designed()` is called twice, the `_filled` result for Size is computed and thrown away, and routing lines are stripped twice (A7, B3 tail).
- A re-add that only changes priority on an old, incomplete brief forces a rewrite that voids its go. This is theoretical; all four current rows are complete (A9).
- `approve` does not run `faults`, so an incomplete row queued before this change could still be approved. The launch backstop catches it, and no such rows exist (B4).
- Greedy pairing in `_pairs` can re-ask when a valid pairing exists. It errs safe, but the docstring overstates what it does (B6).
- `src/jbus/asks.py` was changed instead of `cli.py`. The queue verbs live in `asks.py`, so the Where line was inaccurate rather than the change overreaching. Mention it in the PR description (B7).

### Dismissed
- **B8, "PR description unconfirmed"**: Reviewer B could not see the PR body, but Reviewer A did. A quotes it as stating the method and the `must`/`may` limit. The real gap in the limit section is covered by Act-on 2.

### Agreement Map
Both reviewers independently found the same three substantive problems: template text passing, negation slipping through the typo allowance, and duplicated check lists. They also both flagged the string-matching CLI. That consensus, and the concrete execution paths behind each, make the first three the clear blockers. Their unique findings split by vantage point:
- A looked outward at the consumers (the home skill, the PR text, bots reading `scope`) and found the two other real issues.
- B looked inward at algorithm details and the paperwork; those findings are safe or minor.

Neither inflated nits into warnings beyond reason. The implementation is broadly sound. The blockers are gaps at its edges (template detection, contraction tokenising, a single source of checks) rather than a flawed design.
