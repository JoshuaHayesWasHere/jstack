### Intent
> The user asked (2026-10-15, relayed by Sous Chef) that this project be added to jbus, and that every new home be added to the bus. `/new-home` already registers its repo. A home started by `/home`, or one made before that step existed, never registers.
>
> The PR fixes this in four ways:
> - The home skill's start registers its repo through the same block or helper that new-home's step 3 uses, so the two cannot drift.
> - A home that merges its own pull requests writes its id to `home-thread` before the add, so `jmerge` cannot race it.
> - jbus lists homes with a `home-id` and no project, as one quiet line, in `jbus status` and as a count on the view's machine row. Parties and experts are excluded.
> - `docs/jbus.md` is updated, and there are tests for each.
>
> `jbus project add` stays the only writer of the config. No other repos are added.

### Act On

**1. The home start's step 3 now calls a deliberate merge switch a stale leftover** (A1, B1)
- A self-merging home now writes its id to `home-thread`.
- Every later start then hits step 3 (`skills/home/SKILL.md:171-178`). It prints `jbus does not merge here … Nothing empties it but the user` and explains the id as an old home's leftover from before `home-id` existed.
- B traces the consequence. The user is told the id is stale, empties it, and then jbus and the home both merge. That is the exact race this task exists to prevent.
- Both reviewers found this, and the execution path is concrete.
- Fix: reword step 3, and the row's "not this home's id" clause, so that an id written by "On the bus" reads as the switch being on by choice.
- A's other option is to write a fixed marker instead of an id, since `home_thread` only checks that the file is non-empty. That is also fine.

**2. new-home contradicts itself about who writes `home-thread`** (B2)
- The changed step 3 block now writes the switch.
- Step 4 of the same file was not updated:
  - `:171` still says "written by hand".
  - `:175` still says "this skill writes none of them".
- An agent reading step 4 gets the old rule. This is the same failure as item 1, in another place.
- Fix `:171`/`:175` in this PR.
- These are outside "Where", so note them for a follow-up rather than this PR: `skills/handoff/SKILL.md:199`, `docs/state.md:18`, `docs/configuration.md:151`.

**3. The `ME` placeholder invites a literal "nothing", which silently turns jbus merging off** (B3)
- The placeholder reads `<the id of a home that merges by itself, or nothing>`.
- The block only checks that `<` and `>` are gone. If a model fills in `ME='nothing'`, the block writes that word to `home-thread`, and jbus never merges the repo again.
- This is a rule held only in prose, guarding a silent and lasting effect.
- Fix: reject a value that is not shaped like a thread id and print `not filled in`. Or reword the placeholder so that "empty" is unambiguous (`ME=''`). The check is the stronger fix.

### Consider

**4. Two of the three branches in "On the bus" cannot be reached from a real start** (A2, B4)
- Step 5 runs the block only after step 4 printed `no project:`. So the `on the bus` and `jbus is not installed` branches, and the prose for them, are dead. The block's only real output is `C`.
- The test reaches `on the bus` only by calling `machine.start()` directly. It checks a route that a real start never takes.
- Both reviewers agree, and the cleanup is cheap: derive `C` inline in step 1, or have step 4's `no project:` line print it. That deletes a guarded block, a branch table, and a test path.
- Tradeoff: it is a correctness-neutral simplification. It is worth doing while the file is open, though, because dead branches in a skill file mislead the agent that reads it.

**5. The `status()` docstring says the opposite of what the code does** (A5)
- It says the list is "which no pass leaves", but `poll` writes it to `status.json`, and both the view and the next pass read it back.
- This is a one-line fix to a misleading comment in new code.

**6. The new docs paragraphs split `jbus project add` from its argument bullets** (A6)
- The bullets now read as if they belong to the "homes not on the bus" paragraph.
- Moving the two new paragraphs below the list is trivial, and the section was in scope anyway.

### Noted
- **A4.** A trailing slash in a hand-filled `C` makes `${C##*/}` empty, and `home-thread` lands at the state root. The home's own block derives `C` with `dirname`, so this needs a hand-filled mistake. If the fix for item 3 adds a validation step, an empty-name guard can join it at little cost.
- **B5.** The `project` → `one` renames in `poll` and `alarm` go slightly past what the task needs. They do follow from the newly imported `project` module, but `first(project: …)` still shadows it, so the result is inconsistent either way. This is low impact and not worth a cycle.

### Dismissed
- **A3. "A self-merging home can turn off jbus merging for a project someone else just added."**
  - Whether a repo is home-merged is set by the home's rules, not by which thread ran `jbus project add`.
  - If the home merges by itself, `home-thread` must be set even when the add answers `already`. Emptying it on `already`, as suggested, would let jbus and the home both merge: the race the task removes.
  - Two threads making conflicting merge decisions within seconds of each other is a policy conflict for the user. It is not something this block should reconcile.
