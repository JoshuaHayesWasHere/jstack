### Intent
> The audit's P7 optional items, under the user's approval of "every other upstream update." There are two questions.
> - **Merge result.** Find out from the code whether jmerge's "fails over today's main" check runs the checks on the merge result. If it does, say so in THIRD_PARTY.md. If it doesn't, make it do so, with a test, when main changed a caller or a dependency of the PR's files (or a lockfile).
> - **Effort.** Find out from T3's own tool schema whether a T3 `modelSelection` launch takes an effort setting. Write the decision in THIRD_PARTY.md either way, keeping effort at medium or lower and raising nothing.
>
> `make check` and `jgauge test-slot -- make check` must pass. Scope is `src/jmerge/`, `src/jbus/`, `src/jroles/`, THIRD_PARTY.md and tests.

### Act On

**1. The effort shape is asserted, not read from T3's schema, and the test can't fail.** (A1, B4)
The repo's copy of the T3 schema types `options` as `{"anyOf": [{}, {"type": "null"}]}`, which accepts anything. So the list-of-`{"id": "effort", "value": ...}` shape has no source, and the schema test passes whatever jroles prints. "Done when" requires the answer to be read from T3's own schema, and "Proves it" requires that schema to be quoted. Neither is met.

This matters because a wrong shape fails silently. By the PR's own account, T3's default is `high`, so every Claude role would quietly break the one rule this part exists to keep.

Fix: find the real source of the shape (T3's model-options contract or provider code, or a captured accepted launch), cite it, and pin it in a fixture or test that fails on a different shape. If no source can be found, send the shape question to `jbus gate` and say so in THIRD_PARTY.md instead of stating it as fact.

**2. A PR that renames or moves a module misses callers that main added under the old name.** (B1)
This is a concrete path and the central case of #613. `left` is fed to `stale_paths` but not to `related`, and GitHub lists only the new path of a rename. So main adding `from pkg import core` after the PR moved `core.py` passes as fresh.

Fix: pass `left` into `related` with empty text, and add a Kitchen test that does a `git mv` while main adds a caller of the old module.

**3. An unreadable PR head makes the check pass instead of block.** (A3)
When `git show <head>:<path>` fails, the PR's files are read as empty, so the "main changed a dependency" direction can never match. Everywhere else in jmerge, a git failure blocks the merge; this one fails open.

Fix: check `cat-file -e` first and fetch `refs/pull/<n>/head` as the code already does around `cli.py:1078`. If the head still can't be read, return a stale reason. Add a test for the missing head.

**4. Bare-name imports between test files are never matched.** (A4, B2)
Both reviewers found this independently with the same concrete case: the PR's own `tests/test_jmerge_callers.py` imports `Kitchen` from `test_jmerge_fresh`, and at least ten test files work this way. If main changes a shared test fixture, a PR touching a test that uses it is still called fresh.

Fix: also name files under the pytest import root (`tests/`) by their bare module name, and add a test for a sibling test import.

### Consider

**A raw path mention counts as a dependency, both ways.** (B3; A5 is the same proxy at a smaller scale)
A docs-only PR goes stale whenever main touches a path the docs mention, and this PR's own doc edits are an example. It fails closed, so it is safe. The cost is a full re-run of `make check`, or "needs a rebase" on guarded PRs, for prose mentions.

The tradeoff: limiting path matches to files the check loads (code, Makefile, CI config, lockfiles) is a small change, but it narrows a heuristic that currently errs safe. I recommend doing it, since the noise lands on exactly the docs PRs this repo produces often.

**Codex and Grok lines send no effort, yet THIRD_PARTY.md and the docstring say the rule "holds for every role the map names".** (A2)
Not sending effort doesn't *set* it above medium, so the user's rule isn't broken by code. The written claim, though, is unverified.

Cheapest honest fix: narrow the wording to Claude lines and send the Codex/Grok default question to `jbus gate` with the options. Capping them properly would need each provider's effort option, which is beyond this S task.

**Cost of the new check.** (A6, B5)
There is one `git show` per file per ready PR per run, and B5 adds O(|ours|×|theirs|) `ast.parse` calls, all under a 300 s jbus pass. Parsing each file once and reading blobs with a single `cat-file --batch` is cheap to do. It only matters once a day's worth of main paths piles up, so this can wait unless the pass times are already close to the limit.

### Noted
- **Substring path match and suffix conftest match.** (A5) These fail closed and only add noise. `os.path.basename(...) == "conftest.py"` is a one-line tidy-up worth doing while in that code for the Consider item above.
- **Docs outside the "Where" line.** (A7) `docs/configuration.md`, `docs/jmerge.md` and `docs/jroles.md` each describe the behaviour this PR adds, so keeping them is the right call. They are recorded here as outside Where for whoever owns the scope.

### Dismissed
None. Every finding names a concrete changed line and a real effect. The weakest ones (A5, A6, B5) fail safe or concern cost, and are bucketed accordingly rather than rejected.

### Agreement Map
The reviewers converged on the two places where the PR claims more than it proves:
- The effort shape rests on an `{}` schema (A1 = B4).
- The import heuristic only knows the `src/` layout (A4 = B2).

When two independent reads land on the same file, line and example, those are the strongest signals in this review.

Where they diverged, each found a distinct way the merge-result check fails open:
- B found renames (the old path never compared).
- A found an unreadable head (empty text never matches).

Together these say the "callers and dependencies" check was tested on its happy path (`RENAMED` in place) but not on the ways its inputs can go missing. The fix pattern is the same for both: a missing input must count as stale, not as unrelated.

Their cost and noise findings (A5, A6, B3, B5) all point the other way, at the check being too eager or too slow. None of those is a correctness problem.

The `make check` / `jgauge` line went unexamined by both reviewers and should be confirmed by running it.
