### Intent
> Section 3 of the /deeper design: a step in the home skill's brief writing, not a separate file. It runs on its own for research, perf, analysis and outcome briefs and carries its own copy of the four questions; `/deeper` stays manual. Answer 2 goes to the scout's `Read:` or the request's sources, answer 3 to the brief for the crew, and answer 4 to `Proves it:`. Mechanical fixes, docs changes and known-cause bug fixes skip it. Tests pin the step, and `make check` and `jgauge test-slot -- make check` pass. Where: `skills/home/SKILL.md`, `templates/scout-request.md`, and the home skill's tests. `templates/brief.md`, `skills/deeper/`, the principle and the parser are not to be touched.

### Act On

**1. The step writes a brief line nothing defines, and a `Read:` line the template forbids** (A1, B1)
- The step sends answer 3 to an `Instruments:` line. That line exists only in this diff. `templates/brief.md`, the scout skill and the parser don't know it.
- The step also has the home write `Read:` on its own briefs. `templates/brief.md:17` says home-written briefs leave `Read:` out.
- The phrase "though the home wrote it" acknowledges the conflict without resolving it.
- Effects:
  - A home that reads the template first, as it is told to, gets opposite instructions.
  - A scout following its own skill drops answer 3.
- Why it blocks: the step's whole job is to get answers 2, 3 and 4 into briefs, and the destination for 3 doesn't exist anywhere downstream.
- The Done-when line asks only that answer 3 be "in the brief for the crew" and that answer 2 go to "the scout's `Read:`". Neither requires a new field or a home-written `Read:`.
- Fix inside "Where":
  - Put answer 3 in a line the template already has, such as the task body or the Done-when list, and say which one.
  - Use `Read:` only on scout-written briefs. A home brief carries answer 2 in its body or sources.
  - If a real `Instruments:` field is wanted, record it in the Result as a follow-up for `templates/brief.md` and the scout skill, both outside "Where".

**2. The trigger is the playbook name, not the kind of work** (A2, A3, A4, B2, B3; merged)
The case arm decides from the picked playbook and looks at the kind of work only when the playbook is `none`. Each reviewer found concrete wrong paths:
- **`bug-fix` always skips.** That playbook is "reproduce, root-cause and fix", which covers bugs whose cause is unknown. The boundary exempts only bugs whose cause is known. `tests/test_home_deeper.py:163` locks this mismatch in by labelling `bug-fix` "known bug".
- **Outcome work under `feature` or `autonomous-run` always skips.** Research or perf work run under `swarm` or `arena` skips too. So outcome briefs get the step only when no playbook is picked, which misses the intent's fourth kind.
- **On the scout path (`:430`), the scout's own playbook decides.** Every scout playbook is `investigation` or `trace-forensics`, both in the arm. So a scout request briefing a docs change or a known-cause fix gets the four questions, which breaks the skip line for scout-written briefs.
- **The hard-coded list of ten names will drift.** The test checks only that each listed name is a file in `playbooks/`.

The intent says the kinds are "named how the home tells them, *for example* by its playbook". The playbook was meant as a hint, not the deciding input.

Fix: make the kind of the task being briefed the block's input in every case, for example `research|perf|analysis|outcome|known-cause-fix|mechanical|docs`. On the scout path, that means the kind of the task in the Deliver line, not the scout's playbook. The playbook can suggest a default kind.
- This removes the name list and its one-way test.
- It fixes `bug-fix`, outcome work and the scout path at once.
- The test at `:163` should then pin "known-cause fix skips" and "unknown-cause bug runs".
- A per-playbook marker in `Run by:` would also work, but it changes `playbooks/`. Note it for later.

### Consider

**3. A request that asks for no brief leaves answers 3 and 4 with nowhere to go** (A5, B4)
- `:537` covers only a Deliver list that asks for a brief. Report-only requests exist, so this is a real gap.
- B4's remedy is cheap and inside "Where": write 3 and 4 as `Questions:` items, which the request template already has.
- The tradeoff is small: one sentence. I'd take it while editing `:537` for item 1.

**4. The kind-is-already-covered skip is a prose override** (B6)
- The block prints `deeper`, then a trailing sentence tells the home to skip anyway for a task whose Done-when already names its data, instruments and judge.
- If item 2's rework turns kind into the input, this case can become one more kind, and the block prints the skip itself.
- Worth folding into item 2. Not worth a separate change if item 2 is done some other way.

**5. No test checks that the lines the step names exist in the templates** (A6)
- A test that takes each brief line the block names and asserts it is in `templates/brief.md` (or `templates/scout-request.md` for the request path) would have caught item 1.
- It also executes something real: it parses the block's output against a file.
- The tradeoff: it is cheap and guards against regression once item 1 is fixed. I lean toward adding it.
