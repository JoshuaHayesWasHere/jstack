### Intent
> Answer the audit's P7 optional items from the code. First, does jmerge's "fails over today's main" check run the checks on the merge result? If not, make it do so when main changed a caller or a dependency of the PR's files (or a lockfile), with a test. Second, does a T3 launch (`modelSelection`) take an effort setting, read from T3's own tool schema? Record the decision in THIRD_PARTY.md, and never let jroles set effort above medium. `make check` and `jgauge test-slot -- make check` must pass.

### Reviewers
- Reviewer A: 7 findings (4 warnings, 3 nits)
- Reviewer B: 5 findings (4 warnings, 1 nit)
- They did not agree on everything. Both asked the review skill's questions; A7 covers question 7. Neither reported on the `make check` / `jgauge test-slot` lines, so those still need the Result's own evidence.

### Act On

**1. The effort `options` shape is asserted, not read from T3's schema (A1, B4).**
The repo's T3 fixture types `options` as `anyOf [{}, null]`, so it accepts anything. The test that validates jroles' output against it proves nothing. "Done when" requires the answer to be read from T3's own tool schema, and "Proves it" requires that schema to be quoted. That cannot be done for a shape the schema does not contain. If the shape is wrong, every Claude role silently launches at T3's default, which the PR says is `high`. That breaks the user's one hard rule with no signal. Both reviewers found this independently.
- Fix: cite the real source of the shape (T3's provider or model-options code, or a captured accepted launch) and pin it in a test that fails on a different shape.
- If no source exists: say so in THIRD_PARTY.md and raise it as a gate.

**2. THIRD_PARTY.md and the docstring say the medium cap holds for every role, but Codex and Grok lines send no effort (A2).**
Unlike most findings here, this one is about a false claim in the decision line the task asks for, and it sits on the user's rule. The cheap fix is in scope:
- Narrow the wording to Claude lines.
- Gate the Codex/Grok default question with `jbus gate`.

Finding each provider's default is not needed now.

**3. A rename hides callers that main added under the old module name (B1).**
This is a concrete path, and it is the core #613 case. `left` reaches `stale_paths` but not `related`, and GitHub lists only the new path of a rename. Main can add `from pkg import core` after the PR moved `core.py`, and the PR still merges onto a broken import. The fix is small: feed `left` into `ours` with empty text. Add a `git mv` Kitchen test.

**4. Bare-name sibling imports in `tests/` are never matched (A4, B2).**
Both reviewers found this, and it is concrete in this repo: at least ten test files, including the PR's own new test, import siblings by bare name. A main-side change to the shared `Kitchen` fixture leaves the green standing. That is exactly the "main changed a dependency" case the task targets. Fix it by naming files under the pytest import root by their bare module name, and add the test.

**5. An unreadable head makes the dependency direction fail open (A3).**
If `git show <head>:<path>` fails in the main checkout, every PR file reads as empty and no dependency can match. The check stays green. Two things make this a real gap:
- `moved` fetches branches only, while other code in `cli.py` fetches `refs/pull/<n>/head` for exactly this reason.
- Every other git failure in jmerge blocks the merge, so this is the odd one out in a merge gate.

Fix: check the head with `cat-file -e` and fetch the pull ref if needed. If the head is still unreadable, return a stale reason. Add a test for the missing-head case.

### Consider

**6. A path named in prose counts as a dependency (B3).**
A docs-only PR (THIRD_PARTY.md, `docs/jmerge.md`) goes stale whenever main touches any path it mentions. Guarded PRs get "needs a rebase", and the others re-run all of `make check`. This fails closed, so it is safe, but it is a proxy and the noise will be frequent in this repo.
- Tradeoff: limiting path matches to executable or config files (code, Makefile, CI paths) is a modest change, but it adds a file-kind rule to `uses`.
- Worth doing if docs PRs are common. Otherwise it could follow later.

**7. Three docs files changed outside "Where" (A7).**
`docs/configuration.md`, `docs/jmerge.md` and `docs/jroles.md` each describe the new behaviour. Keeping them in sync is reasonable, but they sit outside "Where", so it is the user's call. I lean toward keeping them and noting it in the Result.

### Noted
- **Substring path match and `endswith("conftest.py")` (A5):** this fails closed. The basename check is a one-line tidy-up if `uses` is touched for item 6 anyway.
- **One `git show` per file and pairwise `ast.parse` (A6, B5):** this is real O(n×m) work, but nothing shows it near the 300 s limit at current PR sizes. Batch it with `cat-file --batch` and parse once per file only if pass times show it matters.

### Dismissed
None. Every finding has a concrete basis; the nits are low-impact rather than wrong.

### Agreement Map
- **Agreed independently:** the effort-shape gap (A1/B4) and the bare-name test imports (A4/B2). These are the two strongest signals, and both are concrete in this repo, not hypothetical.
- **A alone:** the fail-open head read (A3), the Codex/Grok cap claim (A2) and the scope finding (A7).
- **B alone:** the rename blind spot (B1), the strongest single finding, and the docs-staleness proxy (B3).
- **Both:** performance nits that point at the same pairwise loop.

The pattern: the matching heuristic in `ready.py`/`cli.py` has several independent blind spots (renames, non-`src` import roots, unreadable heads). Each one fails open, the opposite of the rest of jmerge. Its noisy cases (substring, prose mentions) fail closed. The fail-open cases are the ones to fix in this PR. On the effort side, both reviewers saw that the "proof" is a schema that proves nothing. Until the shape has a real source, the decision in THIRD_PARTY.md is unproven.
