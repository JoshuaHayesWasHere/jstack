### Intent
> Run the Size/Playbook/Proves-it and required-field checks at `jbus queue add`, before a brief is queued for the user, with the launch checks kept as a backstop. Bind an approval to a deterministic meaning fingerprint over the fields that carry scope and risk, so typos, formatting, reordering and edits to non-scope fields keep the go, while added, removed or changed Done-when lines, paths, numbers or values re-ask. Store the fingerprint, the full `brief_sha` and the approval basis on the record, and make them printable for other bots to verify. Old full-sha rows keep working. Document the method and its known limit, and test all of it under `make check`.

### Reviewers
- Reviewer A: 9 findings
- Reviewer B: 8 findings
- They agreed independently on the three most serious issues: unfilled template text passes, negation keeps the go, and the add and launch checks are two separate lists. The review skill's questions were asked; both reviewers' findings follow them.

### Act On

1. **`queue add` accepts the template's own text for Task, Done when, Pull request and Review** (A1, B1). `_filled` only treats a value starting with `<` as template text. The template's quoted Task, `- <a check>`, and the `x | y` choices all pass.
   - This is a "Done when" line the PR does not meet: "refuses an incomplete brief".
   - The docs and the home skill now claim something untrue.
   - Both reviewers traced the same concrete path.
   - Fix: strip quotes and list markers and use `_template`. Add a test that runs `queue add` on the unedited `templates/brief.md` and expects a fault for every required field.

2. **Negation by contraction keeps the go, and the stated limit leaves it out** (A3, B2).
   - Dropping the apostrophe turns `shouldn't` into `shouldnt`, which is within two edits of `should`.
   - That makes "the gate should fire" and "the gate shouldn't fire" the same, which is exactly the "real change to intent" the user wanted caught.
   - This is the author's normalisation choice, not the spec's, so it should change: split `n't` into a `not` token, and add a test showing `should` → `shouldn't` re-asks.
   - The cases that follow from the spec itself must be added to the documented limit in `docs/jbus.md` and the PR body, as the "Done when" requires:
     - near antonyms within two edits (`include`/`exclude`, `import`/`export`)
     - swapped direction that filler-dropping and sorting hide (`a.py` to `b.py` vs `b.py` to `a.py`)

3. **The add checks and the launch checks are two hand-kept lists** (A4, B3).
   - The whole point of the task is that nothing gated at launch slips past `add`. Today that holds only by convention.
   - `faults` even re-implements `proven`.
   - The only parity test covers Design alone.
   - Fix: one `(kind, check)` tuple in `jbriefs.parse`, used by both `faults` and `dispatch`. Dispatch keeps only the grandfathering: no `Proves it:` line, and the `shaped_since` time. This is in scope and small.

4. **The home skill drops the "its go does not hold" line on a successful add** (A2).
   - The home prints `$said` only when the command fails.
   - So a scope change looks like a plain success, and the user is re-asked only when a later pass gates it.
   - The launch gate still catches it, so nothing unsafe launches. But the task is about moving these signals to queue time, and the fix is a few lines inside the Where line's `skills/home/SKILL.md`.

### Consider

- **`scope` is stored and printed but never checked, and has no version** (A5).
  - A bot comparing `scope` hashes would refuse a typo-fixed brief that `holds: true` accepts. That undercuts the "another bot can check" goal.
  - Cheap remedies:
    - document that `scope` equality is stricter than `holds`
    - check `scope` against `meaning` in `approved_text`
    - add a `method` field so future changes to `FILLER` or the regexes don't silently compare across versions
  - The tamper case needs a hand-edited `queue.json`, which is lower risk.
- **CLI chooses what to print by `endswith` on message constants** (A6, B5). This is fragile, and it interacts with Act On #4. Always printing the line, or returning a structured value, removes it. It is cheap, but nothing is broken today.
- **PR description says the launch checks are unchanged** (A8). `parse.playbook` now refuses non-crewmate playbooks at launch too. The change is intended, but one sentence in the PR body should say so.

### Noted
- A7: `designed` runs twice, a `_filled` result is thrown away, and `ROUTING` is stripped twice. All of this goes away with the refactor in Act On #3.
- A9: re-prioritising an old, incomplete row now forces a rewrite that voids its go. This is theoretical, since every queued row today is complete.
- B4: `approve` doesn't run `faults`, so a faulty row queued before this change can still be put to the user. The launch backstop covers it, and only legacy rows are affected.
- B6: greedy pairing in `_pairs` can re-ask when a valid pairing exists. It errs only toward asking again, which is safe.
- B7: `src/jbus/asks.py` was changed, but the Where line names `cli.py`. The queue verbs live in `asks.py`, so the Where line was inaccurate rather than the change overreaching.

### Dismissed
- B8: "PR description can't be confirmed." Reviewer A read the PR body and confirms it states the method. Its incomplete limit is already covered by Act On #2.
