### Intent
> Task: the audit's P7 optional items. Two questions need answers. First, does jmerge's "fails over today's main" check run against the merge result? If it doesn't, make it go stale when main changed a caller or dependency of the PR's files, and add a test. Second, does a T3 launch take an effort setting, per T3's own tool schema? Record the decision in THIRD_PARTY.md, with nothing above medium. `make check` and `jgauge test-slot -- make check` must pass. Proves it: the merge-result test, and the T3 schema quoted.

### Reviewers
- Reviewer A: 7 findings (4 warnings, 3 nits)
- Reviewer B: 5 findings (4 warnings, 1 nit)
- They agreed independently on two warnings: the effort shape is unproven, and bare-name test imports are missed. Each also found a fail-open path in `related` that the other missed. Both answered the review skill's questions. Neither reported on the `make check` / `jgauge test-slot` "Done when" line, so that line is unverified by this review.

### Act On

1. **The effort shape is not grounded in T3's schema, and no test would catch a wrong one** (A1, B4). Location: `src/jroles/__init__.py` (the `options` line), `THIRD_PARTY.md`, `tests/test_roles.py`.
   - The "Done when" line says the answer must be "read from T3's own tool schema", and "Proves it" asks for that schema to be quoted.
   - The fixture types `options` as `{"anyOf": [{}, {"type": "null"}]}`, so the schema says nothing about the `[{"id":"effort","value":…}]` shape, and the schema test passes any value.
   - If the shape is wrong, every Claude role silently launches at `high`. That is the exact rule this half of the task exists to protect.
   - Fix: cite the real source of the shape (T3's provider or model-options code, or a captured accepted launch), pin it in a fixture that rejects other shapes, and quote it in the Result. If no source can be found, write it as a `jbus gate` with the options weighed. Do not state it as fact.

2. **A rename in the PR hides callers that main added under the old path** (B1). Location: `src/jmerge/cli.py:645, 659-667`.
   - `left` goes to `stale_paths` but not to `related`, so `modules(<old path>)` is never compared against main's new imports.
   - This is a concrete path through #613's core case: moving `core.py` to `engine.py` while main adds `from pkg import core`. The result is a green check on a broken import.
   - Fix: pass `left` into `related` as empty-text entries, and add a Kitchen test that does a `git mv` while main adds a caller of the old name.

3. **`related` fails open when the PR head can't be read** (A3). Location: `src/jmerge/cli.py:169-171`.
   - `git fetch origin` does not fetch `refs/pull/<n>/head`. Elsewhere `cli.py` handles exactly this case, so it does happen.
   - When the head is missing, the PR's own files read as `""`, the dependency direction never matches, and the stale green stands.
   - Every other git failure in jmerge blocks the merge, and this one lets it through.
   - Fix: run `cat-file -e` and fall back to fetching the PR ref. If the head still can't be read, treat the check as stale. Add a test for this case.

4. **Bare-name sibling imports in `tests/` are missed** (A4, B2). Location: `src/jmerge/ready.py`, `modules`.
   - Both reviewers found this independently, and the PR's own new test imports this way (`from test_jmerge_fresh import …`), as do about ten other test files.
   - A change main makes to the shared `Kitchen` fixture would never make a dependent PR stale.
   - Fix: also name files under the pytest import root by their bare module name, and add a sibling-import test.

### Consider

- **Codex and Grok lines send no effort, but the docs say the rule holds for every named role** (A2).
  - Not sending effort does not *set* it above medium, so jroles isn't breaking the rule. The written claim is still unverified.
  - The cheap fix is to narrow the THIRD_PARTY.md and docstring wording to Claude lines and record the Codex/Grok question as a gate. Capping those providers would need schema work that isn't in hand.
- **Any path mentioned in prose counts as a dependency** (B3, with A5's boundary point folded in).
  - This fails closed, but a docs-only PR goes stale whenever main touches a path it mentions. A guarded PR without `fresh-check` then gets "it needs a rebase", which is real friction.
  - Restricting path matches to files the check executes or loads is a modest change. Decide whether the false-stale rate justifies it now or after observation.
- **Three doc files changed outside "Where"** (A7). Location: `docs/configuration.md`, `docs/jmerge.md`, `docs/jroles.md`.
  - The edits describe the new behaviour and look right, but the brief counts each one as a finding. Keep them and say so in the Result, or move them to "Noticed".

### Noted
- A5: the substring and `endswith("conftest.py")` matching has edge cases (`.pyc`, `myconftest.py`). It fails closed and is low impact. Using a basename check is cheap if B3 is addressed anyway.
- A6 and B5: one `git show` per file and an O(n×m) `ast.parse`. The set of paths main changed since a check started is usually small. Parsing each file once is a trivial cleanup, but nothing shows it threatens the 300 s pass today.
