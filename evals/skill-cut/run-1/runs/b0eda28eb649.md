### Intent
> The user asked that the Size, Playbook, Proves-it and required-field checks run when a brief is added to the queue, before it reaches the user, with launch keeping them as a backstop. An approval should bind to the brief's meaning rather than its exact bytes. The fingerprint is deterministic, uses no model, and covers the scope and risk fields: Done when, Proves it, Size, Where, Do not touch, Pull request, Review, Playbook and Stack. It is normalised by lowercasing, dropping punctuation, whitespace and markdown, dropping filler words, sorting words and sorting list lines. Paths, code spans, numbers, URLs and the values of Size, Playbook, Review, Pull request and Stack are kept exact. A typo allowance treats a word of five or more letters within two edits as the same word. So typos, formatting, reordering and edits outside scope fields keep the go, and real scope changes re-ask. The PR description and `docs/jbus.md` must state the method and its known limit. The approval record holds the scope fingerprint, the full `brief_sha` and the basis, and `verify` / `show --json` prints them so other bots can check it. Old rows keep working, and named tests cover all of this.

### Reviewers
- Reviewer A: 9 findings
- Reviewer B: 8 findings
- Both reviewers independently found the same three warnings: template text slips past `_filled`, negation and opposite words fit inside the typo allowance, and the add-time and launch-time checks are two separate lists. They also both flagged the `endswith` dispatch in `asks.py`. The review skill's questions were asked and answered.

### Act On

**1. `queue add` accepts the template's own text for Task, Done when, Pull request and Review** (A1, B1)
- `src/jbriefs/parse.py:355` (`_filled`) treats a value as template text only when it starts with `<`.
- Four of the template's own lines don't start with `<`: Task starts with `"`, Done when starts with `- <`, and Pull request and Review are `a | b` with no `<` at all.
- As a result, an unedited copy of `templates/brief.md` passes those fields, and the docs and home skill now say something untrue.
- This misses the Done-when line the task is built around ("an incomplete brief can't be queued").
- The existing test missed it because it writes `Task: <the request>` without the quotes.
- Fix:
  - Strip quotes and list markers before the check.
  - Reuse `parse._template`.
  - Add a test that runs `queue add` on the unedited template and expects a fault for every required field.

**2. Negation by contraction keeps the go, and the stated limit doesn't mention it** (A3, B2)
- `meaning.py:94` deletes the apostrophe, so `shouldn't` becomes `shouldnt`. That is within two edits of `should`, so "should fire" changed to "shouldn't fire" in a Done-when line keeps the user's approval.
- The two-edit rule comes from the spec, but merging contractions into one word is the author's own choice, and it is what pulls negation inside the allowance.
- This directly undercuts "still catching real changes to intent or scope".
- Fix:
  - Split `n't` into a separate `not` token.
  - Add a test that `should` → `shouldn't` re-asks.
- The other cases come from the spec's own rules: near opposite words (`include`/`exclude`, `import`/`export`) and swapped direction after fillers are dropped and words sorted ("move a to b"). These stay as they are, but the limit section in `docs/jbus.md` and the PR body must name them. Right now both name only `must`/`may` and `files`/`fixes`.

**3. The add check and the launch check are two separate hand-kept lists** (A4, B3)
- `parse.faults` re-implements what `dispatch.CHECKS` + `ASKED` do, and `proven` is rewritten inline.
- A check added to dispatch later would gate at launch and never refuse at `add`. That recreates exactly the "queued, approved, then gated" bug this task exists to remove.
- The only parity test covers the Design case alone.
- Fix: keep one `(kind, check)` tuple in `jbriefs.parse`. `faults` loops over it after the required-field pass, and `dispatch` builds from it, keeping only its grandfathering (no `Proves it:` line, `shaped_since`). The backstop then holds by construction. Doing this also removes A7's duplicate `designed` call and the discarded `_filled` result.

### Consider

**4. The home skill drops the "its go does not hold" line on a successful add** (A2)
- `skills/home/SKILL.md:632` prints `$said` only when the command fails.
- The re-ask still happens later, through the launch gate, so nothing breaks. But the home learns about a voided go a pass late, and the user is asked later than they could be.
- The fix is cheap and inside Where. Pairs naturally with #5.

**5. The CLI decides what to print by matching the end of the result string** (A6, B5)
- `asks.py:107` uses `said.endswith((GO_HOLDS, GO_VOID))`. Rewording either constant breaks it silently.
- Fix by returning the state as data, or by always printing the line. Low cost; worth doing alongside #4.

**6. `scope` and `holds` can disagree, and `scope` isn't checked against `meaning`** (A5)
- After a typo fix, `verify` prints a different `scope` with `holds: true`. A bot that compares `scope`, which is the use the docs describe, would refuse a brief jbus would launch. At minimum, the docs should say `holds` is the verdict and `scope` equality is stricter.
- A method/version field is cheap insurance against later changes to `FILLER` or the regexes. That is a judgment call.
- Checking `scope` against `meaning` only guards against hand-edits to `queue.json`. That is low priority.

**7. The PR description says the launch checks are unchanged, but they aren't** (A8)
- `parse.playbook` now refuses non-crewmate playbooks at launch too.
- The change is intended by the task, but the PR body states otherwise. It's a one-line correction for accuracy.

**8. `approve` doesn't run `faults`** (B4)
- An incomplete row queued before this change can still be put to the user and approved, then gated at launch.
- The launch backstop still catches it, and the fix is one line. Worth adding unless it would block approving legacy rows on purpose.

### Noted
- A7: small redundancies (`designed` called twice, a discarded `_filled` result, routing headers dropped twice). The first two go away with #3.
- A9: re-prioritising a pre-field approved row now requires a complete brief, which voids its go. Theoretical today, since all four queued rows have every field.
- B6: greedy pairing in `_pairs` can re-ask when a valid match exists. It only errs toward asking again, which is safe. The docstring could say so.
- B8: B couldn't see the PR body. A could, and its finding (folded into #2) shows the method is there but the limit is incomplete.

### Dismissed
- B7, "`asks.py` is outside Where": the queue verbs live in `asks.py`, and the Where line named `cli.py` by mistake. Putting `verify` where the other verbs are is correct.

### Agreement Map
- The two reviewers converged on every warning: the template-text gap, negation inside the typo allowance, and the two separate check lists. They also both raised the same string-matching nit.
- That consensus is the signal. All three warnings concern the PR's core promises: an incomplete brief can't be queued, real intent changes re-ask, and launch is a backstop by construction.
- They diverged only on peripheral nits:
  - A looked at the record and the docs (scope vs holds, the PR-body claim, the home skill's handling of output).
  - B looked at control-flow edges (`approve`, greedy pairing, the Where line).
- Neither found a problem with the fingerprint's core design, old-row compatibility, or the verify record. With the three Act On items fixed, the PR meets its intent.
