### Intent
> Every home ends up on jbus. The home skill's start registers its repo when jbus's config has no project for it. It shares one block with new-home's step 3, and `jbus project add` stays the only writer of the config. A home that merges its own pull requests writes its id to `home-thread` before the add, so `jmerge` does not race it. jbus's pass lists `home-id` folders that have no project, as a quiet line, in `jbus status`, and as a count in the view's machine row. Parties and experts are not listed. The tests cover the add, the order of the `home-thread` write, and the listing. `docs/jbus.md` says all this, and `make check` passes.

### Act On
- **Step 3 of the start calls a deliberate `home-thread` id an old home's leftover** (A1, B1). The change now writes the switch on purpose. Every later start still prints "Nothing empties it but the user" and explains the id as stale state from the move to `home-id`. A user who believes that and empties the file brings back the exact double-merge race this task exists to prevent. The same row also still says "not this home's id". This is a consensus finding with a concrete path, and it breaks the merge rule the task asked for. Reword `skills/home/SKILL.md:171-178` and the state row at :74 so that an id written by "On the bus" reads as "on by choice".
- **new-home now contradicts itself about who writes `home-thread`** (B2). Step 3's shared block writes the switch, but step 4 (`skills/new-home/SKILL.md:171`, `:175`) still says the skill "writes none of" the four switches. Both lines are in a file inside "Where", so fix them here. The handoff, `docs/state.md` and `docs/configuration.md` lines are outside "Where", so note them for a follow-up.
- **A literal `ME='nothing'` silently turns jbus merging off** (B3). The placeholder text itself offers "or nothing", and the only guard is that `<` and `>` are gone. Any non-empty word is then written to `home-thread`, and `merge.home_thread` treats it as the switch being on. This rule lives only in prose, and the default path can fail through it. The fix is cheap: require the shape of a thread id before writing, and print `not filled in` otherwise.

### Consider
- **Unreachable branches in the "On the bus" block** (A2, B4). The block only runs after step 4 printed `no project:`, so its `on the bus` and `jbus is not installed` branches are dead from the start flow. The new test reaches `on the bus` only by calling the block directly, so it does not test the route a real start takes. There are two options:
  - Drop the block and take `C` from `git rev-parse --git-common-dir`. This is A2's option, and it also removes one guarded block from the count.
  - Run the block on every start, so it becomes the check itself. This is B4's option.

  Either is simpler than now. The tradeoff is churn against a dead branch table and a test of the wrong route. I lean toward A2.
- **The `status()` docstring says the opposite of what the code does** (A5). The list is written to `status.json`, and the view and `poll` read it back from there. It is a one-line fix on a changed line, and the current wording misleads the next reader.
- **The new docs paragraphs separate `jbus project add` from its argument bullets** (A6). The bullets now read as if they explain the wrong paragraph. Moving the paragraphs below the list is cheap.

### Noted
- **An empty folder name from a checkout with a trailing slash** (A4). It would put `home-thread` at the state root. This needs a hand-filled path ending in `/`, and the home's own `C` comes from `dirname`, so it is low likelihood. A strip of the trailing `/` would close it if the block gets touched anyway.
- **Loop-variable renames in `poll` and `alarm`** (B5). They trace loosely to the new `project` import, and they are harmless. If kept, `first(project: ...)` should match.

### Dismissed
- **The switch kept when `jbus project add` answers `already`** (A3). This is not a bug. The switch records that this home's rules merge by themselves. If the project already exists with jbus merging, leaving the switch off is the race. Writing it is the intended outcome. The task also requires the start to say which it did, so it is not silent.
