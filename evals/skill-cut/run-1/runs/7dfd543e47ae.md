### Intent
> Add a `Proves it:` line to `templates/brief.md`, right after `Done when:`. The brief parser, and jbus's launch checks beside `dispatch.designed`, accept the line only when it names something outside the agent: a test or command, a metric, a dataset, an external judge, or the user. They refuse an empty line, the template's text, and any proof by the crew, crewmate, reviewer, agent, "self", "the model" or a review alone, each with a one-line reason. A brief with no such line is handled the way the Design line was introduced, without stranding an approved row. The change includes tests for every accepted and refused kind, and updates to the home skill's brief section and `docs/`. `make check` and `jgauge test-slot` pass.

### Reviewers
- Reviewer A: 7 findings (3 warning, 4 nit)
- Reviewer B: 6 findings (1 critical, 2 warning, 3 nit)
- Every finding from one reviewer has a counterpart from the other, except A2 and A3, which only A raised. The review skill's questions were asked; both reviewers answered against them.

### Act On

**1. The outside-word patterns let self-referential lines pass (A1, B1, B2).**
`proof()` accepts on the first `_OUTSIDE` match and never reads `_SELF` afterwards. Several patterns match ordinary words:
- any backticked span
- `make \w`, which catches "make sure"
- `\btests?\b`, which catches "self-test"
- any `N%`
- `judge`, `eval`, "his word"

Both reviewers independently built concrete lines that pass:
- "the crewmate will make sure it works"
- "the reviewer is 100% sure"
- "the model is the judge"

These are exactly the refusals the task names. B points out that `_ready` launches whenever `proven()` returns "", so this gate is the only defence.

B2's point belongs to the same fix. The tests cover only the happy side of the "outside wins" rule. No refused case contains a trigger word.

The fix:
- Make the patterns specific: a path or a known command in backticks, `make <target>` but not "make sure", `%` only next to a metric word, and drop "his word/pick/eye" unless tied to "the user".
- Add each example above to `REFUSED`, so the tests run `parse.proof` on them.

**2. A missing `Proves it:` line passes forever, not only for briefs queued before the change (A2).**
`proven()` returns "" whenever the line is absent, and nothing ties that to the row's age. Any new brief can skip the requirement by leaving the line out. The rule then holds only through prose in the home skill. The task says the parser *requires* the line.

The Done-when asks that approved rows not be stranded. It does not ask that the requirement become optional. The queue already records an `approved` time and a `brief_sha`, so a cut-off on either keeps old rows launching and gates new ones. Only one reviewer raised this, but the execution path is concrete and it defeats the feature.

### Consider

**3. Two failed checks mean two gates and two approvals (A3).**
When a brief fails both `designed` and `proven`, the user sees only the design gate. They fix it, approve again, and only then hit the proof gate. Gathering both faults into one gate keyed by the brief sha is cheap, and it also removes the `short, kind` juggling in `_ready`.

The tradeoff is how often this happens. Most new briefs already carry a Design line, so the double round is rare. Still, every round costs the user an approval, and the fix shrinks the code.

**4. `Brief.proof` and `Proof.said` have no consumer outside the tests (A5, B4).**
The change itself adds this surface, so it should either be used (shown on the jbriefs page) or removed in this PR. Removing it costs little.

**5. The template's own text is detected by a leading `<` (A6, B5).**
The check is wrong in both directions:
- It falsely refuses a real line such as `<= 50 ms p95 from jgauge` (B).
- It accepts the guide text once the brackets are stripped, because the guide itself contains "test" (A).

The Done-when requires refusing "the template's own text". Comparing against the actual template line, or against `^<[^>]*>$`, is exact. Both failures are unlikely in practice, so this goes in Consider rather than Act On. It would fit naturally in the same test pass as item 1.

### Noted
- **A head-line loop now exists in two modules, and `proven` is a pass-through (A4, B3).** This is real duplication. The clean fix is a shared `head_line()` in `jbriefs.parse`, but that means moving or editing `designed`, which "Do not touch" covers. Note it for later. In this PR, adopting the single-gate fix from item 3 already absorbs most of B3's `_ready` branching concern.
- **The Result's grandfather statement and the printed launch-check run of a real queued brief cannot be seen in the diff (A7, B6).** Check these in the brief's Result, not the code. With item 2 in place, the Result should describe the cut-off as the grandfathering rule.

### Dismissed
None. Each finding is either correct or correctly scoped.

### Agreement Map
The reviewers converged hard on the central risk: the regex precedence in `proof()`. They reached it independently, with different but overlapping examples ("make sure", backticks, "his word", "%", "judge"). That consensus, plus the concrete strings, makes this the one finding that would block the PR on its own.

They also agreed on all the smaller items: the duplicated loop, the dead `Brief.proof`, the `<` heuristic, and the unverifiable Result items. That suggests these are real but minor.

They diverged only where A looked past the parser into jbus's control flow (A2, A3). B took the "grandfathered" docs at face value. A asked what the code actually exempts, and found the exemption has no boundary. That second look is the more important of A's two solo findings.

Overall pattern: the scaffolding is right, but the gate is currently easy to pass without meaning to, in two ways. A loose match lets a self-referential line through, and a missing line passes unchecked. Fix those two and add the near-miss tests, and the change does what the user asked.
