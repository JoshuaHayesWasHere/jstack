### Act On

**1. A `Holds:` gate answered with its default never releases the thread** (B1)
`tell` and the view's carry path skip any `keeps` answer, because until now a default had always already been carried out. A held gate's thread has not acted, so `jbus answer N --default`, or ticking the default on the page, sends nothing and the held action stays parked forever. The only answer that reaches the thread is one that differs from the default. That defeats the whole fail-safe: the user's "yes, do it" is lost. `docs/jbus.md:132` also now states something false. This is a concrete path through code the change made reachable, and no test answers a `Holds:` gate.

**2. Re-piping a silence-closed question returns "already answered" and drops a new `Holds:`** (A1)
`ask` treats any answered record as settled, and a silence close now counts as answered. A thread that re-parks the same gate at a later head, which the module docstring says threads do, is told "already answered … Go by it". Any new `Holds:`/`Fail-safe:` lines are discarded. That is a path where a held, irreversible action can proceed without anyone saying yes. A1 and B1 are the two ends of the same unmodelled state: "answered" still means "settled and acted on". This is the most serious correctness hole in the PR.

**3. Silence closes the link-conflict questions that ask the home, so stacks park** (A2)
The home's reader selects `.answer == null` into `$LINKS`, and `_quiet` closes these questions after 2 hours. After that the rebase line is never sent and the conflicted link sits. This is the exact opposite of "no question parks work", and the fix sits inside the "Where" line (`questions.py`, `skills/home/SKILL.md`).

**4. "Shown as already acted on" and "with the fail-safe attached" are not met** (A4, B2)
Both reviewers found this independently. `acted`, `holds` and `fail_safe` reach `waiting-on-user.json` and nothing renders them:
- the item's `line` is unchanged
- the home's jq block drops the new fields
- `waiting._blocks` drops them
- the page drops them

Two "Done when" lines are unmet, and the one test checks the JSON file, which is a proxy for what the user sees. The parts in scope are the `line` text in `questions.py` and the home skill's jq and printf. The page panel and `_blocks` changes can be noted for later if they fall outside the "Where" line, but the in-scope surface must show the state.

**5. Home skill still says "only their name closes a question"** (A6)
This is small, but the task requires `skills/home/SKILL.md` to state the new rule. As written, the same section now contradicts it. It is a one-line fix in a file that is in scope.

### Consider

**6. Two marks that can never differ** (A5, B5)
Both reviewers raised this. `(default)` and `(recommended)` must now match on every gate, which costs two refusal branches, roughly a dozen rewritten fixtures, and the refusal of every gate an older thread pipes as `tea (default)`. Reading `(default)` as the pick, and refusing `(recommended)` on any other option, meets the "Done when" line equally well and deletes code.
- **Tradeoff:** the brief's decision deliberately spelled out "the default must be the recommended option", and keeping explicit marks is defensible.
- **Why it matters:** the backward-compatibility cost to threads already in flight is real.

I lean toward the simplification.

**7. Expert findings now recommend against themselves and vanish at 2 hours** (B3)
The expert test fixture was edited to mark "leave it" as recommended so that the suite passes, and `skills/expert/SKILL.md` was not updated. Under the new rule, every expert finding claims the expert recommends doing nothing, and then closes by silence. The literal rule ("every gate in every home") produces that, but the user surely did not mean it. The expert skill is outside the "Where" line, so this needs the user's decision on how expert findings should behave, not a fixture tweak.

**8. A silence-closed question can't be answered on the page, though the docs say it can be answered later** (B4)
A later answer works through the CLI, so the "Done when" line holds, but the question drops off the page. The cheap fix is in scope: say in `docs/jbus.md` that only `jbus answer` takes a late answer. Keeping the question answerable in the view is the better fix, and it can be noted for later.

**9. The "Your words" page presents a silence close as the user's own answer** (A3)
This misattributes a non-answer as the user's word, which the task explicitly said must not happen. The panel is outside the "Where" line, so it is a follow-up, but it is worth fixing soon.
