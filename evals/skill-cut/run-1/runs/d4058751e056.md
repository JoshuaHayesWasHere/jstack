### Intent
> Register a home's repo with jbus at the home's start, the way `/new-home` step 3 already does, using one shared block so the two cannot drift. A home that merges its own pull requests writes its id to `home-thread` before the add, so `jmerge` does not race it. jbus lists homes with a `home-id` and no project in `jbus status` and in the view's machine row, excluding parties and experts. `jbus project add` stays the only writer of the config. Firstmate, LittleRamPantries and other repos are named, not added.

### Reviewers
- Reviewer A: 6 findings
- Reviewer B: 5 findings

### Act On

1. **The new deliberate `home-thread` write contradicts prose that still calls any id there a stale leftover.** Raised by A1, B1 (merged) and B2.
   - **What happens:** a self-merging home now writes its id to `home-thread` on purpose. At every later start, step 3 still tells the user that an old home left its id there and that only the user empties it (`skills/home/SKILL.md:171-178`). New-home's step 4 still says this skill writes none of the four switches (`skills/new-home/SKILL.md:171,175`).
   - **Why it matters:** both reviewers found this on their own, and it shows up at every start. B1 gives the real cost: a user told "stale id" may empty the switch. Then jbus and the home's own rules would both merge, which is the race this task exists to prevent.
   - **Fix in this PR:** reword step 3 and new-home 171/175 so an id written at registration reads as the switch being on by choice.
   - **Later:** `skills/handoff/SKILL.md:199`, `docs/state.md:18` and `docs/configuration.md:151` say the same thing but are outside **Where**. They go under "Noticed".

2. **`ME='<…, or nothing>'` invites a literal word that silently turns off jbus merging.** Raised by B3.
   - **What happens:** the only check is that `<` and `>` are gone, and `merge.home_thread` only checks that the file is not empty. So `ME='nothing'` (or `none`) writes that word to `home-thread`, prints a success line, and stops `jmerge` for the repo.
   - **Why it matters:** this is a concrete path, the rule exists only in prose, and the failure is silent. The placeholder text itself suggests the bad value.
   - **Fix:** a shape check on the thread id (fall through to `not filled in` otherwise), or a separate explicit flag for the self-merge case. Either one is cheap.

3. **Two of the three branches in "On the bus" are unreachable from the start.** Raised by A2 (warning) and B4 (nit), merged.
   - **What happens:** the block runs only after step 4 printed `no project:`. So the `on the bus` branch and the `jbus is not installed` branch never run there, along with their prose. The test reaches `on the bus` only by calling `machine.start()` directly, so it proves a route a real start never takes.
   - **Why it matters:** this is dead logic in a skill that agents read and follow. It is also the kind of reduction the review asks us to push for.
   - **Fix:** take one of two forms.
     - A2's form: drop the block and derive `C` in step 1 (or print it in step 4's `no project:` line). This also lets the guarded-block count go back to 7.
     - B4's form: make the block the check and run it on every start.

     Either removes a branch table. Pick one, and have the test go through the trigger the start actually uses.

### Consider

- **A3, `already` leaves a self-merge switch on a project someone else just added with jbus merging.**
  - The race window between step 4 and the block is narrow. When it happens, though, the change is silent and nothing reconciles it.
  - Arguably the home's rules say it merges, so the switch is "right". Even so, the user should hear that it was turned on for an existing project.
  - A one-line notice on `already` when the block wrote the switch costs little. Emptying the switch automatically is a judgment call.
- **A5, the `status()` docstring says the list is something "no pass leaves".** The code does the opposite: `poll` writes it to `status.json`, and the view and the next pass read it from there. The fix is trivial, and a misleading docstring on new code is worth correcting while it's open.
- **A6, the new docs paragraphs sit between `jbus project add …` and its argument bullets**, so the bullets read as if they belong to the wrong paragraph. Moving them costs nothing, and `docs/jbus.md` is a "Done when" item.

### Noted
- **A4:** a trailing `/` in a hand-filled checkout makes `${C##*/}` empty, which writes a stray `home-thread` at the root of the homes' state. This needs a human typo, and `jbus project add` refuses right after. Stripping the slash is a cheap guard if someone is already in that block.
- **B5:** the `project`→`one` renames in `poll` and `alarm` don't trace to the task, and `first(project: …)` still shadows the module. The point is valid under "every changed line traces to the task", but it is harmless. Not worth a round-trip unless someone is already touching those lines; if so, either revert those two or finish the job in `first`.

### Dismissed
None. Every finding was grounded in a changed line or something a changed line breaks.

### Agreement Map
- **Where they agreed:** both reviewers found the same two problems on their own.
  - The deliberate `home-thread` write is contradicted by the old "stale leftover" prose (A1/B1).
  - The "On the bus" block's branches are unreachable from the start (A2/B4). A rated this a warning and B a nit; the consensus and the test that skips the real trigger push it to Act on.
- **Where they diverged:** A looked for edge cases in the shell (the A3 race, the A4 empty name) and in docs and docstring accuracy. B looked for every place the "only the user writes `home-thread`" rule still lives (B2), and for the placeholder failure mode (B3).
- **What the pattern says:** the jbus side (status, view, pass) drew only nits, so it is probably sound. The weak spot is the merge switch.
  - The change gave `home-thread` a second writer without updating the prose that claims a single owner.
  - It left the new write guarded only by a prose fill-in rule.
  
  Fix those two and remove the dead branches, and this is ready to ship.
