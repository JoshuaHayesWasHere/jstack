### Intent
> The user, on the grill page: "we need to make threads more obvious per project, also i want to be able to track the work of scouts and crewmates as well." Each project's row and page gets a Threads band, grouped by role and read from `pass.json`. A thread route opens a drawer showing what the thread works on. The server reads scouts' `## Report`/`Status:` (read-only) to say whether a scout is researching, has reported or is blocked. A missing thread list is shown as a blind spot. The work is tested from small fixtures, `make check` is green and nothing outside the view changes.

### Reviewers
- Reviewer A: 8 findings
- Reviewer B: 7 findings
- Both reviewers answered the review skill's questions. They agreed independently on four issues: the duplicated row renderer and role tables, the missing empty band on the page, the `"threads"` tag in `health()`, and the folder outside "Where". They diverged on where the scout status goes wrong.

### Act On

1. **An ended scout with no Report still reads "researching"** (A1). `request()` decides the state from the file alone, and `threadChip` puts that state ahead of the thread's liveness. A scout that crashed or was settled early is the one case the user most needs to see, and the page says it is still working. The drawer contradicts itself: the heading says "ended" and the line under it says "researching". The fix:
   - Show "researching" only while the thread is out.
   - Give an ended scout with no Report its own amber state.
   - Add a test for that case.

2. **`Status: not done` is drawn as a green "reported"** (A2, with the concrete parts of B6 folded in). Any Status other than `blocked` maps to `ok`. The scout template allows `done | not done | blocked`, and the scout skill's settle check treats anything but `done` as unfinished. So the view and jbus disagree about whether the work is finished. The fix:
   - Map `done` to reported, `blocked` to blocked, and anything else to a non-`ok` state.
   - Match case-insensitively. B6 points out that `Status: Blocked` currently shows as reported.
   - Read the Status line the way the settle check reads it.
   - Test a last Report whose Status is `not done`.

3. **The page leaves out the band when the thread list is empty** (A5, B2). The "Done when" line says each project's row *and page* has a Threads band. On the page the band is dropped, while the overview row draws a calm "0 out" band for the same data. Drawing the band unconditionally meets the line and deletes a special case and its comment. Add a test for the empty list.

4. **One thread row is written twice, and the role names live in two positional tables** (A3, B3). This is new code in this PR, and the two copies already drift: one table says "crews", the other "Crewmates", and the column orders differ, so `r[0]`/`r[2]` mean different things in each. The fix:
   - Keep one `threadRow` with a parameter for the title.
   - Keep one ordered role list with named fields.
   - Derive the band order from that list.

   Both the band and the drawer are inside "Where", so this is cheap to fix now and costly once the two copies drift further.

### Consider

- **The `"threads"` tag in `health()`** (A4, B5). A string in a fourth tuple slot is added only so `projectRow` can filter it back out. It is a special case in a shared helper, kept in step by a comment. Letting `amber()` add the blind-spot reason itself removes it. There is no live bug, and only one caller is affected today, but the fix is small.
- **The `scouts/` source always says "ok"** (B1). This source can never report "missing" or "unreadable", and `request()` turns a permission error into "no request in the home". The tradeoff: a home with no `scouts/` directory may just have no scouts yet, so "missing" may not be the right word for that case. The `OSError` to "missing" mislabel is the part worth fixing: catch only `FileNotFoundError` as missing. The directory-mtime `at` is a weak proxy for when a report was written.
- **The new `panels/thread/` folder is outside "Where"** (A8, B4). The `thread/<role>/<slug>` route likely forces a separate panel name for discovery, and the empty `panel.py` stub is there for that. Either register the drawer from `panels/threads/` or say in the PR why it can't be. Documenting the new `adds.band` hook in `panels/__init__.py` is outside "Where", so that part is for later.
- **The scout Report parse duplicates jbus's rules** (B6). The in-scope parts (case, which Status line counts) ride along with Act On #2. A shared helper in `jbus.threads`/`mirror` is outside "Where" and is for later.

### Noted
- `gates_inside=True` keeps the gate heading in the Report body, and the `re.split` then cuts it off again (A6). Check that the result is equivalent, then drop both along with the docstring sentence. Trivial.
- `_threads` has `home`/`day` defaults that no caller uses (A7). Make both required and drop the guards. Trivial.
- The panel imports the private `_mtime` from state.py (B7). Defining the scouts `Source` beside `SCOUTS` in state.py would match how `PASS_FILE` and `MERGE_LOG` are done. Low impact.

### Dismissed
- None. Every finding traces to a changed line and names a concrete effect. The nits are small but real, not inflated.

### Agreement Map
The reviewers converged on structure: the duplicated renderer and tables, the empty-band special case, the `health()` tag and the extra folder. When two readers independently flag the same four issues, the shape of the new frontend code is the thing to tidy.

They split on correctness, and each found different holes in the scout status, which is the heart of "track the work of scouts":
- A came at it from the user's view: an ended scout shows as researching, and `not done` shows as green.
- B came at it from the sources: the source is always "ok", permission errors read as missing, and the parse disagrees with the settle check.

Neither saw the other's bugs. That pattern suggests the scout status reader was the least-tested part. The existing fixtures cover the happy paths, and both Act On fixes need fixtures for the failure states.
