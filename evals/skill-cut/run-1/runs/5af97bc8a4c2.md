### Intent
> Section 3 of the /deeper design: a step in the home skill's brief writing, not a separate file. It runs on its own for research, perf, analysis and outcome briefs and carries its own copy of the four questions. Answer 2 goes to the scout's `Read:` or the request's sources, answer 3 into the brief for the crew, and answer 4 into `Proves it:`. Mechanical fixes, docs changes and bug fixes with a known cause skip it. The skill's text tests pin the step. `make check` and `jgauge test-slot -- make check` pass. `skills/deeper/`, the principle, `templates/brief.md` and the parser are not touched.

### Act On

**1. The step invents an `Instruments:` line and tells the home to write a `Read:` line that `templates/brief.md` forbids.** Raised by A1 and B1, at `skills/home/SKILL.md:530` and `:537`.
- No template, skill or parser defines `Instruments:`.
- The scout skill fills only the five template lines, so a scout writing from a request drops answer 3.
- The template, which the home is told to read first, says home-written briefs leave `Read:` out.
- "Though the home wrote it" names the conflict without resolving it. The template is under "Do not touch", so this PR can't settle it by editing the template.

Why it matters: a home following both texts gets opposite instructions, and answer 3 reaches the crew only by luck. The intent says answer 3 goes "in the brief for the crew", not into a new field.

Fix within "Where":
- Send answer 3 to a line the template already has, such as `Change:`, the Done-when list or the task body.
- For a home-written brief, either route answer 2 through the scout path, or keep it in the body and record the template follow-up in the Result.

**2. The step is keyed on the playbook name, not on the kind of work.** Raised by A2, B2, A3, A4 and B3, merged here because one remedy fixes all of them. Locations: `skills/home/SKILL.md:520–533` and `:430`, and `tests/test_home_deeper.py:136–140` and `:163`.

The concrete paths are traced, not hypothetical:
- **Bug fixes always skip.** `bug-fix` is the playbook for root-causing an unknown defect, yet it always skips. The boundary exempts only a fix whose cause is proven, and the test pins the wrong behaviour under the label "known bug".
- **Outcome work skips under common playbooks.** Outcome work under `feature`, `autonomous-run` or `swarm` skips, so the step reaches outcome briefs only when no playbook is picked.
- **Scout requests always run.** Their playbook is always `investigation` or `trace-forensics`, so a request for a docs-change or refactor brief still gets the four questions. That breaks the second Done-when line.
- **The list goes stale silently.** The ten-name arm is a hand-kept copy, and the test only checks it in one direction.

Why it matters: this is the step's core decision, and it misfires in both directions.

Fix: make the home state the kind of work as the input in every case (research, perf, analysis, outcome, known-cause fix, mechanical, docs), and let the playbook be at most a default. For a request, the kind is the kind of the task being briefed. The name list and its stale-list risk then go away. A `Run by:` marker in each playbook is the longer-term alternative, but it touches `playbooks/`, which is outside "Where", so it is a follow-up.

### Consider

- **A request with no brief to deliver loses answers 3 and 4.** Raised by A5 and B4. For a report-only request there is nowhere to put them, and packing methods and the outside judge into the Deliver bullet is awkward. B4's remedy is cheap and uses lines that already exist: write 3 and 4 as `Questions:` items in the request. The tradeoff is small, and it is worth doing alongside Act On 1.
- **No test checks that the lines the step names exist in the templates.** Raised by A6. The current tests do execute the block, which is good, but nothing compares the destinations to `templates/brief.md` and `templates/scout-request.md`. Such a test would have caught Act On 1. Add it once Act On 1 settles the destinations. It's cheap and guards against the same drift.
- **The "already names its data, instruments and judge" skip is a prose override of the block's output.** Raised by B6. If Act On 2 introduces a kind input, adding this as one more kind costs nothing. If not, it can stay as prose.

### Noted
- **Dangling reference.** "The block under it" at `:430` points at a block in another section (B5). It is a one-line clarity fix, so name the section while editing that line for Act On 2.
- **Unshown checks.** `make check` and `jgauge test-slot` are not shown passing (B7). The reviewer ran nothing, so this isn't a code defect. The Result must show both commands passing before merge.

### Dismissed
None. Every finding pointed at a real gap in the changed lines. The nits are minor, but none is wrong.

### Agreement Map
Both reviewers independently found the same three things:
- the `Instruments:`/`Read:` clash with the template,
- the `bug-fix` misclassification,
- the hand-kept playbook list.

That consensus is a strong signal, and both converged on the same root remedy: key the decision on the kind of work.

They diverged on these points:
- Only A saw that scout requests always run the step (A3), which is the mirror image of the bug-fix skip. Together the two findings show the playbook-name key fails in both directions.
- Only B raised the prose-only skip override and the dangling reference.
- A rated the no-brief request gap as a nit and B as a warning. It sits in Consider: a real gap with a cheap fix.

The pattern says the step's wording and tests are sound. Its two load-bearing choices are what need rework: where answer 3 lands, and what decides whether the step runs.
