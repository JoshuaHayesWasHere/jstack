### Intent
> Task: the audit's P6. Once a crewmate has written `fixed and green`, a third rebase forced by main is not made. The crewmate writes one stop line in its Result and pipes a gate, and jbus surfaces the pull request as waiting. The count is kept where jbus or jmerge can read it. A test drives three rebases and finds the stop on the third. `make check` and `jgauge test-slot -- make check` pass. The rebase push stays `--force-with-lease`, untouched.

### Reviewers
- Reviewer A: 6 findings (3 warnings, 3 nits)
- Reviewer B: 5 findings (4 warnings, 1 nit)
- Both reviewers worked through the review skill's questions. They agreed on three issues: the jbus step mapping, the `Fixed:` proxy, and the untested `waits()` path.

### Act On

**1. The held pull request shows as waiting on its crewmate, not on the user** (A1, B1)
`REBASE_HELD` maps to the `rebase` step at src/jbus/merge.py:97, which is drawn as "Rebase, its crewmate". After the hold, the crewmate cannot act until a `Rebase hold lifted:` line exists. The only party who can clear it is the user. While the gate is open, the `asking` pattern hides the problem. Once the gate is answered with the default, the row reads "its crewmate" for good. This contradicts the PR's own text ("jbus lists the gate as waiting on the user"), and the test table locks the wrong mapping in. Both reviewers found it independently, with a concrete path. Move the rule to `hold` and change tests/test_jbus_merge.py:288 to match.

**2. The count reads the whole brief, not the last Result** (B2)
The awk counts `Fixed:`, `Rebased after fixed:` and `Rebase hold lifted:` lines anywhere in the file. SKILL.md:159 says every block reads the last result. Here is the path: two rebases happen in round one, then a steer starts a follow-up round. The first conflict of the new round is held immediately. Steers are routine, so this is a real path. The fix is small: reset the counters on `/^## Result/`.

**3. Re-running the block on a held head parks a second gate** (A3)
The block writes the hold line once per head but prints `hold:` on every run, and the prose says "on `hold`, park a gate". mainmoved.py wakes red PRs on every main commit, and a held PR is often red. So each wake parks a duplicate gate asking the same question. The run-twice case is exactly what question 4 asks about. Print a different word when the line already exists, and park a gate only on the first `hold:`. (See B5 below: the "already exists" check should use the same rule as `rebase_held`.)

**4. The test does not exercise jmerge's `waits()` path, or a rebase that stops on a conflict** (A5, B4)
The test runs the shell block for real, which is good. But it checks jmerge only through `ready.rebase_held` directly. Two things could be deleted without failing any test:
- The cli.py:703 placement (after `ready.held`, before `short_of`, with the early return).
- The `counted` call in the conflict-stop branch.

Every main move in the test touches an unrelated file, so no rebase ever stops. "jbus surfaces it as waiting" is a done-when line, and finding #1 above slipped through for this very reason. Add:
- a stopped-rebase case that asserts a `Rebased after fixed:` line is written;
- a `waits()`-level assertion that a PR at the held head reports `REBASE_HELD` and maps to `hold`.

### Consider

**5. The cap starts at `Fixed:`, not at "fixed and green"** (A2, B3)
This is a real proxy. `Fixed:` is written right after the push, and `Fixed: none needed` is written whatever CI says. So rebases made while CI is red use up the cap. The PR already explains the choice: `fixed and green` is sent to the home and never written to the brief. The tradeoff is that the faithful fix needs a new green marker written from another flow, which widens the change. Rebases on a red PR are arguably the same churn the cap exists to stop. The deviation is documented. Accept it, or add the marker in a follow-up. Either is defensible; I lean toward accepting it.

**6. The hold is recorded at the local HEAD, while jmerge compares GitHub's head** (A4)
The path is narrow but real: the push is refused after the second rebase, then main moves again. The block records an unpushed head, jmerge never matches it, and it reports some other reason. The fix is one line, since the block already has `pushed` from `gh pr view`. It is cheap enough to fold in.

**7. The "once for a head" check accepts any old hold line, not the current one** (B5)
The block's de-dup and `rebase_held` disagree. After a hold is lifted, a conflict stop and an abort can leave the branch back at the same head. The block then sees the stale line and writes nothing, while jmerge, reading the last line, sees "lifted". The path is contrived alone, but the fix belongs with #3: de-dup against the last hold-or-lift line, as `rebase_held` does. Doing #3 without this would build on the inconsistent check.

### Noted

### Dismissed
- **A6: the test helper's `home` argument also switches the slug.** This is a style preference about a test helper, and the harm depends on a future caller that doesn't exist. Nitpick.
