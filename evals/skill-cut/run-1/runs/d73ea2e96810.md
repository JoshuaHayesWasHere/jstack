### Intent
> The user asked, on 2026-10-15, that this project be added to jbus and that every new home be added to the bus. `/new-home` already registers a repo, but a home started by `/home`, or one made before that step existed, never does. This change has three parts:
> - The home skill's start registers its repo through `jbus project add`, using the same block as new-home's step 3, so the two cannot drift.
> - A home that merges its own pull requests writes `home-thread` first, so `jmerge` does not race it.
> - jbus reports homes with a `home-id` that are not in the config, as a quiet pass line, in `jbus status` and as a count on the view's machine row. It does not add them itself.

### Reviewers

- Reviewer B: 5 findings
- Neither reviewer named a "Done when" line the change fails. Neither raised anything against the pass, the status listing, the view count or the tests beyond A5's docstring. Two findings were raised by both: A1/B1 and A2/B4.

### Act On

**1. Step 3 of the start calls the deliberate switch a stale leftover** (A1, B1)
- `skills/home/SKILL.md:171-178` still says an id in `home-thread` was left by "a home that started before the id moved to `home-id`".
- The row at :74 still opens with "not this home's id".
- After this change, every self-merging repo hears at each start that a legacy id is blocking jbus. B1 traces the real harm: the user empties the file as told, and then jbus and the home both merge. That is the race this task exists to prevent.
- Both reviewers found it on their own. The fix is a wording change inside **Where**.
- Reword both places so an id written by "On the bus" reads as the switch set on purpose. A1's alternative is to write a fixed marker. `home_thread` only checks that the file is non-empty, but a thread id is more informative, so keep the id and fix the prose.

**2. new-home still says it writes none of the switches** (B2)
- In the same file as the new writer, `skills/new-home/SKILL.md:171` says "written by hand" and :175 says "this skill writes none of them".
- One skill now gives two opposite rules about the merge switch. Fix both lines in this PR.
- The same stale claim sits in `skills/handoff/SKILL.md:199`, `docs/state.md:18` and `docs/configuration.md:151`. Those files are outside **Where**: note them for a follow-up, not this PR.

**3. A literal `nothing` would turn jbus merging off** (B3)
- The placeholder itself reads "or nothing". The only guard is that `<` and `>` are gone, and any non-empty `ME` gets written to `home-thread`.
- An agent filling in `ME='nothing'` is a likely mistake, not a remote one. The result is silent: jbus stops merging the repo, and the block reports that as success.
- This is the rule-in-prose case the scope warns about. Make the block reject a value that is not shaped like a thread id and print `not filled in`. The check costs a few lines.

### Consider

**Dead branches in "On the bus"** (A2, B4)
- Step 5 calls the block only after step 4 printed `no project:`. So the `on the bus` and `jbus is not installed` branches, and the prose at :321, never run from a real start. The test that reaches `on the bus` calls `machine.start()` directly.
- There are two ways out:
  - A2's: drop the block and name the checkout from `git rev-parse --git-common-dir` or from the `no project:` line.
  - B4's: run the block on every start, so it is the check itself.
- Either removes a branch table. B4's version also makes the test exercise a real route.
- This is simplification, not correctness, which is why it is not in Act on. It is a clear win if the author is touching the block anyway for item 3 above.

**`status()` docstring contradicts the code** (A5)
- "which no pass leaves" is wrong: `poll` writes the list to `status.json`, and the view and the next pass read it from there.
- It is a one-line fix, and a wrong docstring here would mislead whoever next changes the pulse.

**Docs paragraphs split the command from its argument bullets** (A6)
- In `docs/jbus.md:190-192`, the bullets for `<name>`, `--checkout` and `--project-id` now sit under the "homes not on the bus" paragraph.
- Moving the two new paragraphs below the bullets costs nothing and keeps "Add a project" readable.

### Noted
- **Race after a concurrent add** (A3). The window between step 4 and the block is seconds. Also, a home whose rules say it merges itself should have the switch set no matter who added the project, so writing it on `already` is arguably correct. A one-line notice on `already` with `ME` set would be harmless, but nothing breaks without it.
- **Empty folder name from a trailing slash** (A4). It only happens with a hand-filled `C` ending in `/`, and the add then refuses the name anyway. Stripping the slash is cheap but low-impact.
- **`project` → `one` renames in `poll` and `alarm`** (B5). These lines do not trace to the task, and `first(project: ...)` still shadows the module. Reverting them is cosmetic.

### Dismissed
None. Every finding was accurate about the changed lines. The ones I filtered out were filtered on impact, not on correctness.
