### Intent
> Section 3 of the /deeper design: a step inside the home skill's brief writing, not a separate file and not a call to `/deeper`, which stays manual. For research, perf, analysis and outcome briefs, the step has the home answer its own copy of the four questions. Answer 2 (the rawest material) goes into the scout's `Read:` or the request's sources, answer 3 (methods and tools) into the brief for the crew, and answer 4 into `Proves it:`. Mechanical fixes, docs changes and bug fixes with a known cause skip the step. The home skill's text tests cover the step, and `make check` and `jgauge test-slot -- make check` pass. Changes stay within `skills/home/SKILL.md`, `templates/scout-request.md` and the home skill's tests. `skills/deeper/`, the principle, `templates/brief.md` and the parser are untouched.

### Act On

**1. `Instruments:` is a line nothing defines, and a `Read:` line on a home brief contradicts `templates/brief.md`** (A1, B1)
`skills/home/SKILL.md:530`, `:537`. The step tells the home to write a field that no template, skill or parser knows about. The phrase "though the home wrote it" admits the clash with the template rule that "any other brief the home writes leaves all five out" but does not resolve it. The scout skill fills only the template's five lines, so in a scout-written brief answer 3 silently disappears. The task asked for answer 3 "in the brief for the crew", not for a new field.
- **Fix within Where:** send answer 3 to a line the template already has. Use the Done-when list, or plain task-body text that says it is for the crew.
- **`Read:` on home briefs:** either drop it, or name the conflict in the Result as a follow-up for `templates/brief.md` and `skills/scout/SKILL.md`. Both files are outside Where.

**2. The case statement decides by playbook name, not by kind of work** (A2, B2, A3, A4, B3)
Merged because one fix resolves all five.
- **Concrete failure:** `bug-fix` always skips, but its playbook covers bugs whose root cause is still unknown. The principle exempts only a proven cause.
- **Outcome work never gets the step** under `feature` or `autonomous-run`, though the intent names outcome briefs explicitly.
- **For scout requests** (`:430`), the scout's playbook (`investigation` or `trace-forensics`, both in the arm) decides. So every request gets the four questions, even when it is briefing a docs change.
- **The ten-name arm** (`:526`) is a hand-kept copy that drifts. The test checks only one direction, and a new research playbook would skip silently.
- **Fix:** key the block on a kind the home states for every task (research / perf / analysis / outcome / known-cause-fix / mechanical / docs). For a request, use the kind of the task being briefed, not the scout's kind. The name list then disappears.
- **Tests:** the test that pins `bug-fix` as "known bug" (`tests/test_home_deeper.py:163`) must change with this. Add a case for a bug fix with an unknown cause and one for outcome work.

### Consider

- **Answers 3 and 4 in a request with no brief to deliver** (A5, B4). As written they are worked out and then dropped, and packing them into a single Deliver bullet is ad hoc. B's fix is cheap and uses lines the template already has: write 3 and 4 as `Questions:` items. Alternatively, say plainly that the step stops at answer 2 for such requests. Either is one sentence.
- **The "already names its data, instruments and judge" skip is prose-only** (B6). It overrides the block after the block has printed. Once the block takes a kind (Act On 2), this can become one more input value and cost nothing. Fold it in if it fits; otherwise leave it.
- **No test ties the named brief lines to a template** (A6). After Act On 1, a test asserting that every line the echoed questions name exists in `templates/brief.md` is cheap. It would have caught finding 1 and executes something (it parses the echoed output against the template). Worth adding with the fix.
- **"The block under it" at `:430` points 90 lines away into another section** (B5). The skill is read by an agent, so an ambiguous reference costs more here. A one-phrase fix.

### Noted

Both are Done-when lines, though, and the Result must report their actual outcome after the fixes above. The same applies to the Proves-it requirement that the Result say how the post-merge brief check was prepared.

### Dismissed

None. Every finding was concrete and within scope. A5 and B6 were mild but not nits, and B5 is a real readability snag in agent-facing text.

### Agreement Map

The reviewers converged independently on the three structural problems: the undefined destination line, the playbook-keyed skip, and the hard-coded list. That consensus, plus a concrete execution path for each (`picked='bug-fix'` prints the known-cause skip), is why they land in Act On.

The divergences were about severity, not substance:
- On answers 3 and 4 in a no-brief request, A called it a nit and B a warning.
- A alone traced the scout-request path (A3).
- B alone flagged the prose override (B6), the dangling reference (B5) and the unrun checks (B7).

The pattern says the change's core flaw is one design choice. Using the playbook name as a stand-in for the kind of work produces most of the findings, and replacing it with a stated kind deletes the list, the special cases and the wrong skips together. Separately, the step writes into a brief shape it is not allowed to change, so it must use existing lines or log the follow-up explicitly.
