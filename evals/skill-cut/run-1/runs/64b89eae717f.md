### Intent
> Make each project's threads obvious, and let the user follow the work of scouts and crewmates. Each project's row and page gets a Threads band from `pass.json` `projects[name].threads`, grouped by role. Threads that are out come first, with liveness and last write. Threads that ended today are dimmed, and the rest are folded. `#/<project>/thread/<role>/<slug>` opens a drawer showing what the thread works on. One new read-only source, each scout request's `## Report` and `Status:` under the home's `scouts/`, says researching, reported or blocked. A pass that left no thread list is shown as a blind spot, never as none. Tests use small made-up fixtures, and `make check` and `jgauge test-slot -- make check` pass. Work stays in `state.py`, `view/__init__.py` (only if needed), `panels/threads/`, `page.html` and the tests. The view only reads, vanilla JS only, and the CSP and ports stay untouched. Mockup-b's Threads band and drawer are the design.

### Reviewers
- Reviewer A: 8 findings
- Reviewer B: 7 findings
- Both answered the review skill's questions. They agreed on four issues: the duplicated row and role tables, the `health()` tag, the missing empty band on the page, and the out-of-Where `thread/` panel.

### Act On

1. **An ended scout with no Report still reads "researching"** (A1). `request()` decides the state from the file alone. A scout thread that crashed or was settled early shows a dimmed "researching" chip, and its drawer heading says "ended" above "researching". The task is to let the user track scouts, and this is exactly the case that needs their attention. The chip says the scout is still working. Only say researching while the thread is out. Give ended-with-no-Report its own amber wording, and add a fixture for it.

2. **The Status line is read wrong, so `not done` shows as a green "reported"** (A2, B6, merged). Any Status other than `blocked` maps to `reported`, which gets an `ok` chip. The scout template allows `done | not done | blocked`, and the skill's settle check treats anything but `done` as unfinished. B6 adds two more gaps:
   - `request()` takes the *first* `Status:` in the Report, while the skill takes the *last*.
   - The match is case-sensitive, so `Status: Blocked` shows as reported.

   Fix inside `request()`: map `done` to reported, `blocked` to blocked, and anything else to a non-`ok` state. Use the skill's last-Status rule and match case-insensitively. Test a last Report whose Status is `not done`. Moving the parse into a shared helper in `jbus.threads` or `mirror` is outside Where, so that part is noted for later.

3. **`scouts/` source health is a proxy that always says ok** (B1). `seen` never passes `path` or `read`, so a home with no `scouts/`, or one that can't be read, still shows `ok`. `request()` also folds every `OSError` into "missing", so a file that exists but can't be read is reported as "No request in the home". The task makes this the one new source the server reads, so its health has to be true.
   - Pass `path` and `read`.
   - Treat only `FileNotFoundError` as missing.
   - Test a home with no `scouts/` directory.

   The directory mtime as `at` is also a weak signal, since appending a Report doesn't change it. That one is worth a line in the PR but needn't block.

4. **A project page with an empty thread list draws no band** (A5, B2). This breaks the "each project's row **and page**" line of Done when. The row draws a calm "0 out" band, and the page draws nothing from the same data. This is not the blind-spot case: a missing list is a blind spot, while an empty list is "0 out". Drop the special case and draw the band on both, which deletes code.

5. **The thread row and the role tables are written twice** (A3, B3). `about()` in the drawer copies `threadRow()` line for line. `ROLE` (page.html) and `ROLES` (threads panel) are two positional tables with different column orders, and they already disagree on names ("crews" vs "Crewmates"). This is new code in this PR, and it will drift on the next role or note. Keep one ordered role list with named fields and one row renderer with a title-link parameter.

### Consider

- **The `"threads"` tag in a fourth `health()` slot** (A4, B5). A magic string is filtered by one caller and explained in prose. It's cheap to remove: let `amber()` add the threads reason itself, or let the row build chips without it. It's not urgent, since there is one caller today.
- **`panels/thread/` lives outside Where, and `adds.band` is undocumented** (A8, B4).
  - The route likely needs a drawer kind, and Where allows route work in `__init__.py`, so this is defensible.
  - Either justify it in the PR, or register the drawer from `panels/threads/` and drop the empty `panel.py` stub.
  - Documenting `adds.band` in `panels/__init__.py` is outside Where, so it's noted for later.
- **`gates_inside=True` followed by a `re.split` that undoes it** (A6). If A6 is right, both lines and the docstring sentence go. Do it while rewriting `request()` for item 2, after checking the result matches.
- **Unused defaults on `_threads`** (A7). The only caller passes both values, so making them required deletes two guards. This is a cheap deletion.
- **`_mtime` imported across modules** (B7). Define the scouts `Source` in state.py beside `PASS_FILE` and `MERGE_LOG`. This falls out naturally from the item 3 fix.

### Noted
- Moving the shared Report/Status parse into `jbus.threads` or `mirror` (from B6) is outside Where and left for later.
- Moving `threadChip`/`LIVESAY` out of the page shell (part of B3) is optional once item 5 is done.

### Dismissed
- None outright. No finding was a "different approach" preference or missed context. B4's note on `probe.js` was already self-resolved as test scope.

### Agreement Map
The reviewers converged independently on the structural issues: the duplicate renderer and tables, the `health()` tag, the empty-band gap, and the extra panel folder. That consensus makes items 4 and 5 solid.

They diverged on where they looked:
- A traced the scout state semantics: ended-without-Report and `not done`.
- B traced source health and parse fidelity: the always-ok source, OSError handling, and the first-vs-last Status.

Both strands are about the same thing, which is whether the scout status the page shows is true. That is the core of what the user asked for. The correctness work concentrates in `request()` and the scouts `Source`, and fixing items 1–3 together, plus the A6/A7/B7 cleanups, is one focused pass over a small area.
