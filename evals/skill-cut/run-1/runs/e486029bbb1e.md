### Intent
> Task P6 of the pstack catch-up audit. In `skills/crew/SKILL.md` "A conflict": once a crewmate has written `fixed and green`, it does not make a third rebase forced by main. Instead it writes one stop line in its Result and pipes a gate, and jbus shows the pull request as waiting. The count is kept where jbus or jmerge can read it, and a suite test drives three rebases and finds the stop on the third. `make check` and `jgauge test-slot -- make check` pass. Where: the crew skill's "A conflict" section, `src/jmerge/` or `src/jbus/`, and the tests. Do not touch how a rebase is pushed.

### Reviewers
- Reviewer A: 6 findings (3 warnings, 3 nits)
- Reviewer B: 5 findings (4 warnings, 1 nit)
- Both reviewers raised two findings independently: the board showing the wrong owner, and `Fixed:` standing in for "fixed and green". Both also flagged the same test gaps. Both answered the review skill's questions.

### Act On

1. **The held pull request is shown as waiting on its crewmate when it is waiting on the user** (A1, B1). `REBASE_HELD` maps to the `rebase` step, which `work.py:287` draws as "Rebase, its crewmate". The crewmate is forbidden from acting until a `Rebase hold lifted:` line is written. While the gate is open, the `asking` pattern hides the mismatch. Once the gate is answered, or if it is never parked, the row reads "its crewmate" for good. That contradicts the skill's own text ("jbus lists the gate as waiting on the user") and the Done-when line's intent that jbus surface the stop. The repo already sends user-only wait reasons such as `NOT_UPHELD` and `UNRULED_DROPS` to `hold`. The fix is to move the pattern to the `hold` rule and change `tests/test_jbus_merge.py:288` to `"REBASE_HELD": "hold"`.

2. **The count starts at `Fixed:`, not at "fixed and green"** (A2, B3). The first Done-when line names "fixed and green". The block starts counting at the `Fixed:` line instead. That line is written right after the push and before CI passes, and `Fixed: none needed` starts it too. Rebases made while the head is red use up the allowance, so a pull request can be held before it was ever green. The cost runs toward over-holding, which is safe, so this is not dangerous. But it is a Done-when line the change does not meet, and the PR's reason for the substitute is that no written marker exists, which is a gap the PR could close itself. The fix is to have the crewmate write a brief line when it sends `fixed and green` and count from that line. If the user prefers the proxy, the PR should state the deviation explicitly so it is a recorded decision and not a silent substitution.

3. **The count spans the whole brief, not the last Result** (B2). SKILL.md:159 says every block reads the last Result. This awk matches `Fixed:` and `Rebased after fixed:` lines anywhere in the file. A follow-up round therefore inherits the earlier round's two rebases, and its first conflict is held at once. The path is concrete, since steers start follow-up rounds routinely. The fix is to reset the counters on `/^## Result/`.

4. **Running the block again on a held head parks another gate** (A3). The block prints `hold:` on every run, and the prose says to park a gate on `hold`. `mainmoved.py` wakes red pull requests on every main commit, and a held pull request is often red. Each wake would therefore park a duplicate gate for the same question. This is the run-twice case: what the block prints should depend on the state left by the first run. The fix is to print a distinct word (for example `held:`) when the line already exists, and park a gate only on the first `hold:`. B5 should be folded into this fix (see Consider).

### Consider

- **The hold line records the local HEAD, not the pushed head** (A4). After a refused push followed by another main move, `Rebase hold: at <unpushed>` never matches jmerge's `one.head`, so jmerge reports some other reason. The path is narrow, but the block already has `pushed` from `gh pr view`, so the fix is one variable. It is worth taking while the block is open for items 3 and 4.
- **De-dup checks any earlier hold line, while jmerge checks the last hold-or-lift line** (B5). The scenario is: lift, a rebase stops on a conflict, `git rebase --abort` returns to the same head. That is more plausible than it sounds, because aborting restores exactly the earlier head. Whether a new hold even follows depends on how a lift resets the count. If item 4 is fixed by de-duping against the last hold-or-lift line (the rule `rebase_held` already uses), this goes away for free. I recommend doing it that way.
- **Test coverage of the jmerge path and the stopped-rebase count** (A5, B4). The test the task asked for exists and executes: it runs the shell block through three rebases and finds the stop. That meets the "Proves it" line. Two paths are still unexercised:
  - the `rebase_held` placement inside `waits()` at cli.py:703, which is the part that makes jmerge surface the hold;
  - the `counted` call on a rebase that stops on a conflict.

  Deleting either would not fail the suite. Adding one `waits()` assertion and one conflicting move of main is cheap. Since item 1 already requires changing the test table, I'd add them in the same pass, but they don't block on their own.

### Noted
- **The test helper's `home` argument also switches the slug** (A6). This is real coupling in a test helper with one caller. It is harmless now and can be tidied if a second caller appears.

### Dismissed
None. Every finding pointed at a concrete path or a stated rule in the skill. None was a preference.

### Agreement Map
The two reviewers converged on the two most important problems: the wrong owner on the board, and the `Fixed:` proxy for "fixed and green". Two independent hits on each is a strong signal that both are real. They also overlapped on the test gaps, each from a different side. A noticed the bypassed jmerge `waits()` path, and B added the never-run conflict-stop branch.

Where they diverged, each found a separate state-reading bug in the same awk/grep block:
- B: the scope of the count (whole brief versus the last Result).
- A: idempotency of the hold output.
- A: which head the hold line names.
- B: inconsistent de-dup against lifts.

The pattern says the core mechanism (count, hold, gate) is sound, but the block reads brief state looser than the rest of the system does. jmerge and the "read the last result" convention are both stricter. Tightening the block to the same rules jmerge uses (last Result, last hold-or-lift line, pushed head) closes items 3 and 4 and both Consider items about the block in one coherent edit.
