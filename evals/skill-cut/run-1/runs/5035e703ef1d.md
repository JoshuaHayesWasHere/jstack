### Intent
> Topic 10 of the user's 2026-10-15 re-homing: "A way to undo a bad merge into standing.md." The home skill (including scoped homes) and the handoff skill run `jbus snapshot` right after any edit to `$H/standing.md`. That way each edit is its own commit in `~/.local/state/home`, and it is pushed. The twice-daily timer stays. `jbus snapshot` takes `--why <text>`, which goes after the time in the message. `docs/state.md` gains "Undo an edit to standing.md" (find with `log -p`, restore with `show <commit>^:...`, re-snapshot with `--why`). Tests run in a temporary tree with a bare remote, and `make check` exits 0. Size S.

### Act On

**1. Snapshot runs are not locked against each other or the timer** (A1, B1 in part)
The change moves `take` from a once-or-twice-a-day job to one that any home can trigger at any moment. It does `add -A` → `reset`/`commit` → `push` on one shared index with no lock. The failures are concrete, not hypothetical:
- Overlapping runs collide on `.git/index.lock`. If the timer's run loses, `OnFailure` fires `--alarm` to the desk and every project for nothing.
- One run's `git reset -q` can wipe another run's staging, so that run commits nothing. The edit then never gets the commit the task promises.

Fix: an exclusive `fcntl.flock` on a file under the tree's `.git`, held across add/commit/push in `take`. This is in `snapshot.py`, inside Where. Add a test that runs two `take` calls concurrently.

**2. The documented restore empties the live `standing.md` when `git show` fails** (A2, B2)
The shell's `>` truncates the target before `git show` runs. Ordinary cases make `git show` fail:
- undoing the edit that created the file (`<commit>^` has no such path),
- the root commit,
- a mistyped hash.

Each leaves an empty rules file, and the doc's next step tells the user to snapshot it. This is the undo path the task exists to provide, so it has to be safe. Fix: use `git -C ~/.local/state/home restore --source=<commit>^ -- <repo>/standing.md`, which writes nothing on failure. Alternatively, write to a temp file and `mv` it only on success. Also say in one line what to do when the bad edit created the file. Add the test both reviewers asked for, where `<commit>` is the commit that created the file.

**3. The handoff skill gains a rule-writing duty nobody asked for** (A5, B3)
"One it did not write yet goes there now, as one dated line" is new behaviour. It contradicts the sentence just before it ("the home wrote it to `standing.md` when it heard it"). The task asked only for a snapshot after an edit. Cut it, and leave the general instruction: "after any edit to `$H/standing.md`, run `jbus snapshot --why ...`". This also removes the hardcoded `added` that A4 saw drifting from the other two copies.

### Consider

**Whole-tree commits carry a `--why` that describes only part of them** (A3, B1 in part)
`take` still does `git add -A`. So a "jstack standing rule 28 added" commit also sweeps in briefs, `merge.log`, other repos' trees and so on. If two homes of one repo both edit `standing.md` before either snapshots, both edits land in one commit, and undoing "the bad one" reverts both.

How much this matters:
- The path-limited `log -p` and `show` in the doc still work, so undo works in the common case.
- The lock from Act On 1 narrows the two-edits window but does not close it.

The tradeoff: a path-scoped form (`jbus snapshot --why ... -- <repo>/standing.md`, committing with `git commit -- <path>`) would make "a commit of its own" literally true and the message accurate. But it widens the CLI beyond the "one flag" the brief settled on. It is a small change inside `snapshot.py`, and I lean toward doing it if it stays a few lines. Otherwise, take it up as a follow-up.

### Agreement Map
Both reviewers independently found the same three real problems:
- the missing lock on a tree that is now written concurrently,
- the truncating restore command,
- the invented handoff duty.

That consensus, plus concrete execution paths in each case, is why they are Act On. They split on severity for the handoff line (A: warning, B: nit). I side with A, because it changes what a skill does.

A separated "mixed commits" (A3) from locking (A1). B folded them together. Separating them is right: the lock fixes the failures, and path-scoping fixes the meaning of the commit.

The rest of each reviewer's list is nits about scope and tests. That pattern says the core implementation (flag, message, test harness) is sound. What needs work is how the change behaves now that snapshots run often, and the safety of the documented undo.
