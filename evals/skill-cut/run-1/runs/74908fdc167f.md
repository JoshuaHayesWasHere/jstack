First, answer from the code, with a test, whether jmerge's "fails over today's main" check runs on the merge result, and make it do so when main changed a caller or dependency of the PR's files. Second, settle from T3's own tool schema whether a T3 launch takes an effort setting, and record the decision in THIRD_PARTY.md, with nothing ever above medium. Both `make check` and `jgauge test-slot -- make check` must pass. Proves it: the merge-result test, and the T3 schema quoted in the Result.

### Act On

1. **The effort shape has no source, and no test pins it** (A1, B4). Both reviewers found this independently. The repo's T3 schema types `options` as `{"anyOf": [{}, {"type": "null"}]}`. So the `[{"id": "effort", "value": ...}]` shape isn't "read from T3's own tool schema," and the schema test passes any shape.
   - This misses a "Done when" line and the "Proves it" line.
   - If the shape is wrong, every Claude role silently launches at T3's default. By the PR's own account that default is `high`, which is exactly what the user's rule forbids.
   - Fix: cite a real source (T3's model-options contract or provider code, or a captured accepted launch) and test against it. If no source can be found, record the question with `jbus gate`.

2. **The PR moves a module, and main adds a caller under the old name** (B1). This is a concrete path through the exact case #613 exists for. `related` builds `ours` from `one.files` only, and GitHub lists only the new path of a rename. A caller of the old path that main adds is therefore never matched. The check stands and the PR merges onto a broken import.
   - The fix is cheap: pass `left` into `related` with empty text.
   - Add a Kitchen test with a `git mv` plus a new caller on main.

3. **An unreadable head fails open** (A3). When `git show <head>:<path>` fails, the file reads as empty, so no dependency can match and the check stays green.
   - Everywhere else in jmerge, a git failure blocks the merge, and elsewhere in `cli.py` the PR head is fetched via `refs/pull/<n>/head`.
   - A merge gate that passes on a read error is a correctness bug.
   - Fix: check that the head commit exists and fetch it if needed. If it still can't be read, return a stale reason. Add a test for this.

4. **Bare-name sibling imports in `tests/` are missed** (A4, B2). Both reviewers found this, and the evidence is concrete in this repo. The PR's own new test imports `from test_jmerge_fresh import ...`, and about ten test files do the same. `modules()` only yields `tests.test_jmerge_fresh`, so a main change to the shared `Kitchen` fixture never makes a dependent PR stale.
   - This is the "main changed a dependency" case the task targets.
   - Fix: add the bare module name for files under a pytest import root (`tests/`), plus a test for that case.

5. **The "never above medium" claim covers roles nobody checked** (A2). THIRD_PARTY.md and the jroles docstring say the rule holds for every role the map names. Codex and Grok lines send no effort, and their T3 defaults were never looked up.
   - The user's rule is absolute, so an unverified claim of compliance is worse than an honest gap.
   - Minimum fix, inside **Where**: narrow both texts to Claude lines and gate the Codex/Grok default question.

### Consider

- **Path mentions in prose count as dependencies** (B3). A PR that edits THIRD_PARTY.md or docs/ goes stale whenever main touches a path those docs name. For a guarded PR without `fresh-check`, that means a forced rebase. The check fails closed, so it's safe, but it's noisy, and this PR itself would trip it. Limiting path matches to files the check executes or loads (code, Makefile, CI config) is a small change.
- **Three doc files changed outside Where** (A7): `docs/configuration.md`, `docs/jmerge.md`, `docs/jroles.md`. Each one describes the new behaviour, so keeping them is probably right. Still, it's the user's call, and the Result should say so as "not fixed, … because."

### Noted

- **Substring path match and suffix-based conftest detection** (A5). This fails closed, and the `myconftest.py` / `xsrc/` collisions are unlikely. Using a basename check is cheap if the code is touched anyway for B3.
- **One `git show` per file and repeated `ast.parse` per pair** (A6, B5). Nobody has measured it against the 300 s pass limit. A single `cat-file --batch` and one parse per file would be the fix if it shows up.
