### Intent
> Every home lands on jbus. When a home starts and its repo has no project in jbus's config, the start finds the T3 project id and runs `jbus project add` through one block shared with `/new-home` step 3, reading `added`, `already` and `needs you` the same way. A home that merges its own pull requests writes its id to `home-thread` before the add, so `jmerge` does not race it. A home that lets jbus merge leaves `home-thread` empty. jbus also lists homes with a `home-id` and no project, but not parties or experts: one quiet line per pass, a line in `jbus status`, and a count on the view's machine row. Nothing but `jbus project add` writes the config, and no other repo is added.

- They agreed on two issues: the stale-id prose in step 3, and the dead branches in "On the bus". Neither reviewer named an unmet "Done when" line or a test that executes nothing, so I take the tests, the view count and the party exclusion as covered.

### Act On
1. **Step 3 of the start still calls an id in `home-thread` an old home's leftover** (A1, B1). A self-merging home now writes that id on purpose. Every later start would tell the user it is stale legacy state, at skills/home/SKILL.md:171-178 and in the row's "not this home's id" clause at :74. If the user follows that and empties the file, jbus and the home both merge. That is exactly the race the task exists to prevent. Both reviewers found this independently, and the fix is inside the "Where" line. Reword step 3 so an id written by "On the bus" reads as the switch set by choice.
2. **new-home contradicts itself about who writes `home-thread`** (B2). Step 3's shared block now writes the switch. Step 4 of the same file still says "this skill writes none of them" (:171, :175), and an agent reading step 4 gets the old rule. Fix both lines in this PR. The lines in handoff/SKILL.md:199, docs/state.md:18 and docs/configuration.md:151 are outside "Where" and are noted for a follow-up.
3. **`ME='<..., or nothing>'` invites a literal `nothing`** (B3). The only check is that `<` and `>` are gone. A model filling in `nothing` or `none` writes that word to `home-thread`. `merge.home_thread` only checks that the file is non-empty, so the repo silently stops being merged by jbus. This is a rule kept only in prose, with a concrete and plausible path. Either reword the placeholder so it has no word to copy, or reject a value that is not a thread id.

### Consider
- **A self-merging start can switch off jbus merging for a project someone just added** (A3). If another thread adds the project between step 4 and the block, the switch is written and the add answers `already`. The window is narrow, and the Done-when line requires writing before the add. Still, the cost is cheap. On `already`, when the block itself wrote the switch, empty it again or say so.
- **Dead branches in "On the bus"** (A2, B4). Step 5 only runs after `no project:`, so the `on the bus` and `jbus is not installed` branches can never run. The test reaches them only by calling `machine.start()` outside the real trigger. Dropping the block and deriving `C` inline, as A2 suggests, removes a guarded block and a branch table. B4's other option, running the check on every start, is also fine. This is not a correctness bug, but simplifying is cheap and makes the test exercise the route a real start takes.
- **`status()` docstring says the opposite of the code** (A5). The list does land in `status.json` and the view reads it. This is a one-line fix to a misleading statement.
- **docs/jbus.md paragraphs split the command from its argument bullets** (A6). The bullets now read as if they belong to the wrong paragraph. Moving the two paragraphs below the list fixes it.

### Noted
- An empty `${C##*/}` from a hand-filled trailing slash (A4). This is hypothetical: the home's own `C` comes from `dirname`, and the result is one stray file, not a folder the pass would list.
- Loop-variable renames in `poll` and `alarm` (B5). The rename is needed in `status()`, but elsewhere it is churn, and `first(project: ...)` still shadows the module. This is low impact. Revert the renames or finish them as you like.

### Dismissed
- None. Every finding was grounded in the changed lines, though B5 and A4 are minor.

### Agreement Map
The reviewers converged on the most important problem, the step-3 prose that now misreports a deliberate switch. They also converged on the dead "On the bus" branches. A1 and B1 independently traced the same path at unchanged lines that the change broke, which is a strong signal. Their other findings diverged but did not conflict. A looked at races and edge cases in the new write (A3, A4) and at docs polish (A5, A6). B looked at consistency across the surrounding prose (B2) and at prose-only rules (B3). Together they show one pattern. The change made `home-thread` something a skill writes, but the guards and wording around it still assume only the user writes it. All three Act On items are that one gap. Close it, and the PR is shippable.
