### Intent
> Topic 10, "A way to undo a bad merge into standing.md": the home skill (including scoped homes) and the handoff skill run `jbus snapshot` right after any edit to `$H/standing.md`, so each edit gets its own pushed commit in `~/.local/state/home`. The twice-daily timer stays. `jbus snapshot` takes `--why <text>`, which goes into the commit message after the time. `docs/state.md` gains an "Undo an edit to standing.md" section covering find, restore and re-snapshot. Executing tests cover the `--why` commit and the documented restore against a temporary tree with a bare remote. `make check` exits 0. No live `standing.md`, no `~/.local/state/home`, and no change to the timer's times.

### Reviewers
- Reviewer A: 7 findings
- Reviewer B: 5 findings
- Both reviewers answered the review skill's questions. They agreed on the substance of every shared finding (concurrency, the restore truncating the file, the handoff's new duty, `docs/jbus.md`) and differed only on severity.

### Act On

**1. `take` has no lock, and this change is what makes concurrent runs happen** (A1, B1)
- Before this change, only the timer ran `take`.
- Now any home, scoped homes included, can run it at any time on the same index.
- Two concrete failures follow:
  - A collision on `.git/index.lock` makes `_must` raise. If the timer's run is the one that fails, `OnFailure` fires `--alarm` and alerts the desk and every project about a failure that isn't real.
  - One home's `git reset -q` between another home's `add -A` and `diff --cached` leaves that home with "nothing changed". Its edit then gets no commit of its own, which breaks the very guarantee the task asks for.
- This is a concrete execution path that both reviewers found independently.
- Fix: hold an exclusive blocking `fcntl.flock` on a file inside the tree's `.git` across add, gitleaks, commit and push in `take`. This is inside `snapshot.py`, so it is in the Where line.
- A test with two overlapping `take` calls would prove it, though one that only shows the lock serializes them is enough.

**2. The documented restore empties the live `standing.md` whenever `git show` fails** (A2, B2)
- The shell's `>` truncates the target before `git show` runs.
- `git show` fails in ordinary cases: the undo of the very first rule (the commit that created the file), a root commit, or a mistyped hash.
- The doc's next step then tells the user to snapshot the empty file.
- Undo is the whole point of this topic, so a documented undo that can wipe every rule blocks the change.
- Fix: document `git -C ~/.local/state/home restore --source=<commit>^ -- <repo>/standing.md`, or write to a temp file and `mv` only on success.
- Say what to do when the bad edit is the one that created the file: remove the file, then snapshot.
- Add a test for that case. The fixture currently never runs it.

**3. Handoff gains a new duty to write rules** (A5, B3)
- The new line "One it did not write yet goes there now, as one dated line" adds a place where rules get written, and the task never asked for one.
- It also contradicts the sentence just before it ("the home wrote it to `standing.md` when it heard it").
- Models execute this file as instructions, so the line is a behavior change, not a wording issue.
- Fix: cut the line and keep only "after any edit to `$H/standing.md`, run `jbus snapshot --why …`".

### Consider

**Whole-tree `add -A` under a `--why` message** (A3, the mixed-commit part of B1)
- A `--why "<repo> standing rule 3 added"` commit also carries whatever else is dirty in the tree, and the message names only the rule.
- The undo still works, because the documented `log -p` and `restore` are path-limited.
- Snapshotting right after the edit, as the skills now do, already makes it that edit's own standing.md commit in the common case.
- Tradeoff: committing only the named path (`--why … -- <path>`) gives honest history, but adds an argument and a second commit mode that the task didn't ask for.
- B's case of two homes of one repo editing the same file before either snapshots isn't solved by path scoping either. The lock plus immediate snapshot narrows it about as far as is practical.
- My recommendation is to leave this for now, or at most a one-word hint in the message that the snapshot is whole-tree.

### Noted
- **The rule lives in prose, in three places** (A4). The task chose skill prose as the mechanism, so this is by design. A `jbus standing add` verb that writes the rule and snapshots in one step would be the durable fix, but it sits outside Where and is for later. The small wording drift is worth evening out if the handoff line is being edited for item 3 anyway: handoff hardcodes `added` while the other two say `<added, changed or removed>`.
- **`docs/jbus.md` is edited outside Where** (A6, B4). The edit is correct and needed, since otherwise the flag would be undocumented on the commands page. Keep it. The brief's Where line should have listed it.
- **Test name** (B5). `test_a_snapshot_with_no_why_says_only_the_time` also checks the `why=` message, and its no-why half repeats the test at line 77. Renaming it and dropping the duplicate half is cheap, but nothing breaks if it stays.

### Dismissed
- **`with_origin` duplicates inline setup** (A7). The new helper is fine. Moving the older inline tests onto it would mean rewriting test lines the task didn't touch, which this review's scope rules out. Leaving two old copies is not a legacy API kept beside a new one.

### Agreement Map
- The reviewers converged on the two real defects: the concurrency introduced by moving snapshots from the timer to many homes, and the truncating restore. They also both caught the handoff's invented rule-writing step. That consensus is why all three are in Act On.
- They diverged only in severity. A rated the handoff line a warning and B a nit. A split the concurrency and mixed-commit issues into two findings where B folded them into one.
- The remaining findings are the reviewers' own lower-severity notes, and none of them shows a broken path.
- The pattern says the core code (the flag, the message and the tests) is sound. The risk sits where the change meets shared state and the shell, so fixing the three Act On items should make this shippable.
